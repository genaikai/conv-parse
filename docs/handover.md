# 실무 전달본 — 무엇을 담고 무엇을 빼나

설계: [design/decision_tree_v4.md](design/decision_tree_v4.md). 판정 결과 파일은 **되짚는 사람**을
위한 것이다 — 턴마다 단계 · 문항 · 확률이 전부 있다. 챗봇을 고칠 사람은 다른 것을 묻는다:
무엇이 제일 많이 터지나, 그중 하나를 보여 달라, 왜 그렇게 판정했나.

```bash
python <저장소>/src/handover.py output/<결과.json>     # → <결과>_handover.json
python <저장소>/src/handover.py output/<결과.json> -o 보낼것.json
```

**LLM 도 kev 도 부르지 않는다.** 결과 파일만 읽어 다시 담으므로, 문구나 담을 항목이 마음에 안
들면 이것만 몇 번이든 다시 돌린다. 같은 결과 파일이면 언제나 같은 전달본이 나온다.

로직은 `ragdiag/features/handover/`, 진입점은 `src/handover.py`. `FEATURES` 등록부에는 없다 —
파이프라인에 끼지 않고 따로 불린다. v3 결과 파일(`analysis_results`)은 읽지 않는다.

## 모양

```
생성일시
대상        { 로그 · 분석한 턴 · 실패로 판정 · 정상으로 판정 · 검토 · 오류 }
제외한_실패  고정 문장 — 이 방법으로 안 보는 것
분류[]      { 묶음 · 고칠_곳 · 건수 · 들어온_길{이유 문장: n} · 사례[] }   건수 많은 순. 정상 · 검토 제외
              사례 { 질문 · 답변 · 사용자_반응 · 분석 {
                       사유 · 지나온_단계[] · 근거_위치[] · 근거_구절{} · meta_data{대화 · 턴 · 부서 · 직급 · 직무} } }
플래그      { 앞 턴 누락 · history 재구성 · 질문에 개인정보 · 옛 로그 }   있을 때만. 전부에서 센다
검토        { 설명 · 건수 · 막힌_문항{stopped_at: n} · 사례[] }            있을 때만, 맨 뒤
```

축은 결정 트리 그대로 **묶음(고치는 사람) → 들어온 길 → 사례**다. `분류` 가 건수 순인 것은
실무가 처음 보는 것이 "**어디가 제일 많이 터지나**"이기 때문이고, `들어온_길` 은 그 묶음 안에서
어느 이유 문장이 몇 건인지다 — 근거 묶음 30건 중 "근거 어디에도 답이 없었다" 가 25, "청크도
도구 결과도 없었다" 가 5 면 고칠 순서가 정해진다. 이유 문장은 결과 파일의 `because` 그대로라
결과 파일에서 검색이 된다.

## 사례 하나는 두 덩이다

**위는 사용자와 챗봇이 실제로 한 말이고, `분석` 아래는 전부 이 도구가 만든 것이다.** 섞어 두면
읽는 사람이 어느 게 원문이고 어느 게 우리 추정인지 매번 가려야 한다.

```json
"질문": "해외 출장 숙박비 상한은?",
"답변": "규정을 확인해 보시기 바랍니다.",
"사용자_반응": "금액을 물었는데요",
"분석": {
  "사유": "근거 어디에도 질문의 답이 없었다",
  "지나온_단계": [
    "코드 확정: 자원 부족 문구 아니오 · 빈 답변 아니오 · 붕괴 아니오",
    "불만 판정: 후속 발화가 답변을 문제 삼는다 예 · 정책·권한 거절이고 그걸 불평한다 아니오 · …",
    "근거 판정: 이번 턴 검색 청크에 답이 있다 아니오 · 이번 턴 도구 결과에 답이 있다 비어 있어 묻지 않음 · 근거 전체에 답이 있다 없음"
  ],
  "근거_위치": ["이번 턴 검색 청크", "이번 턴 도구 결과", "앞 턴 근거", "메모리"],
  "meta_data": { "대화": "C-0015", "턴": 4, "부서": "해외영업팀", "직급": "책임", "직무": "영업" }
}
```

`사유` 는 결과 파일의 고정 문장이다 — 판정 모델이 쓴 문장이 아니라 코드가 멈춘 자리마다 정해 둔
것이라 같은 결론은 늘 같은 문장이고, 묶어 읽을 수 있다. `지나온_단계` 는 결과 파일의 `steps` 를
한 단계 한 줄로 편 것이다. 문항과 답만 있고 확률은 없다 — 어느 문항이 어느 답으로 이 묶음에
왔는지가 따라가진다.

`근거_위치` 는 근거 판정을 지난 턴에만 있다. 생성 묶음이면 답이 있던 칸, 근거 묶음이면 비었거나
답이 없던 칸이다. `근거_구절` 은 그 칸의 본문(결과 파일 `text`)이고, `--no-text` 로 돌린 결과
파일이면 없다 — 그때 `질문 · 답변 · 사용자_반응` 도 `(본문 없음 — --no-text)` 다.

## 검토는 맨 뒤에 따로

검토는 묶음이 아니라 "kev 가 확신하지 못했다" 는 상태다. 숨기면 실패 건수가 줄어 보이고, 실무가
보면 "이건 왜 실패냐" 가 된다. `막힌_문항` 이 어느 문항에서 몇 건 막혔는지 세고, 그게 문항의
기준문을 고칠 곳이다. 검토 사례의 `사유` 에서는 확률 숫자를 지운다 — "확신이 없다" 까지만.

## 빼기로 한 것

| | 왜 |
|---|---|
| 확률 (`p`) | 실무가 무엇을 할지 정하는 기준이 아니다. 지나온 단계의 답(예 · 아니오 · 모름)으로 충분하다 |
| 정상 턴 | 챗봇 지표가 아니라 **필터 지표**다. 보내면 "이게 왜 실패냐"가 된다. 건수는 `대상` 에 센다 |
| 청크 전문 | 근거 판정을 지난 턴의 `근거_위치` 칸만 `근거_구절` 로 |
| 부서별 집계 | `meta_data.부서` 가 남아 필요하면 다시 센다. 대시보드가 그 축을 맡는다 |
| 내부 용어 | 문항 id(`complains`) 가 아니라 문장이 간다. 결과 파일부터 그렇다 |

`플래그` 는 정상 · 검토를 포함한 **판정된 턴 전부**에서 센다. 사용자가 개인정보를 넣은 것과
답변이 나빴던 것은 독립 사건이고, 앞 턴 누락이 많은 사이클은 사용자 묶음 집계를 보류해야 한다.
`옛 로그` 는 `history_input` 자체가 없어 앞 턴 누락을 판정하지 않은 턴 수다.

## 약한 곳

**`meta_data` 의 `부서` 와 `대화` 는 결과 파일의 `axes.부서` · `chat_id` 다.** 로그가 다른
이름을 쓰면 에러 없이 빈 값이 들어간다. 이 둘은 사례 하나를 티켓에 붙였을 때 원본으로 돌아갈
유일한 길이라 첫 실행에서 눈으로 봐야 한다.

**`지나온_단계` 가 길다.** 불만 판정 한 줄에 문항 여덟이 들어간다. 정확하지만 훑기에는 길고,
결과 파일의 `verdict` 만 보는 것으로 충분한 사람에게는 소음이다.
