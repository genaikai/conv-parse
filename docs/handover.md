# 실무 전달본 — 무엇을 담고 무엇을 빼나

판정 결과 파일은 **되짚는 사람**을 위한 것이다. 사용자 → 대화 → 턴 순이고, 청크 전문과
내부 용어가 들어 있다. 챗봇을 고칠 사람은 다른 것을 묻는다: 무엇이 제일 많이 터지나,
그중 하나를 보여 달라, 왜 그렇게 판정했나.

```bash
python <저장소>/src/handover.py output/<결과.json>     # → <결과>_handover.json
python <저장소>/src/handover.py output/<결과.json> -o 보낼것.json
```

**LLM 을 부르지 않는다.** 결과 파일만 읽어 다시 담으므로, 문구나 담을 항목이 마음에 안
들면 이것만 몇 번이든 다시 돌린다. 판정을 다시 돌리면 호출 수천 번인 데다 그때마다
판정이 조금씩 흔들려 앞서 보낸 것과 숫자가 달라진다. 같은 결과 파일이면 언제나 같은
전달본이 나온다.

로직은 `ragdiag/features/handover/`, 진입점은 `src/handover.py`. 다른 기능과 달리
`FEATURES` 등록부에는 없다 — 파이프라인에 끼지 않고 따로 불린다.

## 모양

```
생성일시
대상       { 로그 · 분석한 턴 · 실패로 판정 · 정상으로 판정 }
제외한_실패  "지연 · 잘림 · … 은 이 로그로 못 본다"                 고정 문장
분류[]     { type · 이름 · 고칠_곳 · 건수 · 세부[] }             묶음(고치는 사람). 건수 많은 순
             세부[] { case · 이름 · 뜻 · 건수 · 태그별 · 태그_뜻 · 사례[] }   라벨. taxonomy 순
                      사례[]
                        앞_질문들 · 질문 · 답변 · 사용자_반응     실제로 오간 말
                        분석 {                                  우리가 본 것
                          사유 { 요약 · 근거[] }
                          문서 { 성격 · 설명 · 구절[] · 어긋난_구절[] · 없던_내용 }   있을 때만
                          판정자가_읽은_것 { 질문 · 원한_것 }
                          meta_data { 대화 · 턴 · 부서 · case · 태그 · 함께_관찰됨 }
                        }
무결성_이벤트 { 설명 · 항목[] { id · 이름 · 뜻 · 건수 · 턴[] } }  있을 때만. 실패 건수 밖
미분류      { 설명 · 건수 · 사례[] }                            있을 때만, 맨 뒤
```

축은 v3 분류 체계 그대로 **묶음 → 라벨 → 태그 → 사례**다. `분류` 가 건수 순인 것은
실무가 처음 보는 것이 "**어디가 제일 많이 터지나**"이기 때문이고, 묶음이 `고칠_곳` 을
달고 있는 것은 묶음 자체가 고치는 사람 단위이기 때문이다. 그 안의 `세부`(라벨)는
taxonomy 순서를 지킨다 — 표에서 본 라벨을 찾을 수 있어야 한다.

라벨 하나 안에서 **무엇을 어겼나는 태그**다. `태그별` 이 그 라벨의 사례들에 붙은 태그를
센다 — G1 이 66건이면 그중 포맷 35 · 어조 28 · 언어 3 이 고칠 순서를 정한다. 등록된
태그는 `태그_뜻` 에 뜻이 붙고, 코드 검증기 이름 같은 태그는 뜻 없이 센다.

`무결성_이벤트` 는 플래그(C1 앞 턴 누락 · C2 memory 어긋남)와 이벤트(U2 질문에
개인정보)의 표다. 챗봇이 틀린 것이 아니라 기록을 믿을 수 없거나 입력 쪽 사건이라
**실패 건수에 넣지 않고** 따로 센다. 정상 턴(N0)에서도 센다. 하나도 없으면 칸이 없다.

`제외한_실패` 는 로그에 정보가 없어 이 방법으로 못 보는 것(지연 · 잘림 · 컨텍스트 초과 ·
구 문서 · 권한 조회)을 머리에 적는다. 목록에서 조용히 지우면 "그건 안 터지나"로 읽힌다.

## 사례 하나는 두 덩이다

경계가 여기에만 있다. **위는 사용자와 챗봇이 실제로 한 말이고, `분석` 아래는 전부
이 도구가 만든 것이다** — 사유도, 고른 문서도, 식별자도. 섞어 두면 읽는 사람이 어느 게
원문이고 어느 게 우리 추정인지 매번 가려야 하고, 접을 수도 없다. 접으면 대화만 남아
훑기 좋고, 펴면 결론 → 근거 → 판정자가 읽은 것 → 식별자 순으로 나온다.

`질문` 과 `앞_질문들` 을 가른 이유: **`질문` 이 그 답변이 실제로 응답한 질문**이다.
전부를 한 배열로 펴면 "마지막 것이 답을 받은 질문"임을 읽는 사람이 알아야 한다.
앞 질문들이 필요한 건 챗봇이 그것들을 함께 받고 답했기 때문이다 — "국내 기준으로만"이
두 턴 앞에 있고 답변이 해외로 답했다면, 마지막 질문만 봐서는 답변이 멀쩡해 보인다.

```json
"질문": "만 몇 세부터 종합검진 대상인가요?",
"답변": "건강검진 관련 사항은 인사팀에 직접 문의해 주시기 바랍니다.",
"사용자_반응": "문의하라는 말 말고 규정에 뭐라고 되어 있는지 알려주세요.",
"분석": {
  "사유": {
    "요약": "문서에 답이 있었는데 답변이 그것을 쓰지 않았다",
    "근거": ["검색된 문서에 그 내용이 있었다 (아래 구절)",
             "답변이 그 내용을 쓰지 않고 다르게 답했다",
             "사용자 반응에서 읽은 근거: 문의하라는 말 말고 …"]
  },
  "문서": {
    "성격": "활용했어야_할_문서",
    "설명": "검색은 됐는데 답변이 쓰지 않은 구절",
    "구절": [{"문서번호": 0, "p": 0.93,
              "구절": "임직원 건강검진은 매년 1회 실시하며, 만 35세 이상은 종합검진 대상으로 한다."}]
  },
  "판정자가_읽은_것": { "질문": "회사 규정상 만 몇 세부터 …", "원한_것": "규정에 명시된 종합검진 대상 연령" },
  "meta_data": { "대화": "C-0015", "턴": 4, "부서": "해외영업팀", "case": "G5", "태그": ["G5:안씀"] }
}
```

## 사유는 어떻게 만들어지나

라벨마다 **문장 틀**이 있고 **태그가 문장을 고른다**. v3 는 "무엇을 어겼나"가 라벨이
아니라 태그에 있어서, 라벨만 보고 쓰면 G5 가 전부 같은 문장이 된다 — `G5:안씀` 은
"문서에 답이 있었는데 쓰지 않았다", `G5:어긋남` 은 "근거 문서와 어긋나는 주장을 했다"다.
판정 모델이 쓴 문장을 그대로 내보내지 않는다 — 그러면 같은 라벨인데 표현이 제각각이라
묶어 읽을 수 없다. `reason_for(label_id, tags, turn)` 이 전부다.

`근거` 를 한 문장이 아니라 **줄 단위 배열**로 둔 것은 판정 경로를 따라갈 수 있게 하기
위해서다. 뭉치면 어디서 갈렸는지 되짚을 수 없다. 줄은 세 갈래에서 온다.

| 출처 | 예 |
|---|---|
| 라벨 · 태그별 고정 문구 | `검색된 문서에 그 내용이 있었다 (아래 구절)` (G5:안씀) · `질문이 여러 가지를 한 번에 물었다` (복합질문) |
| 관측값 | `앞 질문에서 정한 조건: 국내 기준으로만 …` (G2:조건) |
| 그 턴의 플래그 | `기록 주의 — 앞 턴이 기록에 빠져 있어 앞 대화 관련 판정은 하지 않았다` (C1) |
| **코드가 확인한 것** | `코드 확인 — arithmetic: 3,000 + 2,000 = 6,000 (실제 5,000)` |

마지막 것이 **신뢰도 등급을 뺀 대가**다. `high`/`medium` 이라는 라벨보다 "답변에서 이걸
확인했다"가 실무에게 뜻이 분명하다. 판정의 한계(`notes`)도 그대로 붙는다 —
`검색 실패와 코퍼스 부재는 구분 불가 — 부서 편중으로만 추정` 같은 줄이다.

## 문서 — 키는 하나, 뜻은 `성격` 이 말한다

| 라벨 · 태그 | `성격` | `설명` |
|---|---|---|
| G5:안씀 · G5:과거근거 | `활용했어야_할_문서` | 검색은 됐는데 답변이 쓰지 않은 구절 / 이전 턴의 문서에만 답이 있었다 |
| G5:어긋남 · G5:지어낸인용 · G2:모순 · G2:memory | `답변과_어긋나는_문서` | 답변이 이것과 다른 주장을 했다 |
| G3 · G4 | `활용한_문서` | 썼지만 원한 것과 달랐다 / 일부만 답했다 |
| D1 · T1 · T2 · T3 | `문서에_없던_것` | 구절 대신 `없던_내용` (문장). 설명은 라벨마다 — 검색은 됐는데 없던 것과 부르지도 않은 것은 고칠 곳이 다르다 |
| 그 밖 | `판정에_쓰인_문서` | 판정 근거로 쓰인 구절 |

**같은 구절이 태그마다 다른 뜻이다.** 처음엔 키 이름을 case 마다 다르게 뒀는데, 그러면
받아서 파싱하는 쪽이 네 이름을 다 알고 하나씩 있는지 봐야 한다. 키는 `문서` 하나로 두고
분기는 `성격` 값으로 한다.

**청크 풀 전체가 아니라 근거로 선 청크만** 싣는다. v3 는 판정 모델이 구절을 뽑지 않고
청크마다 "질문에 답하나"를 물어 확률을 받는다 — 문턱(0.8) 이상인 청크가 근거이고 그
전문이 `구절` 에 `p` 와 함께 실린다. 실을 수 있는 가장 작은 단위가 청크라서 v2 보다
길지만, 열 개짜리 풀을 통째로 주는 것과는 다르다.

어긋남(G5:어긋남 · G2:모순 · G2:memory)에는 `어긋난_구절` 이 더 붙는다 — 답변과 근거에서
각각 글자 그대로 뽑은 한 쌍이다. LLM 이 쓴 인용이라 코드가 양쪽 원문에서 찾아 **살아남은
것만** 싣는다. 떨어진 것은 판정에도 안 쓰였다.

D1 · T1 · T2 · T3 은 결론이 "쓸 문서가 없었다"라서 구절 칸을 두면 빈 배열만 남는다. 대신
충족도의 `missing`(없으면 관측의 `unmet_need`)을 `없던_내용` 으로 싣는다.

## 빼기로 한 것

| | 왜 |
|---|---|
| 신뢰도 · 증거 등급 · 후보 목록 | 실무가 무엇을 할지 정하는 기준이 아니다. 대신 코드 확인 줄을 싣는다 |
| N0 정상 턴 | 챗봇 지표가 아니라 **필터 지표**다. 보내면 "이게 왜 실패냐"가 된다. 건수는 `대상` 에 센다 |
| 청크 전문 | 위 참고 |
| 부서별 집계 | 한 번 넣었다 뺐다 — 복잡도만 더했다. `meta_data.부서` 가 남아 필요하면 다시 센다 |
| 내부 용어 | `complaint_target` · `verdict` 같은 말은 사유 문장으로 바꿔 나간다 |

**미분류는 숨기지 않는다.** 맨 뒤에 따로 묶고, 어느 쪽인지(`unclassified` / v3 에 자리
없는 옛 case)는 `meta_data.구분` 에 둔다. 숨기면 실패 건수가 줄어 보이고, 나중에
원본과 대조할 때 신뢰를 잃는다.

**옛 결과 파일(case0~30)도 읽는다.** `taxonomy.from_v2` 로 라벨 + 태그로 옮긴다
(case22 → G5 + `G5:안씀`). 제외된 옛 case(5 · 7 · 8 · 19 · 23)와 태그로만 남는 것
(1 · 3 · 4)은 미분류로 간다. 옛 파일에는 청크 확률이 없어 `p` 가 null 이다.

## 약한 곳 셋

**`meta_data` 의 `부서` 와 `대화` 는 필드 이름을 가정한다.** 각각 로그의 `db_dept_name` ·
`conversation_id` 에서 읽는데, 로그가 다른 이름을 쓰면 **에러 없이** 빈 값이나 대체
식별자가 들어간다. 이 둘은 사례 하나를 티켓에 붙였을 때 원본으로 돌아갈 유일한 길이라,
첫 실행에서 눈으로 봐야 한다.

**`무결성_이벤트.뜻` 은 taxonomy 의 설명 그대로라 `history_chat` 같은 필드 이름이 섞여
있다.** 받는 쪽이 로그 · 적재 담당이라 그대로 뒀지만, 사례의 `사유` 와 달리 내부 용어
금지를 지키지 않는 유일한 칸이다.

**`없던_내용` 이 길다.** 판정 모델이 쓴 문장 그대로라 실측 중앙값이 60자를 넘는다.
정확하지만 훑기에는 길다.
