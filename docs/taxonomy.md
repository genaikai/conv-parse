# 실패 묶음 v4 — 결정 트리의 출구 다섯

설계: [design/decision_tree_v4.md](design/decision_tree_v4.md). 표의 원본은
`src/ragdiag/taxonomy.py`(묶음 · 단계 · 이유 문장)와 `src/ragdiag/questions.py`(문항), 묶음이
붙기까지의 경로는 [process_flow.md](process_flow.md). 문서와 코드의 어긋남은
`tests/test_spec_compliance.py` 가 잡는다.

v3 의 라벨 17개 · 태그 · 등급 4단계는 없다. 처음부터 모든 경우를 가르지 않는다 — **큰 묶음을 먼저
잡고** 세부는 데이터를 본 뒤 2단계에서 태그로 더한다.

## 가진 것

턴 하나당 주어지는 증거는 이게 전부다 (conv_eval 포맷, 2026-10 로그 기준).

| 필드 | 내용 |
|---|---|
| `user_question` · `llm_response` | 그 턴의 질문과 답변 |
| `retrieved_data` · `tool_output` · `tool_calls` | 그 질문으로 검색된 청크, 도구 결과, 무엇을 어떻게 불렀나 |
| `history_input` | 서비스가 이 턴을 답할 때 모델에 **실제로 넣은** 것 — 앞 턴 질문 · 답변(`history_chat`), 과거 문서 · 도구 결과, `memory` |
| `memory` | 서비스가 들고 있던 사용자에 대한 정보 |
| `llm_emotion_*` | 다른 시스템의 후속 발화 감정 분류. 필터에만 쓴다 |
| 사용자 메타 | 부서 · 직급 · 직무. 집계 축 |

진단 단위는 연속한 두 턴의 쌍이다. 불만은 turn N+1 의 `user_question` 이고, 판정 대상은 turn N 의
답변과 turn N 이 볼 수 있었던 것 전부다.

여기 없는 것: 서버 응답 시간, `finish_reason`, 문서 개정일, 권한 조회 결과. 지연 · 컨텍스트 초과 ·
구 문서 · 권한 조회 실패는 그래서 묶음에 없다 — "없는 문제" 가 아니라 "이 방법으로 못 보는 문제" 다.

## 묶음 — 고치는 사람이다

| 묶음 | 고치는 사람 | 들어오는 길 |
|---|---|---|
| **정상** | 필터 (챗봇이 아니다) | 후속 발화가 앞 답변을 문제 삼지 않는다 |
| **사용자** | 질문 유도 · UI | 감정 표출뿐이라 단서가 없다 · 앞 질문에 없던 새 요구를 하며 불평한다 |
| **근거** | 검색기 · 도구 연동 · 문서 | 근거 어디에도 답이 없었다 · 청크도 도구 결과도 없었다 · 근거가 일부였고 불만이 가리키는 부분이 없었다 |
| **생성** | 프롬프트 · 모델 | 근거에 답이 있었는데 못 살렸다 · 질문과 다른 언어 · 문서 무관 질문의 오답 · 근거가 일부였지만 불만이 가리키는 부분은 있었다 |
| **시스템** | 인프라 · 서빙 · 권한 정책 | 자원 부족 문구 · 빈 답변 · 붕괴 · 정책 거절에 불만 · 읽을 수 없는 글 · 중간에 끊김 |

**검토**는 묶음이 아니라 상태다. kev 가 어느 문항에서 확신하지 못한 턴이고, 멈춘 문항이 곧 이유다.
실패율 분모에서 빼고 따로 센다. 검토가 많이 막히는 문항이 기준문을 고칠 곳이다.

**들어오는 길이 곧 결과 파일의 `because` 문장이다.** 같은 결론은 늘 같은 문장이라 전달본 ·
대시보드가 그 문장으로 센다.

## 네 단계

```
코드 확정        답변 문자열만. 자원 부족 문구 · 빈 답변 · 붕괴         → 시스템
불만 판정        kev 8문항 1요청. 코드가 순서로 읽는다                   → 정상 · 시스템 · 생성 · 사용자
근거 판정        kev 5문항 1요청. 전체 문항(전부 · 일부 · 없음)이 정한다   → 생성 · 근거 · (일부면 다음)
불만 부분 근거 판정   kev 1문항. 근거가 일부일 때만                  → 생성 · 근거
어디서든 모름                                                            → 검토
```

**모름은 흘리지 않는다.** `p ≥ 0.9` 예, `p ≤ 0.1` 아니오, 사이는 모름이고 그 문항에서 멈춰 검토로
닫는다. 다음 문항으로 넘기면 "어디서 막혔나" 가 한 줄로 안 보인다.

### 불만 판정의 문항 여덟 — 순서대로

| | 문항 | 예 | 아니오 |
|---|---|---|---|
| 1 | 후속 발화가 답변을 문제 삼는다 | 다음 | **정상** |
| 2 | 정책·권한 거절이고 그걸 불평한다 | **시스템** | 다음 |
| 3 | 답변이 읽을 수 없는 글이다 | **시스템** | 다음 |
| 4 | 답변이 중간에 끊겼다 | **시스템** | 다음 |
| 5 | 답변이 질문과 다른 언어다 | **생성** | 다음 |
| 6 | 후속 발화가 감정 표출뿐이다 | **사용자** | 다음 |
| 7 | 앞 질문에 없던 새 요구를 하며 불평한다 | **사용자** | 다음 |
| 8 | 문서·도구 없이 답할 질문이다 | **생성** | 근거 판정으로 |

입력은 history(앞 대화) · 질문 · 답변 · 후속 발화 넷. 문서 · 도구 결과 · memory 는 안 준다.

### 근거 판정의 문항 다섯

| 문항 | 범위 | 역할 |
|---|---|---|
| 이번 턴 검색 청크에 답이 있다 | 그 칸 | 어디에 있었나 |
| 이번 턴 도구 결과에 답이 있다 | 그 칸 | 〃 |
| 앞 턴 근거에 답이 있다 | 그 칸 | 〃 |
| 메모리에 답이 있다 | 그 칸 | 〃 |
| 근거 전체에 답이 있다 | 네 칸 전부 | 있었나 — 전부 · 일부 · 없음 |

칸별은 "일부라도" 기준으로 어디에 있었나를 적을 뿐이고, 묶음은 전체 문항이 정한다. 답변 · 후속
발화는 안 준다. 네 칸이 전부 비면 kev 를 안 부르고 근거(빈 묶음)로 닫는다.

## 플래그 — 트리 밖, 판정에 안 끼어듦

| 플래그 | 뜻 |
|---|---|
| 앞 턴 누락 | 대화에 앞 턴이 있는데 `history_chat` 에 없다. 모델이 못 본 것인지 로그가 떨어뜨린 것인지 못 가른다 |
| history 재구성 턴 수 | `history_chat` 이 비어 턴 순서로 최근 3턴을 되살렸다 |
| 질문에 개인정보 | 사용자가 질문에 개인정보를 넣었다. 답변의 성패와 독립인 사건 |

앞 턴 누락이 많이 서는 사이클은 사용자 묶음 집계를 보류한다.

## 집계 축 — 묶음이 아니다

`answered_by` · `ask_on` · `fallback` · 부서 · 직급 · 직무. 대시보드의 축이고 전달본 `meta_data` 의
식별자다.

## 일부러 가르지 않는 것 (2단계)

근거 묶음 안의 검색 실패 vs 도구 미호출(칸별 답에 이미 있다), 생성 묶음 안의 안 씀 · 어긋남 · 조건 ·
memory · 모순 · 길이 · 포맷, 인젝션 수행 · 개인정보 유출 · 못 내는 형태 요구 · 불명확 질문. 데이터를
돌려 묶음별 건수를 본 뒤 많이 나온 묶음에만 태그를 더한다.
