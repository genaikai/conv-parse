# 실패 분류 체계 v3 — 묶음 라벨 · 태그 · 증거 등급

이 로그로 **실제로 판정할 수 있는 것**만으로 짠 분류다. 설계와 이유는
[design/taxonomy_v3.md](design/taxonomy_v3.md), 표의 원본은 `src/ragdiag/taxonomy.py`, 라벨이
붙기까지의 경로는 [process_flow.md](process_flow.md). 이 문서는 라벨 표와 원칙만 짧게 둔다.
문서와 코드의 어긋남은 `tests/test_spec_compliance.py` 가 잡는다.

## 가진 것

턴 하나당 주어지는 증거는 이게 전부다 (conv_eval 포맷, 2026-10 로그 기준).

| 필드 | 내용 |
|---|---|
| `user_question` · `llm_response` | 그 턴의 질문과 답변 |
| `retrieved_data` · `tool_output` · `tool_calls` | 그 질문으로 검색된 청크, 도구 결과, 무엇을 어떻게 불렀나 |
| `history_input` | 서비스가 이 턴을 답할 때 모델에 **실제로 넣은** 것 — 앞 턴 질문 · 답변(`history_chat`), 과거 문서 · 도구 결과, `memory` |
| `memory` | 서비스가 들고 있던 사용자에 대한 정보 |
| `llm_eval_*` · `llm_emotion_*` | 다른 시스템의 후속 질문 성격 · 감정 분류. 필터에만 쓴다 |
| 사용자 메타 | 부서 · 직급 · 직무. 집계 축 |

진단 단위는 연속한 두 턴의 쌍이다. 불만은 turn N+1 의 `user_question` 이고, 판정 대상은 turn N 의
답변과 turn N 이 볼 수 있었던 것 전부다.

여기 없는 것: 서버 응답 시간, `finish_reason`, 문서 개정일, 권한 조회 결과, 세션. **이 목록이 판정
가능 범위를 결정한다.** 지연 · 잘림 · 컨텍스트 초과 · 구 문서 · 권한 조회 실패 · 세션/인증은 그래서
라벨에 없다 — "없는 문제" 가 아니라 "이 방법으로 못 보는 문제" 다.

## 설계 원칙

**1. 조치 주체로 묶는다.** 증상이 아니라 "누가 고치는가"로 묶음을 나눈다. D1 과 G5 는 사용자에게
같은 증상("답이 부실하다")이지만 하나는 문서팀, 하나는 프롬프트 담당이 고친다. 증상으로 묶으면
집계가 아무도 지목하지 못한다.

**2. 못 가르면 합친다.** 검색 결과만으로는 "코퍼스에 문서가 없다"와 "검색기가 못 찾았다"를 가를 수
없다. 그래서 D1 은 하나의 라벨이다. 검색 도구 이름 목록이 없으면 D1 과 T2 도 가르지 않고
`D:출처미상` 태그로 합친다. 구분 못 하는 걸 구분한 척하는 라벨이 제일 나쁘다.

**3. 태그로 내린다.** 같은 묶음 안의 "무엇을 어겼나"(언어 · 길이 · 포맷 · 어조, 조건 · memory · 모순,
안씀 · 어긋남 · 지어낸인용)는 라벨이 아니라 태그다. v2 는 라벨 30개 중 실제로 나온 것이 9개였다 —
라벨이 많으면 셀이 비어 표가 안 읽힌다. 태그는 주 라벨이 무엇이든 전부 붙고 집계 셀을 만들지 않는다.

**4. 플래그 · 이벤트는 분모 밖.** 기록을 믿을 수 없는 턴(C1 · C2)과 챗봇 실패가 아닌 사건(U2)은
실패율 분모에 넣지 않는다. 플래그는 그 턴에서 G2 만 막고, 이벤트는 아무것도 막지 않는다 — 답변은
끝까지 따로 판정한다.

**5. 등급이 신뢰도다.** 신뢰도는 라벨의 고정값이 아니라 **그 후보를 떠받치는 증거의 등급**이다.
코드 확정(4) · 근거 확정(3) · 확신 p ≥ 0.9 (2) · 기울어짐 p ≥ 0.6 (1). 같은 D1 이라도 2차 검증을
지난 것과 아닌 것은 등급이 다르고, 등급 1 · 0 은 표본 검토 대상이라 같은 무게로 집계하지 않는다.

## 라벨

표기는 `묶음글자 + 번호` 다. 묶음 글자는 영어 머리글자이고 문서에서는 `G(generation)` 처럼 괄호로
뜻을 붙인다. 목록은 묶음(N U C T D G S I) → 번호 순이다.

### 실패 라벨 — 실패율 분모에 들어간다

| 묶음 | 라벨 | 뜻 | 근거 | 고칠 곳 |
|---|---|---|---|---|
| **N(none)** 실패 아님 | `N0` 정상 후속 | 후속 발화가 앞 답변을 문제 삼지 않는다 | 관측 불만 종류 = none | 필터 (챗봇 아님) |
| **U(user)** 입력 | `U1` 낼 수 없는 형태 요구 | 링크 · 이미지 · 파일 등 서비스가 낼 수 없는 것을 요구 | 관측 | 질문 유도 · UI |
| **T(tool)** 도구 호출 | `T1` 호출 없음 | 업무 질문인데 `tool_calls` 와 이번 턴 청크가 모두 빔 | 코드 + 관측 | 오케스트레이션 · 도구 연동 |
| | `T2` 결과가 질문과 무관 | 업무 도구만 불렀고 그 결과가 질문에 답하지 못함 | 충족도 (출처 = 업무 도구) | 오케스트레이션 · 도구 연동 |
| | `T3` 빈 결과에 단정 | 도구 결과가 비었는데 답변이 수치 · 식별자를 단정 | 코드 | 오케스트레이션 · 도구 연동 |
| **D(document)** 검색 근거 | `D1` 검색 근거에 답 없음 | 검색이 가져온 청크 어디에도 요구에 답하는 것이 없음 | 충족도 + 2차 검증 | 검색기 · 문서 |
| **G(generation)** 생성 | `G1` 명시 요구 불이행 | 언어 · 길이 · 포맷 · 어조 요구를 어김 | 코드 검증기 + 요구 확인 | 생성 프롬프트 · 모델 |
| | `G2` 맥락 불이행 | 앞 질문의 조건 · memory 의 사용자 정보를 어김 · 앞 답변과 모순 | 관측 + memory · 일관성 + 원문 대조 | 생성 프롬프트 · 모델 |
| | `G3` 의도와 다른 답 | 물은 것과 다른 것을 답함. 다른 라벨에 안 걸린 불만의 **잔여** — 등급 1 뿐 | 관측 | 생성 프롬프트 · 모델 |
| | `G4` 복합 일부만 답 | 복합 질문의 일부만 답함 | 관측 | 생성 프롬프트 · 모델 |
| | `G5` 근거 활용 실패 | 근거가 있는데 안 씀 · 어긋남 · 지어낸 인용 | 주장 판정 + 코드 | 생성 프롬프트 · 모델 |
| | `G6` 일반 지식 · 계산 · 코드 오류 | 문서 무관 질문의 오답 — 코드가 확인한 것은 4, 아니면 1 | 코드 검증기 | 생성 프롬프트 · 모델 |
| **S(safety)** 정책 · 보안 | `S1` 정책 거절 | 정책 · 권한을 이유로 거절했고 사용자가 불만 | 관측 | 권한 정책 · 입력 방어 · 출력 필터 |
| | `S2` 인젝션 수행 | 문서에 심긴 지시를 답변이 수행 | 코드 | 권한 정책 · 입력 방어 · 출력 필터 |
| | `S3` 답변 정보 유출 | 질문에 없던 개인정보 패턴이 답변에 있음 | 코드 | 권한 정책 · 입력 방어 · 출력 필터 |
| **I(infra)** 서빙 | `I1` 자원 부족 문구 | 서비스 확정 문구 | 코드 | 인프라 · 모델 서빙 |
| | `I2` 붕괴 · 읽을 수 없음 | 반복 · 토큰 잡탕 · 내부 유출 | 코드 + 읽기 판정 | 인프라 · 모델 서빙 |

잔여: `unclassified` (등급 0 — 어느 후보도 확신이 없음). "문제 없음" 이 아니라 수동 검토 대상이다.

### 무결성 플래그 — 분모 밖. 그 턴의 기록을 믿을 수 없다

| 플래그 | 뜻 | 근거 | 효과 |
|---|---|---|---|
| `C1` 앞 턴 누락 | 대화에 앞 턴이 있는데 `history_chat` 에 없다 | 턴 번호 ↔ `history_chat` 의 user 수 | **G2 전체**를 후보에서 뺀다 |
| `C2` memory 어긋남 | memory 가 있는데 그 내용어가 대화 어디에도 없다 | memory ↔ 대화 어휘 겹침 | **G2[memory]** 만 뺀다 |

빠진 것이 모델이 못 본 것인지 로그/적재가 떨어뜨린 것인지는 로그만으로 못 가른다. 그래서 라벨이
아니라 플래그다. 받는 쪽은 로그 · 적재 · 맥락 관리다. C1 이 많이 나오면 그 사이클의 G2 집계를 보류한다.

### 이벤트 — 분모 밖 카운트

| 이벤트 | 뜻 | 근거 |
|---|---|---|
| `U2` 질문에 개인정보 | 사용자가 질문에 개인정보를 넣었다 | pii 패턴 (질문) |

사용자가 개인정보를 넣은 것과 답변이 나빴던 것은 독립 사건이다. 받는 쪽은 입력 마스킹(UI).

### 태그 — 주 라벨에 딸린다

| 태그 | 붙는 조건 |
|---|---|
| `U3` | 질문 명확성이 clear 가 아니다 |
| `되묻기없음` | U3 인데 답변이 되묻지 않았다 (G3 와 짝) |
| `G1:언어` `G1:길이` `G1:포맷` `G1:어조` | 어느 요구를 어겼나 |
| `G2:조건` `G2:memory` `G2:모순` | 어느 맥락을 어겼나 (`G2:약속` 은 등록만) |
| `G5:안씀` `G5:어긋남` `G5:지어낸인용` `G5:과거근거` | 근거를 어떻게 잘못 썼나. 과거근거 = 답이 `history_input` 의 문서에만 있었다 |
| `G6:계산` `G6:코드` `G6:일반` | 무엇이 틀렸나 |
| `T:인자불일치` | 질문의 식별자가 도구 인자에 없다 (`T:순서` 는 등록만) |
| `D:출처미상` | 검색 도구 이름 목록이 없어 D1/T2 를 못 가름 |
| `복합질문` | 질문이 복합이다 (G4 가 아니어도) |
| `미검증주장` | 일반 지식 주장이 있어 대조하지 못함 |
| `2차불일치` | 충족도 2차 검증이 1차와 어긋났다 |
| 코드 검증기 이름 | 위반한 검증기 전부 (`pii` `language` `format` …) |

### 집계 축 — 라벨이 아니다

질문 유형(`question_domain`) · `answered_by` · `ask_on` · `fallback` · 부서 · 직급 · 반복 불만 횟수.
대시보드의 축이고 전달본의 분할 기준이다.

## 판정 순서

묻는 것은 넷이다. ⑴ 만 턴을 멈추고, ⑵ ⑶ 은 v2 의 if-체인과 달리 **전부 돌고 후보를 전부 낸 뒤**
⑷ 에서 등급으로 고른다. 그림은 [process_flow.md](process_flow.md) 와 README 의 것과 같다.

```
                    ┌──────────────────────────────────────────────────────────────┐
  Case ───────────▶ │ ⑴ 판정할 답이 있기는 한가?                          코드      │
                    │    자원 부족 문구 · 글자 반복 · 템플릿 토큰 · 인젝션 수행 · 유출 │
                    └──────────────────────────────────────────────────────────────┘
                         │ 없다 ──▶ I1 · I2 · S2 · S3  (등급 4, 모델 호출 0)  ──▶ 끝
                         │ 있다
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑵ 사용자가 무엇을 불평했나?                         kev + LLM │
                    │    불만 종류 · 질문 종류 · 거절했나 · 복합질문 · 앞 조건 무시   │
                    │    + 요구(언어 · 길이 · 표) · 못 내는 형태(그림 · 링크)       │
                    └──────────────────────────────────────────────────────────────┘
                         │ 불만 없음 ───▶ N0            거절에 불만 ───▶ S1
                         │ 요구 어김 ───▶ G1 (코드 확인)  못 내는 형태 ─▶ U1 (⑶ 을 덮는다)
                         │ 내용 불만
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑶ 근거가 있었나? 모델이 그걸 썼나?                  kev + 코드 │
                    │    청크마다 "요구에 답하나"  ·  답변 주장마다 "근거와 맞나"      │
                    │    + 맥락: 앞 질문의 조건 · memory · 앞 답변과 모순            │
                    └──────────────────────────────────────────────────────────────┘
                         │
                         │              모델이 근거대로 말함      근거와 다르게 말함
                         │   근거 있음   G3 · G4(일부만)          G5
                         │   근거 없음   D1 검색 실패 · T1 도구 안 부름 · T2 엉뚱한 도구
                         │   맥락 어김   G2 (조건 · memory · 모순)
                         │   문서 아님   G6 (계산 · 코드 · 상식)
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑷ 제일 확실한 증거의 라벨을 집는다                   코드      │
                    │    등급  4 코드 확정 › 3 근거 대조 › 2 kev 확신 › 1 기울어짐   │
                    │    동급이면 라벨 순서. 후보 없음 → unclassified                │
                    │    나머지 후보는 태그로. 플래그(C1 · C2) · 이벤트(U2) 는 곁에   │
                    └──────────────────────────────────────────────────────────────┘
                         │
                         ▼  주 라벨 · 등급 · 태그 · 플래그 · 이벤트
```

라벨 묶음과 질문의 대응: **I · S2 · S3** 는 ⑴, **N0 · S1 · U1 · G1** 은 ⑵, **T · D · G2~G6** 은 ⑶ 의
표에서 나온다. 무결성 플래그 **C1 · C2** 와 이벤트 **U2** 는 ⑴ 앞에서 코드가 적는 장부라 어느 질문의
답도 아니고 ⑷ 의 후보도 아니다 — C1 · C2 는 ⑶ 의 맥락 칸(G2)을 잠글 뿐이다.

**⑷ 주 라벨 = 등급 최대, 같으면 라벨 순서의 앞.** 순서는 `I1 I2 S2 S3 N0 S1 U1 T1 T3 D1 T2 G1 G5 G6 G4 G2 G3`
(`taxonomy.ORDER`) 다. N0 가 S1 보다 앞인 이유: 불만 없는 거절은 정당한 거절이다. S2 · S3 가 N0 보다
앞인 이유: 불만과 무관한 사건이다. G3 가 맨 뒤인 이유: 잔여 라벨이라 구조적으로 아무것도 삼키지
못하게. 나머지 후보는 태그와 `secondary_cases` 로 남는다.

### v2 → v3 대응

옛 결과 파일을 읽을 때만 쓴다 (`taxonomy.from_v2`).

```
case0→N0  case1·4→(U3 태그)  case2→U1  case3→(복합질문 태그)  case6→U2
case9→I1  case30→I2  case10·11·12·16→G1  case13·17→G3  case14→G2  case15→G4
case18·22·24→G5  case20→D1  case21→T1  case25·26·27→G6  case28→S1  case29→S2
case5·7·8·19·23→(제외)
```

새로 생긴 라벨은 C1 · C2 · T2 · T3 · S3 — `history_input` · `tool_calls` 가 있는 2026-10 로그에서
처음 보이는 실패다.
