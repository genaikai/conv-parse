# ④ 불만 판정 입력 축약 — kev 500 · 422 폴백

**누가 읽나.** 이 코드를 실행 환경에서 돌리는 사람. 코드를 고칠 수 없다는 전제라, 여기 적힌 것은
전부 설정과 운영 절차다. 구현해야 하는 코드는 없다.

## 무슨 일이 생기나

kev 의 state 한도는 65,536 토큰이다 (문항은 행마다 따로 8,192 가 더 있어 문항 수는 무관하다). ④ 불만
판정은 한 요청에 `history` · `question` · `answer` · `followup` 넷을 보내는데, 앞 대화가 길거나 답변 ·
질문에 긴 자료가 붙은 턴은 두 가지로 실패한다. 한도 **안인데** GPU 메모리가 바닥나면 HTTP **500**(OOM),
한도를 **넘으면** kev 가 토큰 수를 적어 **422** 로 거절한다. 앞단에 프록시가 있으면 본문 크기 제한으로
**413** 이 올 수도 있다. 그 턴들은 지금까지 에러로 끝났다.

이제는 이렇게 간다.

1. 원문을 그대로 보낸다. 평소 경로는 아무것도 달라지지 않는다.
2. kev 가 **500 · 422 · 413** 을 내면 칸별 상한으로 입력을 줄인다 (아래 표). 상한을 넘은 칸만 건드린다.
3. 줄인 입력으로 **한 번만** 다시 묻는다.
4. 그 턴의 플래그 `입력 축약` 에 어느 칸을 어떤 방법으로 몇 자에서 몇 자로 줄였는지 남는다.

다음은 축약하지 않고 에러를 그대로 올린다.

- 그 밖의 코드 (400 · 502 · 503 · 504 …). 크기 문제가 아니다 — 서버 상태거나 요청 모양 오류다.
- 어느 칸도 상한을 넘지 않은 500 · 422 · 413. 역시 크기 문제가 아니다 — kev 쪽을 볼 것. (문항 모양
  오류의 422 는 여기서 걸러진다.)
- ⑤ 근거 판정 · ⑥ 불만 부분 근거 판정의 500. 근거 칸의 축약 규칙은 따로 설계해야 해서 아직 없다.
- 줄인 뒤의 두 번째 실패. 메시지에 `입력을 축약한 뒤에도 실패 (answer elide 31,200→6,000자 · …)` 가 붙는다.

## 칸별 상한과 방법

| 칸 | 상한(토큰) | 방법 | LLM | 왜 이 방법인가 |
|---|---|---|---|---|
| `answer` | 5000 | 머리 70% + `…(중략 N자)…` + 꼬리 30% | 안 쓴다 | 거절 · "문서에 없습니다" 는 머리에, 끊김은 꼬리에 있다. 언어 · 형식은 표본이면 보인다. LLM 요약은 이 신호를 전부 지운다 |
| `followup` | 3000 | 머리 50% + 꼬리 50% | 안 쓴다 | 모든 문항의 출발점. 바꾸면 판정 자체가 바뀐다. 사실상 안 걸리는 안전장치다 |
| `history` | 1200 | ① assistant 발화를 앞 80자 + `…(답변 생략 · N자)` 로 접는다 ② 그래도 넘치면 마지막 user 둘은 원문, 그 앞 user 발화를 LLM 이 "무엇을 요구했고 무엇이 틀렸다 했나" 로 요약 ③ LLM 이 없거나 요약이 미심쩍으면 앞에서부터 버린다 | ② 만 | 6번 문항은 user 발화만 단서로 본다. 요약 각 줄이 원문과 낱말을 하나도 안 나누면 지어낸 것으로 보고 버린다 |
| `question` | 1200 | LLM 이 지시문(원문 발췌)과 붙여 넣은 자료의 요약으로 분리. 발췌가 아니면 머리 · 꼬리 | 쓴다 | 긴 질문은 거의 "짧은 요구 + 붙여 넣은 자료" 다. 3 · 6 · 7 문항이 읽는 것은 요구 쪽이다 |

상한은 토큰 **추정**이다: `글자 수 / abbrev.chars_per_token`. 실제 토크나이저를 쓰지 않는다.

## 설정 — 실행 환경에서 적는 것

운영 설정 파일(`AA/configs/env.yaml`, `--config` 로 가리키는 것) 하나에 다 적는다.

```yaml
kev:
  url: [http://host:8008, http://host:8009, http://host:8010, http://host:8011]

llm:                              # history · question 요약에 쓴다. 2차 판정과 같은 백엔드다
  url: http://host:8000           # OpenAI 호환 (vLLM 등). 비우면 요약 없이 자르기만으로 돈다
  key: any
  model: null                     # 비우면 서버의 첫 모델
  # 다른 프로젝트가 vLLM 설정을 들고 있으면 그 파일을 가리켜도 된다 — 비어 있을 때만 끌어온다
  # env_file: ../serving/configs/env.yaml
  # env_file_section: vllm

abbrev:
  enabled: true                   # false 면 500 · 422 가 예전처럼 그대로 올라온다
  history_tokens: 1200
  question_tokens: 1200
  answer_tokens: 5000
  followup_tokens: 3000
  chars_per_token: 1.2
```

환경변수로도 된다: `ABBREV_ENABLED` · `ABBREV_HISTORY_TOKENS` · `ABBREV_QUESTION_TOKENS` ·
`ABBREV_ANSWER_TOKENS` · `ABBREV_FOLLOWUP_TOKENS` · `ABBREV_CHARS_PER_TOKEN`. 우선순위는 다른 키와
같다 — CLI(`--set abbrev.answer_tokens=4000`) > 설정 파일 > 환경변수 > 기본값.

**`llm.url` 이 없으면** (kev 만 있는 배포) 요약 단계가 빠지고 history 는 앞에서부터 버리고 question 은
머리 · 꼬리만 남긴다. 멈추지는 않는다. 2차 판정도 같은 이유로 꺼져 있을 것이다.

### chars_per_token 맞추기

1.2 는 한국어를 보수적으로 잡은 값이다 — 실제보다 토큰을 많이 세서 조금 일찍 자른다. kev 토크나이저로
한 번 재면 맞출 수 있다.

```python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("jaredpalmer/kev-4b")     # 실제 서빙 모델 이름으로
text = open("sample_answer.txt", encoding="utf-8").read()    # 사내 로그의 긴 답변 몇 개를 이어 붙인 것
print(len(text) / len(tok.encode(text)))                      # 이 값을 chars_per_token 에
```

값이 커지면(예: 1.6) 같은 상한에 더 많은 글자가 들어간다. 422 가 **줄인 뒤에도** 나면 이 값이 너무 큰
것이니 낮춘다 (422 본문의 토큰 수와 우리 글자 수를 나누면 바로 나온다). 상한 네 개의 합(10,400 토큰)은 문항 아홉을 더해도 65k 의 1/5 이라 여유가 크다 —
두 번째 500 은 추정이 틀린 게 아니라 kev 서버 쪽 문제일 가능성이 더 높다.

## 결과에서 보는 법

- 결과 파일 `turns[].flags["입력 축약"]` — 비어 있지 않으면 그 턴은 줄인 입력으로 판정됐다.
  ```json
  "입력 축약": [{"field": "answer", "method": "elide", "before": 31200, "after": 6000},
                {"field": "history", "method": "fold", "before": 9800, "after": 1300}]
  ```
  `method` 는 `elide`(머리 · 꼬리) · `fold`(assistant 접기) · `summarize`(LLM 요약) · `split`(지시문 분리) ·
  `drop`(앞에서 버림). `before` · `after` 는 글자 수다.
- 실행 요약의 `kev calls` 는 500 · 422 를 받은 요청도 센다 (턴당 최대 4 가 된다). `llm calls` 에 요약 호출이 더해진다.
- 전달본(`handover.py`) 의 `플래그.입력 축약` 이 건수, `주의` 에 설명 한 줄. 대시보드 사례 표에 `축약` 열.
- **축약된 턴의 묶음 분포가 나머지와 다르면** 축약이 판정을 흔드는 것이다. 특히 `summarize` 가 많은데
  사용자 묶음이 늘면 6번이 요약에 속은 것이니 `history_tokens` 를 올리거나 `llm.url` 을 비워 요약을 끈다.

## 캐시

판정 캐시(`paths.cache`) 는 **원문** state 를 키로 쓴다. 한 번 500 · 422 를 맞고 줄여서 답을 받은 턴은
재실행에서 캐시로 바로 나오고 다시 맞지 않는다. 플래그도 캐시에 함께 있어 재실행에도 남는다.
요약 LLM 호출도 같은 캐시에 있다 (`o-abbrev-history-*` · `o-abbrev-question-*`).

## 바뀌지 않은 것

- ⑤ · ⑥ 의 입력, 문항 아홉, 임계, 묶음. 축약은 입력만 건드린다.
- 500 이 안 나는 턴. 원문 그대로다.

## 왜 실패 뒤에 하나 — 미리 줄이지 않는 이유

미리 상한을 적용하면 긴 턴 전부가 줄인 입력으로 판정된다. kev-27B 는 65k 까지 정확도가 유지되고 500 · 422
는 드물며 축약은 어떤 방법이든 정보를 버리므로, 필요한 턴에만 쓴다. 대가는 500 을 한 번 맞는 비용과, OOM 이 kev 프로세스를 잠시 넘어뜨릴
수 있다는 점이다. 서버가 여럿이면 재시도가 자연히 다음 대로 가고, 한 대면 재시도가 연결 오류를 맞을 수
있다 — 그 턴은 에러로 남고 다음 실행에서 캐시 덕에 그 턴만 다시 묻는다.
