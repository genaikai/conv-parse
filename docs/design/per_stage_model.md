# 단계별 모델 — 어느 단계가 작은 모델을 받을 수 있나

**아직 안 쟀다.** 이 문서가 담은 것은 측정값이 아니라 **구조적 제약**이다 — 어느 단계는
원리적으로 작은 모델로 못 내린다는 것, 그리고 그 판단의 근거가 코드 어디에 있는지.
수치는 `## 재는 방법` 을 돌린 뒤에 여기 채운다.

## 묻는 것

판정만 빠르게 내는 작은 모델(출력이 닫힌 집합 한 칸)을 3스텝 어딘가에 끼워
속도나 정확도를 얻을 수 있는가.

## 가르는 기준은 "출력이 실제로 소비되는가"

프롬프트가 무엇을 묻는지가 아니라, **그 단계의 출력 중 코드가 실제로 읽는 칸이
무엇인지**가 기준이다. 자유서술과 글자 그대로의 인용이 뒤 단계의 입력이면 작은
모델로 못 내린다 — 거부권 구조가 거기에 걸려 있다.

| 단계 | 스키마 필드 | 코드가 읽는 것 | 내릴 수 있나 |
|---|---|---|---|
| ④′ 읽기 | `reasoning` · `quote` · `legible` | **셋 다** | 조건부 |
| ⑤ 관측 | 19개 | 타입 12개 + 자유서술 3개가 **⑦ 의 입력** | 아니다 |
| ⑦ 충족도 | `reasoning` · `evidence[]` · `verdict` · `missing` | `evidence` 는 청크와 대조, `missing` 은 대시보드 | 아니다 |
| **⑨ 근거 활용** | `reasoning` · `answer_used_rag` | **`answer_used_rag` 뿐** | 그렇다 |

근거는 코드다. `GroundingCheck` 는 필드가 둘인데 `reasoning` 을 읽는 곳이 **없다** —
`output.py` 가 `answer_used_rag` 만 싣고, `features/route/table.py` 가 그걸 읽는 것이
전부다. 즉 ⑨ 는 이미 **3지 분류 한 칸**짜리 단계다.

④′ 가 조건부인 이유는 `quote` 다. 코드 관문 셋(인용 대조 · 코드 블록 · 구절 깨짐
확인)이 그 구절을 입력으로 받는다 — 지어낸 구절은 걸러지므로 **오탐 쪽은 코드가
막아 준다.** 반대 방향(미탐)은 아무도 못 막는다. 27B 실측이 오탐 0/50 · 미탐 3/22
였으니, 약한 모델이 나빠지는 쪽이 하필 코드가 못 막는 쪽이다.

## 속도 이득은 생각보다 작다

비용이 어디 있는지와 작은 모델이 갈 수 있는 자리가 어긋난다.

```
④′  입력 작다 (답변만)        출력 짧다
⑤   입력 중간 (문서 없음)     출력 길다 ← 디코드 비용이 여기 몰린다
⑦   입력 크다 (청크 전부)     출력 중간
⑨   입력 크다 (답변+청크)     출력 짧다
```

배치 작업의 GPU 초를 먹는 것은 디코드이고, 디코드는 ⑤ 에 몰려 있다. 그리고 ⑤ 가
작은 모델이 못 가는 자리다. ⑨ 를 내리면 **프리필만** 줄고, ⑨ 는 `verdict ==
sufficient` 일 때만 돈다.

그래서 ⑨ 를 내리는 값은 속도가 아니라 **출력이 한 칸이라는 성질**에 있다. 같은
입력을 N번 돌려 다수결하면 3-2 와 5-0 이 갈리고, 그게 지금 taxonomy 에 손으로 박아
둔 `confidence` 를 측정값으로 바꾼다. 출력이 긴 ⑤ · ⑦ 에서 같은 것을 하면 N배다.

## 한 가지 긴장

세 스키마 모두 **`reasoning` 이 첫 필드**고 `verdict` · `legible` 이 뒤다. 일부러다 —
출력 안에서 먼저 추론하고 나중에 단정하게 만든 것이고, `LEGIBILITY_SYSTEM` 의 "확신이
없으면 legible=true" 같은 지시가 그 추론에 기대고 있다. 판정만 내는 모델은 그 발판을
치운다. 그러니 "3지선다쯤은 작은 모델도 하겠지" 를 **가정하면 안 된다.**

전례가 있다. 벤치마크 14/14 에서 이긴 모델이 우리 관측 골든셋에서는 94% 대 97%
였다 — 벤치마크 우위가 넘어오지 않았다.

## 넣은 것

단계마다 `model` · `url` · `key` 를 따로 줄 수 있다 (`llm.<것>_<단계>` ·
`--model-<단계>` · `--base-url-<단계>` · `--api-key-<단계>`). 적은 단계만 그쪽으로
가고 나머지는 기본 백엔드로 간다. 안 준 것은 물려받는다 —
`OpenAICompatBackend.variant`.

주소까지 받는 이유는 **모델이 서버마다 따로 떠 있는 경우**가 있어서다. 처음에는 한
서버에 모델 둘을 전제했는데 그게 아니었다. 주소만 주고 모델을 비우면 그 서버의
`/v1/models` 에서 찾는다.

`json_mode` · `thinking` · `max_tokens` · `timeout` 은 **언제나 공통**이다. 그게
단계마다 달라지면 같은 조건에서 모델을 비교하는 게 아니게 된다.

주소를 줬는데 모델 이름도 줬으면 설정 때 `/v1/models` 를 한 번 물어본다. 모델 이름을
주면 생성자가 서버에 아무것도 묻지 않아서, 주소 오타가 판정 중에야 드러난다 — 턴마다
⑤ ⑦ 를 다 사고 나서 그 단계만 전부 실패하는 모양이고, 사이클 하나를 버린다.

캐시는 손대지 않았다. 키가 이미 `(단계, 모델, system, user)` 였다 — 한 단계의 모델만
바꾸면 **그 단계의 캐시만** 무효화되고 나머지는 다시 사지 않는다.

같이 고쳐야 했던 것 둘. 결과 파일에 `judged_by` 를 넣었고(단계 → 모델),
폴백 집계가 백엔드 전부를 보게 했다. 모델이 갈리는 순간 "그 실행은 그 모델" 이
깨지는데, 결과를 가지고 나올 수 없는 환경에서 판정의 출처가 파일에 없으면 나중에
해석할 방법이 아예 없다.

**자동 승격(표가 갈리면 큰 모델로)은 넣지 않았다.** 측정 전에 정책을 박으면 그
정책이 측정을 오염시킨다. 지금은 손으로 두 번 돌려 비교한다.

## 재는 방법

골든셋 측정에는 단계별 플래그를 쓰지 않는다. **한 번에 한 모델**이 맞고, 그쪽은
`--model` 로 통째로 바꾼다. 섞어 돌리는 것은 실제 실행 경로뿐이다.

```
1. 기준선        --golden --golden-set {observations,messy,legibility} · 큰 모델
                 지금 수치는 전부 다른 모델에서 잰 것이라 기준선이 없다
2. ⑨ 만 비교     같은 골든셋 항목에 큰 모델 1회 / 큰 모델 N회 / 작은 모델 N회
                 작은 모델 N회가 큰 모델 1회를 따라잡는지가 분기점
3. 따라잡으면    --model-grounding 으로 실제 실행. judged_by 로 출처가 남는다
   못 따라잡으면 ⑨ 에 큰 모델 N회만 넣어 confidence 를 측정값으로 바꾼다
```

둘 다 이득이고, 2번이 어느 쪽인지 알려 준다.
