# ④′ 읽기 — 답변만 보고 "읽을 수 있는 글인가"

2026-09-21. 잘림(case8) 검증기를 뺀 자리에서 나온 논의의 결과다.

## 왜

실데이터에 모델이 답을 만들다 무너진 턴이 있었다 — `5555555555`, `!!!!!!!!!`. 관측(Step 1)에
그대로 넣으면 판정자가 무응답이나 거절로 읽어 엉뚱한 case 로 보내고 호출 세 번이 날아간다.

두 겹으로 잡는다.

| 층 | 무엇으로 | 잡는 것 | 신뢰도 | 호출 |
|---|---|---|---|---|
| ④ `short_circuit/degenerate` | 코드 | 글자 2종 이하 · 짧은 조각의 되풀이 · 글자 없음 · 끝의 긴 반복 | high | 0 |
| ④′ `features/legibility` | LLM (답변만) | 토큰 잡탕 · 중간부터 깨짐 · 문단이 조금씩 바뀌며 되풀이 · 프롬프트/내부 유출 | medium | 1 |

규칙은 **오탐이 0 인 것이 확실한 모양**에서 멈춘다. 잘림 검증기가 밟은 길 — 예외를 쌓을수록
정상 답변(표 · 코드 · 영문)이 걸리기 시작한다 — 을 되풀이하지 않기 위해서다. 커버리지는
LLM 층이 책임진다.

## 설계

- 입력은 **답변 하나.** 질문 · 불만 · 문서를 주면 "질문에 맞는 답인가" 를 재기 시작하고,
  그러면 부실한 답변까지 붕괴로 세어 case20 · 22 가 사라진다.
- 묻는 것도 하나. 사람이 읽고 뜻을 잡을 수 있는가. 유용한지 · 맞는지는 묻지 않는다.
- 오탐 방어는 인용. `legible=false` 면 깨진 구절을 원문에서 따오게 하고 코드가 대조한다
  (`verify_complaint_quote`). 못 대면 판정 무효, ⑤로 흘려보낸다. ⑧ 인용 대조와 같은 원리.
- "확신이 없으면 legible" 을 프롬프트에 못 박았다. 이 판정이 틀리면 그 턴의 진짜 원인은
  아무 단계에서도 판정받지 못한다.
- 설정 `run.legibility: false` 로 끈다.

## 측정 — Haiku 4.5 · 생각 끔 · 캐시 없음

골든셋 `fixtures/judgments.LEGIBILITY` 60건: 붕괴 20 (토큰 잡탕 5 · 중간부터 깨짐 4 · 문단
되풀이 3 · 프롬프트 유출 3 · 내부 오류 노출 2 · 무의미한 문장 3) + 정상 40 (표 5 · 코드 5 ·
JSON 3 · 영문 4 · 한 줄 5 · 이모지 3 · 번호 목록 4 · 긴 정상 3 · 거절 3 · 약어 3 · 숫자 2).
정상을 두 배로 둔 것은 재는 것이 오탐이라서다. 붕괴 쪽은 코드 규칙이 못 잡는 모양만
담았다 (테스트가 확인한다).

| 프롬프트 | 회 | 오탐 (정상→붕괴, 인용 통과) | 무효 오탐 | 잡음 | 놓침 | 오류 |
|---|---|---|---|---|---|---|
| V1 | 3 | **0 / 120** | 0 | 52 / 60 | 8 | 0 |
| V2 (채택) | 3 | **0 / 120** | 0 | 57 / 57 | 0 | 3 |
| V2 + JSON 추출 수정 | 1 | **0 / 40** | 0 | 20 / 20 | 0 | 0 |

**V1 의 놓침 8건은 전부 같은 부류였다** — `<think>` 유출(bad15) · 에러 JSON(bad16) · 스택
트레이스(bad17). 판정자의 사유: "JSON 형식의 에러 응답으로, 사람이 읽고 뜻을 잡을 수 있다".
틀린 말은 아니다. 프롬프트가 "읽을 수 있는가" 만 물었고, 스택 트레이스는 읽을 수 있는 글이다.
V2 는 이 부류를 한 줄로 못 박았다: *읽을 수 있어도 사용자에게 보내는 답변이 아닌 것(스택
트레이스 · 서버 에러 JSON · 모델의 내부 사고 · 시스템 프롬프트 · 채워지지 않은 템플릿)은
legible=false 다.* 그러자 놓침 0, 오탐은 그대로 0.

**V2 의 오류 3건은 판정이 아니라 파싱이었다.** bad15 는 답변에 `</think>` 가 들어 있고, 판정자가
그 구절을 quote 에 그대로 따왔다. `extract_json` 이 마지막 `</think>` 뒤를 취하는 규칙이라
JSON 의 앞부분이 잘려 나갔다 — 3회 모두 같은 자리에서. 추론 모델(Qwen3 등)의 추론 블록을
걷어내려던 규칙이 인용 안의 태그에 걸린 것이다. 뒤 태그부터 차례로 잘라 보고 JSON 으로
읽히는 첫 후보를 쓰도록 고쳤다. 실행 환경의 로컬 모델에서도 같은 일이 났을 것이다.

### 3차 — 끝을 중점으로, 중간의 오류 문구는 내용일 수 있다

"중간에 error 같은 문구가 있어도 답변 내용일 수 있다. 붕괴는 끝에서 드러난다" 는 지적을
받아 프롬프트에 한 문단을 더했다: *끝을 중점적으로 봐라. 중간의 오류 낱말 · 코드 · 로그
조각은 답변의 내용일 수 있고, 앞뒤가 멀쩡한 글로 이어지면 legible 이다.* 골든셋에는 오류를
설명하는 정상 답변 4건(ok41~44, `KeyError` · `error 809` · `[E-1042]` · `Traceback` 이 본문에
있음)과 앞은 멀쩡하고 끝만 깨진 붕괴 2건(bad21~22, 토큰 잡탕 · `<|endoftext|>` 유출)을 더했다.

| 프롬프트 | 회 | 오탐 | 무효 오탐 | 잡음 | 놓침 | 오류 |
|---|---|---|---|---|---|---|
| V3 (채택) · 66건 | 3 | **0 / 132** | 0 | 66 / 66 | 0 | 0 |

오류를 설명하는 답변 12건 전부 legible, 끝만 깨진 6건 전부 붕괴.

코드 규칙 쪽도 같은 자리에서 못 박았다: 되풀이는 **붙어 있을 때만** 붕괴다. "다음도
시도해보세요: A. 다음도 시도해보세요: B. …" 처럼 다른 내용을 사이에 둔 되풀이는 글의
구조다. `_repeated_unit` 은 원래 그렇게 동작했고, 테스트로 고정했다.

## 남은 것

- 실데이터에서 ④′ 가 얼마나 잡는지, 무효(인용 실패)가 얼마나 나오는지는 실행 요약에
  지표로 세지 않는다. 결과 JSON 의 `evidence.legibility` 에 남으니 첫 사이클에서 그걸 세어
  볼 것. 무효가 잦으면 인용 규칙이 이 자리에 안 맞는 것이다.
- 한 줄 답변("네.")에 대한 오탐은 0 이었지만 표본이 5개다. 실데이터에서 짧은 답변이
  붕괴로 닫히는 일이 있으면 "짧으면 묻지 않는다" 를 코드에 둔다.
