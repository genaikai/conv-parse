# 분류 체계 v4 — 결정 트리 (2026-10-29)

v3 의 "후보를 전부 내고 등급으로 중재" 를 버린다. 사내 피드백은 **흐름을 따라갈 수 없다**는
것이었다 — 상자 스물셋, 후보 생성 규칙, 등급 네 단계, 억제 규칙, 2차 검증, 조건부 인용. v4 는
턴 하나에 질문을 **순서대로** 묻고 **처음 걸리는 묶음 하나**를 붙인다. 결과 한 줄이 "어느 단계
어느 문항에서 멈췄고 뭐라 답했나" 로 읽힌다.

처음부터 모든 경우를 가르지 않는다. **큰 묶음을 먼저 잡고** 세부는 데이터를 본 뒤 태그로 더한다
(2단계). 이 문서는 1단계다.

## 목표 · 비목표

**목표**
- 결과 하나를 코드 없이 설명할 수 있다 — 멈춘 단계 · 문항 · 답.
- 턴당 kev 요청 최대 3, 일반 LLM 0.
- 고치는 사람이 다른 묶음 다섯으로 집계한다.

**비목표 (2단계로 미룸)**
- 묶음 안의 세부 — 근거를 안 썼나 어긋났나, 조건·memory·모순, 언어·길이·포맷, 계산·코드.
- context 초과 처리. 지금은 설계만 적어 두고 구현하지 않는다 (끝의 "미결").
- 인젝션 수행 · 개인정보 유출 · 못 내는 형태 요구 · 불명확 질문. 입구를 두지 않는다.

**안 바꾸는 것** — ① 파싱·짝짓기, ② 필터, eval.jsonl 경로(`assemble`), kev/LLM/Scripted 백엔드
(`decide.py`), 캐시, 실행 방식(turn/stage), 집계 축.

## 묶음 — 고치는 사람이다

| 묶음 | 고치는 사람 | 입구 |
|---|---|---|
| **정상** | 필터 (챗봇이 아니다) | 불만 판정 1 아니오 |
| **사용자** | 질문 유도 · UI | 불만 판정 6 · 7 |
| **근거** | 검색기 · 도구 연동 · 문서 | 근거 판정 없음·일부, 불만 부분 근거 판정 아니오 |
| **생성** | 프롬프트 · 모델 | 불만 판정 5 · 8, 근거 판정 전부, 불만 부분 근거 판정 예 |
| **시스템** | 인프라 · 서빙 · 권한 정책 | 코드 확정 셋, 불만 판정 2 · 3 · 4 |
| 검토 | 사람 | 어느 문항이든 모름 |

v3 와의 대응: N→정상, U→사용자, T·D→근거, G→생성, S·I→시스템. 가르기 어려운 경계(D1/T2,
S1/I1)를 처음부터 안 가른다. C(무결성)·U2(이벤트)는 플래그 열로만 남고 판정에 안 끼어든다.

**검토는 묶음이 아니라 상태다.** "문제 없음" 이 아니라 kev 가 확신하지 못한 턴이고, 멈춘 문항이
곧 그 이유다. 실패율 분모에서 빼고 따로 센다.

## 흐름

```
Case
 코드 확정        3규칙                      ─▶ 시스템
 불만 판정        kev 1요청 · 8문항 · 순서    ─▶ 정상 · 시스템 · 생성 · 사용자
 근거 판정        kev 1요청 · 5문항 · 합      ─▶ 생성 · 근거 · (일부면 다음)
 불만 부분 근거   kev 1요청 · 1문항           ─▶ 생성 · 근거
 어디서든 모름                               ─▶ 검토 (멈춘 문항 기록)
```

kev 는 요청 하나에 문항 여러 개를 받고 **각각 독립으로** 확률을 낸다. "1 이 예일 때만 2 를 봐라"
같은 순서는 kev 가 아니라 코드가 읽는다. 그래서 문항 하나하나가 혼자 읽혀도 뜻이 서야 한다.

**확신은 임계 하나.** `p ≥ 0.9` 예, `p ≤ 0.1` 아니오, 사이는 **모름**. 택일 문항(근거 전체)은
고른 선택지의 p 가 0.9 이상이어야 확신이다. 임계는 설정 `thresholds.kev_confident` 하나로 두고
`kev_lean` 은 없앤다.

**모름은 흘리지 않는다.** 모름이 나온 문항에서 멈추고 검토로 닫는다. 다음 문항으로 넘기면 "어디서
막혔나" 가 한 줄로 안 보인다. 예외는 근거 판정의 합 규칙 하나다 (아래).

### 코드 확정

답변 문자열만 본다. 불만은 안 본다 — 답이 없으면 불평 여부와 무관하게 시스템이다.

| 순서 | 규칙 | 어떻게 | 지금 코드 |
|---|---|---|---|
| 1 | 자원 부족 문구 | 공백 지운 답변에 설정 `service_error.templates` 문구가 통째로 들어 있다 | `short_circuit/service_error` 그대로 |
| 2 | 빈 답변 | 공백 지우고 아무것도 없다 | 새 규칙 (한 줄) |
| 3 | 붕괴 | 같은 글자·기호의 붙은 반복뿐 — 네 모양 (글자 2종 이하 · 짧은 조각 되풀이 · 글자 없음 · 끝에 긴 반복) | `short_circuit/degenerate` 그대로 |

처음 걸린 규칙에서 멈춘다. 안 걸린 규칙의 결과도 남긴다 ("봤는데 아니었다"). 걸리면 시스템 ·
확실 · kev 0.

셋 다 "걸리면 확실" 이고 다른 점은 놓치는 양이다. 붕괴는 보수적이라 토큰 잡탕 · 조금씩 바뀌는
되풀이 · 스택 트레이스 · 템플릿 토큰을 못 잡는데, 그건 불만 판정 3 이 받는다.

인젝션 수행(패턴 6 + 2단계 대조) · 개인정보 유출(패턴 + 질문 값 빼기) · kev "읽을 수 있나" 는
뺐다. 입구를 두지 않는다.

### 불만 판정

**입력** — `history_chat`(아래 규칙) · turn N 질문 · turn N 답변 · turn N+1 발화. 문서 · 도구 결과 ·
memory · 앞 턴 청크는 안 준다 — 주면 kev 가 "답이 맞았나" 를 재기 시작하고 그건 근거 판정의 일이다.

**문항 여덟, 요청 하나.** 코드가 1→8 순서로 읽어 처음 걸리는 데서 멈춘다. 1 이 아니오면 2~8 이
뭐라 했든 정상이다.

| 순서 | 문항 (결과 파일의 키가 된다) | 보는 것 | 예 | 아니오 |
|---|---|---|---|---|
| 1 | 후속 발화가 답변을 문제 삼는다 | 답변 + 후속 (+history) | 다음 | **정상** |
| 2 | 정책·권한 거절이고 그걸 불평한다 | 답변 + 후속 (+history) | **시스템** | 다음 |
| 3 | 답변이 읽을 수 없는 글이다 (토큰 잡탕 · 중간부터 깨짐 · 템플릿 토큰 · 스택 트레이스) | 답변 | **시스템** | 다음 |
| 4 | 답변이 중간에 끊겼다 (문장 · 목록 · 코드 블록 미완) | 답변 | **시스템** | 다음 |
| 5 | 답변이 질문과 다른 언어다 (혼합 포함. 질문이 요구한 언어가 있으면 그게 기준) | 질문 + 답변 | **생성** | 다음 |
| 6 | 후속 발화가 감정 표출뿐이다 (무엇이 틀렸는지 단서 없음) | 후속 | **사용자** | 다음 |
| 7 | 앞 질문에 없던 새 요구를 하며 불평한다 (앞 질문 = turn N + history 의 user) | history + 질문 + 후속 | **사용자** | 다음 |
| 8 | 문서·도구 없이 답할 질문이다 (계산 · 코드 · 일반 상식) | 질문 | **생성** | 근거 판정으로 |

순서의 이유 — 2~5 는 답변 자체가 보여 주는 사실이라 후속 발화의 성격(6 · 7)보다 앞이다. 끊긴 답에
욕만 했어도 끊긴 건 시스템이다. 6 · 7 이 8 과 근거 판정보다 앞인 건, 단서가 없거나 요구가 바뀐
불만은 원래 질문의 근거를 재 봐야 뜻이 없어서다. 그래서 근거 판정에 도착하는 턴은 "멀쩡한 답 ·
원래 질문 · 구체적 내용 불만 · 문서 질문" 으로 좁혀진다.

**history 규칙** (`history_chat` 은 서비스가 모델에 실제로 넣은 앞 턴 user·assistant 메시지)

| `history_chat` | 불만 판정의 history | 플래그 |
|---|---|---|
| 있다 (몇 턴이든) | 그대로. 상한 없음 — 사실은 자르지 않는다 | — |
| 비었고 앞 턴이 있다 | 턴 순서로 **최근 3턴**의 질문·답변을 재구성 | 앞 턴 누락 · 재구성 턴 수 |
| 첫 턴 | 비움 | — |

재구성은 "사용자가 전에 그 요구를 했나"(7) 를 위한 것이고, 모델이 그걸 봤는지는 플래그가 따로
말한다. 재구성의 출처는 지금 `conv.py` 의 폴백 그대로다 — `carried_turn_nos` 가 있으면 그 턴들,
없으면 턴 순서로 최근 것. 어느 쪽이든 **3턴 상한**. `history_input` 자체가 없는 옛 로그 · 골든셋도
"비었다" 와 같이 재구성하되 앞 턴 누락 플래그는 "옛 로그 — 판정 안 함" 으로 적는다 (없음과 비었음은
다르다). 그런 로그의 "앞 턴 근거" 칸은 폴백 scope 가 주는 것만 들어간다. 플래그가 선 턴이 많은 사이클은 사용자 행 집계를 보류한다고 전달본 머리에 적는다.

eval.jsonl 경로에서는 `records.jsonl` 이 답변 턴·불만 턴 둘만 담으므로, `history_input` 이 빈
행은 ② lookup 이 앞 3턴의 `user_question` · `llm_response` 도 가져와야 한다 — `docs/assemble.md`
계약에 한 줄 는다.

### 근거 판정

**묻는 것** — turn N 이 볼 수 있었던 근거에 질문의 답이 있었나. **답변과 후속 발화는 안 준다.**
근거 유무는 답변과 무관하고, 주면 kev 가 답의 옳고 그름을 잰다.

**state 다섯 칸**

| 칸 | 출처 |
|---|---|
| question | turn N 질문 |
| 이번 턴 검색 청크 | `retrieved_data` |
| 이번 턴 도구 결과 | `tool_output` |
| 앞 턴 근거 | `history_input.retrieved_data` + `history_input.tool_output` |
| 메모리 | `memory` + `history_input.memory` |

네 칸이 전부 비면 kev 를 안 부르고 **근거(빈 묶음)** 로 닫는다.

**문항 다섯, 요청 하나.** 칸별 넷은 "어디에 있었나", 전체 하나가 "있었나" 를 정한다. 기준은 두
가지로 다르다.

| 문항 | 범위 | 기준 | 답 |
|---|---|---|---|
| 이번 턴 검색 청크에 답이 있다 | 그 칸 | 질문의 **일부라도** 답하는 내용. 주제만 같은 건 아니오 | 예/아니오 |
| 이번 턴 도구 결과에 답이 있다 | 〃 | 〃 | 〃 |
| 앞 턴 근거에 답이 있다 | 〃 | 〃 | 〃 |
| 메모리에 답이 있다 | 〃 | 〃 | 〃 |
| 근거 전체에 답이 있다 | 네 칸 전부 | 질문이 묻는 것 **전부**인가 | 전부 / 일부 / 없음 |

빈 칸의 칸별 문항은 묻지 않고 "비어 있어 묻지 않음" 으로 적는다. 전체 문항은 칸이 하나라도 있으면
묻는다.

**읽는 규칙** — 묶음은 전체 문항 하나가 정한다. 칸별은 곁 정보다.

```
전체 = 전부 (확신)   → 생성   (where = 칸별 예인 칸)
전체 = 없음 (확신)   → 근거   (where = 빈 칸 · 아니오 칸)
전체 = 일부 (확신)   → 불만 부분 근거 판정으로
전체 = 모름          → 검토
```

칸별이 모름이어도 묶음에 안 끼어든다 — `where` 가 비는 것뿐이다.

칸별과 전체를 가른 이유: 칸마다 따로 물으면 답이 두 칸에 반씩 걸친 복합 질문을 칸별 전부
아니오로 놓친다. 전체 문항이 그 구멍을 막고, 칸별은 "어디" 를 공짜로 남긴다 (근거 묶음 안에서
검색 실패/도구 미호출, 생성 묶음 안에서 "앞 턴 근거에만 있었다" 가 2단계 없이도 보인다).

### 불만 부분 근거 판정

근거가 **일부**일 때만 돈다. 질문이 둘을 묻고 근거가 하나만 덮었을 때, 사용자가 **빠진 쪽**을
불평했으면 근거, **있던 쪽**을 틀렸다고 불평했으면 생성이다. 근거 판정은 후속 발화를 안 봐서
이 둘을 못 가른다.

**state** — turn N 질문 · turn N+1 발화 · 근거 네 칸 (근거 판정과 같은 것). 답변은 여기서도 안
준다 — "1.5 가 아닌데요" 가 질문의 어느 부분인지는 질문과 후속으로 잡힌다.

| 문항 | 예 | 아니오 |
|---|---|---|
| 불만이 가리키는 부분에 답이 근거에 있다 | **생성** | **근거** |

근거 판정의 여섯째 문항으로 넣지 않고 따로 요청하는 이유: 같은 요청에 넣으면 state 에 후속 발화가
들어가 근거 판정 다섯 문항 전부가 불만을 본 채로 채점된다.

## 플래그 — 트리 밖, 판정에 안 끼어듦

| 플래그 | 코드 |
|---|---|
| 앞 턴 누락 | 지금 `integrity.check_missing_turns` 그대로 (턴 번호 ↔ `history_chat` user 수) |
| history 재구성 턴 수 | 재구성했을 때 0~3 |
| 질문에 개인정보 | 지금 `pii.find_pii` 를 `pre_queries[-1]` 에. 종류·건수만, 값은 안 남긴다 |

memory 어긋남(C2)은 뺀다 — 그게 막던 라벨이 없다.

## 결과 파일

```json

  "turn": 4, "event_time": "2026-10-21T09:14:03",
  "target_turn": 3, "target_event_time": "2026-10-21T09:12:40",
  "verdict": {
    "bucket": "생성",
    "sure": true,
    "stopped_at": "근거 판정",
    "because": "근거에 답이 전부 있었는데 답변이 살리지 못했다",
    "where": ["이번 턴 검색 청크", "앞 턴 근거"]
  },
  "steps": [
    { "step": "코드 확정",
      "rules": { "자원 부족 문구": "아니오", "빈 답변": "아니오", "붕괴": "아니오" } },
    { "step": "불만 판정",
      "answers": {

        "정책·권한 거절이고 그걸 불평한다":       { "answer": "아니오", "p": 0.95 },
```

- `verdict` 다섯 키 고정. `because` 는 멈춘 자리마다 **고정 문장** — 같은 결론은 늘 같은 문장이라
  검색이 된다. `where` 는 근거 판정을 지난 턴만, 아니면 빈 목록.
- `stopped_at` 은 단계 이름. 검토면 문항까지: `"불만 판정 · 정책·권한 거절이고 그걸 불평한다"`.
- 불만 판정의 답은 여덟 전부 싣는다 — 멈춘 뒤의 것도. kev 가 한 번에 준 것이고 검토할 때 "뒤는
  뭐라 했나" 가 보인다. **`p` 는 보인 답의 확신**이다 ("아니오 0.95" = 확신 있는 아니오). 모름은
  `"answer": "모름"` 에 P(예) 그대로 — 어느 쪽으로 기울었는지가 검토자의 단서다.
- 근거 판정을 지난 턴은 어느 단계에서 닫혔든 `where` 가 있다 — 생성이면 답이 있던 칸, 근거면
  비었거나 답이 없던 칸.
- 불만 부분 근거 판정까지 간 턴은 `steps` 가 넷: `{ "step": "불만 부분 근거 판정", "answers":
  { "불만이 가리키는 부분에 답이 근거에 있다": {…} } }`.
- 본문은 맨 끝 `text` 블록에 싣는다 — `question` · `answer` · `followup` · `history`(불만 판정에
  준 것) · 근거 네 칸(칸마다 조각 목록). 전달본 · 대시보드가 **결과 파일만 읽어** 사례를 만드는
  구조라 빼면 둘이 원 로그를 다시 열어야 한다 (v3 도 실었다). `--no-text` 로 뺄 수 있고, 그때
  전달본의 사례 절은 비운다. 개인정보 값은 v3 처럼 플래그에 종류·건수만 남기고 본문은 그대로다.
- 식별자는 둘 다 싣는다 — `turn` · `event_time` 은 **불만 턴(N+1)**, `target_turn` ·
  `target_event_time` 은 **답변 턴(N)**. 하나만 실으면 사내 조인이 한 턴 어긋난다. `axes` 의
  `answered_by` · `ask_on` · `fallback` 은 답변 턴(N) 것, 조직 셋(부서 · 직급 · 직무)은 그대로.
- 문항 문장이 키다. 코드는 문항 id(`complains` 같은)로 들고 있다가 쓸 때 문장으로 바꾼다. 문장을
  고치면 결과 키도 바뀌니 문항 목록 한 곳이 원본이다.

## 미결 — 다음에 정한다

**context 초과.** kev 한계는 사내 서버 설정이라 모른다. 정해 둔 방향만 적는다 — 상한을 설정값
(`kev.max_chars`)으로, 먼저 실데이터 길이 분포를 재고, 넘치면 "검토(길이)". 불만 판정은 history
를 뒤에서부터 턴 단위로 자르고 답변은 안 자른다. 근거 판정은 칸 경계로 조각내 OR 로 합치고 순서
(이번 턴 → 도구 → 앞 턴 → 메모리)를 둔다. 요약 · 단어 겹침 가지치기는 안 쓴다. **이번 구현은
길이를 보지 않는다** — kev 가 거부하면 그 턴은 오류로 남긴다.

**2단계 태그.** 묶음별 건수를 본 뒤 많이 나온 묶음에만 코드로 되는 세부부터 (근거: 도구 안 부름 ·
검색 빗나감 — 칸별 답에서 이미 나온다 · 생성: 언어 · 포맷). kev 문항을 더하는 세부는 그 다음.

**복합 질문 비율.** 불만 부분 근거 판정이 얼마나 도는지로 본다.

## 빌더에게 맡기는 것

- 문항의 criteria 문장 (한국어, kev `noul` · `choice` 형식). 이 문서의 기준은 뜻이고 문장은 빌더가.
- 트리 엔진의 모듈 배치 — `features/` 등록부를 그대로 쓸지(단계 넷이 기능 넷), 단일 `tree.py` 로
  합칠지. 실행 방식 turn/stage 와 낙오자 규칙이 깨지지 않으면 어느 쪽이든.
- `TurnResult` · `Candidate` · `Classification` 을 새 스키마로 갈 것. 옛 결과 파일 읽기(`from_v2`)
  는 지원하지 않는다.
- `because` 고정 문장 목록.
- golden 러너(`--golden`)를 새 트리에 맞출지 뺄지 — 측정 모델 메모(`measurement-model`)는 그대로.
