# 처리 흐름 — 무엇을 쓰고 무엇을 일부러 안 쓰는가

`conv-data`(대화 로그)와 `filter-data`(필터)가 들어와 라벨(`case_id`)이 붙기까지의 경로.
단계마다 **목적 · 입력 · 출력**으로 적었다. 분류 체계는 v3 다 (`docs/design/taxonomy_v3.md`
가 설계, `src/ragdiag/taxonomy.py` 가 표). v2 의 옛 번호는 라벨 절 끝의 대응표에만 나온다.

읽을 때 중요한 것은 각 단계가 무엇을 받는가가 아니라 **무엇을 일부러 안 받는가**다.
판정자에게 정보를 더 주면 정확해질 것 같지만 이 파이프라인에서는 반대다 —
정보를 더 주면 **원인이 아니라 인상을 판정하게 된다.** 그래서 단계마다 입력을 잘라낸다.

```bash
python <저장소>/src/run.py \
    --conv-data   data/conv_eval.json \
    --filter-data data/filter.json \
    --output-dir  outputs
```

## 네 질문으로 보는 흐름 — 먼저 이것만

상자는 스물셋이지만 묻는 것은 **넷**이다. 나머지 상자는 이 넷에 "얼마나 확실한가" 를 붙이는
장부다. 아래 번호 ⑴~⑷ 는 이 절에서만 쓰고, 그 아래 단계 번호(③~⑦)와의 대응은 끝의 표에 있다.

```
                    ┌──────────────────────────────────────────────────────────────┐
  Case ───────────▶ │ ⑴ 판정할 답이 있기는 한가?                          코드      │
                    │    자원 부족 문구 · 글자 반복 · 템플릿 토큰 · 인젝션 수행 · 유출 │
                    └──────────────────────────────────────────────────────────────┘
                         │ 없다 ──▶ I1 · I2 · S2 · S3  (등급 4, 모델 호출 0)  ──▶ 끝
                         │ 있다
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑵ 사용자가 무엇을 불평했나?                         kev + LLM │
                    │    불만 종류 · 질문 종류 · 거절했나 · 복합질문 · 앞 조건 무시   │
                    │    + 요구(언어 · 길이 · 표) · 못 내는 형태(그림 · 링크)       │
                    └──────────────────────────────────────────────────────────────┘
                         │ 불만 없음 ───▶ N0            거절에 불만 ───▶ S1
                         │ 요구 어김 ───▶ G1 (코드 확인)  못 내는 형태 ─▶ U1 (⑶ 을 덮는다)
                         │ 내용 불만
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑶ 근거가 있었나? 모델이 그걸 썼나?                  kev + 코드 │
                    │    청크마다 "요구에 답하나"  ·  답변 주장마다 "근거와 맞나"      │
                    │    + 맥락: 앞 질문의 조건 · memory · 앞 답변과 모순            │
                    └──────────────────────────────────────────────────────────────┘
                         │
                         │              모델이 근거대로 말함      근거와 다르게 말함
                         │   근거 있음   G3 · G4(일부만)          G5
                         │   근거 없음   D1 검색 실패 · T1 도구 안 부름 · T2 엉뚱한 도구
                         │   맥락 어김   G2 (조건 · memory · 모순)
                         │   문서 아님   G6 (계산 · 코드 · 상식)
                         ▼
                    ┌──────────────────────────────────────────────────────────────┐
                    │ ⑷ 제일 확실한 증거의 라벨을 집는다                   코드      │
                    │    등급  4 코드 확정 › 3 근거 대조 › 2 kev 확신 › 1 기울어짐   │
                    │    동급이면 라벨 순서. 후보 없음 → unclassified                │
                    │    나머지 후보는 태그로. 플래그(C1 · C2) · 이벤트(U2) 는 곁에   │
                    └──────────────────────────────────────────────────────────────┘
                         │
                         ▼  주 라벨 · 등급 · 태그 · 플래그 · 이벤트
```

⑴ 만 턴을 멈춘다. ⑵ ⑶ 은 **분기하지 않고 전부 돈 뒤 후보만 낸다** — 그래서 상세 흐름도에
"건너뜀" 표시가 많다. 건너뜀은 분기가 아니라 "그 질문이 이 턴에 해당 없음" 이다.

**⑶ 이 핵심이다.** 표의 네 칸이 라벨 묶음을 가른다. 가로축은 주장 검증(contradicted 냐), 세로축은
충족도(sufficient 냐). 근거가 없으면 모델이 어길 것도 없으니 오른쪽 아래 칸은 비어 있고, 그 자리는
"왜 근거가 없었나" 로 쪼개진다 — 도구를 안 불렀나(T1) · 엉뚱한 도구였나(T2) · 검색이 빗나갔나(D1).

**예제 열 개를 이 그림에 놓으면** (`src/ragdiag/fixtures/v3_cases.py`)

| 예제 | 멈춘 곳 | 라벨 | 그림의 어디 |
|---|---|---|---|
| `i1-service` | ⑴ | I1(4) | 확정 문구. 호출 0 |
| `n0-thanks` | ⑷ | N0(2) | ⑵ 불만 없음 |
| `u1-image` | ⑷ | U1(2) | ⑵ 못 내는 형태. ⑶ 은 돌았지만 후보를 못 낸다 |
| `g5-contradict` | ⑷ | G5(3) | ⑶ 오른쪽 위 — 근거 있음 · 다르게 말함 |
| `d1-unverified` | ⑷ | D1(2) | ⑶ 왼쪽 아래 — 근거 없음. 2차 검증 불일치라 3 이 아니라 2 |
| `t2-biz` | ⑷ | T2(3) | ⑶ 왼쪽 아래 — 근거 없음인데 출처가 업무 도구뿐 |
| `g2-condition` | ⑷ | G2(3) | ⑶ 맥락 — 조건 구절을 원문에서 찾아 3. G5(2) 는 태그 |
| `c1-gap` | ⑷ | G5(3)+C1 | ⑶ 맥락 칸이 **C1 로 잠김** → 남은 G5 |
| `g2-contradict` | ⑷ | G5(3) | ⑶ 오른쪽 위와 맥락 둘 다 3 → ⑷ 순서로 G5. G2:모순 은 태그 |
| `unclassified-unsure` | ⑷ | unclassified | ⑵ 에서 kev 가 확신을 못 냄 → 후보 0 |

**네 질문과 코드 단계의 대응**

| 질문 | 단계 (아래 절) | 기능 (`features/__init__.py` JUDGES 순) |
|---|---|---|
| ⑴ 답이 있나 | ④ 확정 사건 · ④ 읽기 | `short_circuit`, `legibility` (+ 앞선 `integrity`, CHECKS_EARLY 는 장부) |
| ⑵ 무엇을 불평했나 | ⑤ 관측 · 요구 확인 · 조건 인용 대조 · 검증기 뒤 묶음 | `observe`, `request_quote`, `history_quote`, CHECKS_LATE |
| ⑶ 근거 · 사용 · 맥락 | ⑥ 검증 | `sufficiency`, `claims`, `memory_check`, `consistency`, `quotes` |
| ⑷ 고르기 | ⑦ 중재 | `arbitrate` |

⑴ 앞에 도는 `integrity`(C1 · C2 · U2) 와 코드 검증기 앞 묶음 8종은 질문이 아니라 **장부**다 —
⑴ 에서 닫히는 턴에도 플래그와 태그가 남도록 먼저 돈다.

## 전체 그림

실행 주체가 셋이다. **코드**(문자열 · 규칙 · 대조), **kev**(분류 모델 — yes/no · 택일 문항에
보정된 확률로 답한다. 문장은 못 만든다), **일반 LLM**(문장을 만들어야 하는 자리에만). 범주 답은
전부 kev 로 가고, 설정 `kev.url` 이 없으면 일반 LLM 이 같은 문항에 JSON 으로 답하는 에뮬레이션으로
떨어진다 (확률은 self-report 라 실행 요약에 "kev 에뮬레이션" 이라고 찍힌다).

```
conv-data ─┐
           ├─▶ ① 파싱·짝짓기 ─▶ ② 필터 ─▶ Case ─┬─▶ ③ 무결성 · 이벤트     코드    C1 · C2 플래그 · U2 이벤트. 멈추지 않는다
filter-data┘                                     ├─▶ ⑥ 검증기 앞 묶음 8종   코드    닫히는 턴에도 태그가 남게 먼저
                                                 ├─▶ ④ 확정 사건           코드    I1 · I2 · S2 · S3 ─▶ 끝
                                                 ├─▶ ④ 읽을 수 있나        kev ①  ← 답변만 봄 ─▶ I2 ─▶ 끝
                                                 ├─▶ ⑤ 관측               kev ②a 12문항 + LLM ②b 텍스트  ← 문서 · memory · 앞 답변 안 봄
                                                 ├─▶    요구 확인 · 조건 인용 대조   코드  ← 관측을 되돌린다
                                                 ├─▶ ⑥ 검증 — 전부 돈다
                                                 │      검증기 뒤 묶음 3종   코드   관측이 뽑은 요구값을 쓴다
                                                 │      충족도 ③ · 2차 ⑦    kev    ← 답변 안 봄. 청크 하나씩
                                                 │      주장 ④a LLM · ④b kev        ← 질문 · 불만 안 봄
                                                 │      memory ⑤ · 일관성 ⑥  kev    ← 불만 · 문서 안 봄
                                                 │      인용 (조건부)        LLM    전달본용. 판정을 바꾸지 않는다
                                                 └─▶ ⑦ 중재               코드 ─▶ 주 라벨 · 태그 · 등급
                                                                                   │
                              output/<시각>_<로그>_<필터>.json ◀───────────────────┤
                              output/<시각>_<로그>_<필터>_summary.txt ◀────────────┘
                                       │
                                       └─▶ src/handover.py ─▶ …_handover.json   실무 전달본
```

동그라미 번호가 둘이다. **단계**는 ③~⑦ 이고, ⑥ 안의 **호출**은 설계 문서의 번호(① 읽기 · ② 관측 ·
③ 충족도 · ④ 주장 · ⑤ memory · ⑥ 일관성 · ⑦ 2차)를 그대로 썼다. 아래에서는 호출 번호를
"호출 ③" 처럼 적는다.

| | 일반 LLM | kev | 언제 도나 |
|---|---|---|---|
| ③ 무결성 · 이벤트 | — | — | 항상. 걸려도 멈추지 않는다 |
| ④ 확정 사건 (규칙 4종) | — | — | 항상. 걸리면 여기서 끝 |
| ④ 읽기 | — | 1문항 | 항상 (`run.legibility: false` 로 끈다). 템플릿 토큰은 kev 없이 코드가 닫는다 |
| ⑤ 관측 | **1회** (②b) | 12문항 (②a) | ④ 를 통과한 턴 |
| 요구 확인 · 조건 인용 대조 | — | — | 관측이 있을 때 |
| ⑥ 코드 검증기 | — | — | 앞 8종은 항상, 뒤 3종은 관측 뒤 |
| ⑥ 충족도 + 2차 | — | 청크마다 1 (내용 불만이면 2) + 2차 1~근거 수 | 문서 질문(`domain` · `technical`) + 청크 있음 |
| ⑥ 주장 | **1회** (④a) | doc 주장마다 1 (④b) | 문서 질문 + 청크 있음 |
| ⑥ memory | — | 1문항 | `memory` 가 있고 C2 가 아닐 때 |
| ⑥ 일관성 | — | 앞 답변마다 1 | `prior_answers` 가 있을 때 |
| ⑥ 인용 | 최대 **3회** | — | 어긋남 · 모순 쌍이 있을 때만 |
| ⑦ 중재 | — | — | 항상 |

**일반 LLM 은 턴당 2회**(②b 관측 텍스트 · ④a 주장 추출)에 조건부 인용이 최대 3회 붙고, 일찍 닫힌
턴은 0회다. **kev 는 문항 수만큼** 부른다 — 보통 1 + 12 + 청크 수 + 주장 수 안팎이고 결과 파일의
`kev_calls` 에 턴마다 남는다. **라벨은 LLM 도 kev 도 고르지 않는다** — ⑦ 이 코드로 정한다.

**세 줄로 줄이면 이렇다.**

1. kev 에는 **좁은 범주 문항만** 묻고, 일반 LLM 에는 **문장이 필요한 칸만** 맡긴다 (④ ⑤ ⑥).
2. 그 답을 **코드가 검증하고 되돌린다** (요구 확인 · 조건 인용 대조 · 검증기 · 2차 검증).
3. 단계마다 낸 **후보를 증거 등급으로 중재해** 주 라벨 하나를 고르고 나머지는 태그로 내린다 (⑦).

이 문서의 나머지는 그 각 단계가 무엇을 받고 무엇을 일부러 안 받는가다.

## 무엇으로 분류되나 — 묶음 라벨 20개

라벨은 `묶음글자 + 번호` 다. 묶음은 증상이 아니라 **누가 고치는가**다 — 같은 증상도 문서팀이
고칠 일과 프롬프트 담당이 고칠 일은 다르고, 증상으로 묶으면 집계가 아무도 지목하지 못한다.
같은 묶음 안의 "무엇을 어겼나" 는 라벨이 아니라 **태그**다 — 라벨이 많으면 셀이 비어 표가 안
읽힌다 (v2 는 30개 중 실제로 나온 것이 9개였다). 목록은 묶음이 먼저(N U C T D G S I), 그 안에서
번호순이다 (`taxonomy.sort_key`). 고르는 자리와 표가 같은 순서여야 표에서 본 라벨을 찾을 수 있다.

종류가 셋이다. **failure** 는 실패 라벨로 실패율 분모에 들어간다. **flag** 는 무결성 플래그로 그
턴의 기록을 믿을 수 없다는 뜻이고 분모 밖이다. **event** 는 챗봇 실패가 아닌 사건이라 분모 밖에서
카운트만 한다. 실패 라벨 17개는 ⑦ 중재가 전부 낼 수 있다 — v2 처럼 "로그에 필드가 없어 도달
못 하는" 라벨은 목록에 두지 않았다 (아래 "제외한 실패").

**N(none) · 실패 아님** — 고칠 곳: 필터 (챗봇이 아니다)

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `N0` | 정상 후속 | failure | 필터 | 후속 발화가 앞 답변을 문제 삼지 않는다. 새 질문이거나 수긍이다. 실패율 분모에서 빼고, 쌓이면 필터를 좁힐 신호. `unclassified`(판정이 안 섬)와 다르다 |

필터는 재현율 쪽으로 넓게 잡으므로 그냥 다음을 묻는 턴이 섞여 들어온다. 낼 자리가 없으면 그게
`content_missing` 으로 읽혀 `D1` 을 부풀리고, 그 숫자가 코퍼스 보강 목록이 되어 문서팀이 **쓸 필요
없는 문서**를 쓴다.

**U(user) · 입력** — 고칠 곳: 질문 유도 · UI

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `U1` | 낼 수 없는 형태 요구 | failure | 질문 유도 · UI | 링크 · 이미지 · 파일 첨부처럼 이 서비스가 낼 수 없는 형태를 요구했다. 낼 수 있는 형식인데 안 지킨 것은 G1 |
| `U2` | 질문에 개인정보 | event | 질문 유도 · UI | 사용자가 질문에 주민번호 · 연락처 등을 넣었다. 입력 사건이다 — 그 턴의 답변은 따로 끝까지 판정한다 |

**C(context) · 맥락 기록** — 고칠 곳: 로그 · 적재 · 맥락 관리

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `C1` | 앞 턴 누락 | flag | 로그 · 적재 · 맥락 관리 | 대화에 앞 턴이 있는데 `history_chat` 에 빠져 있다. 이 턴의 **G2 전체**를 후보에서 뺀다 |
| `C2` | memory 어긋남 | flag | 로그 · 적재 · 맥락 관리 | memory 가 있는데 그 내용어가 대화 어디에도 없다. 이 턴의 **G2[memory]** 만 뺀다 |

빠진 것이 모델이 못 본 것인지 로그/적재가 떨어뜨린 것인지는 로그만으로 못 가른다. 그래서 라벨이
아니라 플래그다. 맥락을 봤는지 모르는 모델에게 맥락 불이행을 물을 수 없으므로 G2 만 막는다. C1 이
많이 나오면 그 사이클의 G2 집계를 보류한다 — 실행 요약이 그 줄을 찍는다.

**T(tool) · 도구 호출** — 고칠 곳: 오케스트레이션 · 도구 연동

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `T1` | 호출 없음 | failure | 오케스트레이션 · 도구 연동 | 업무 질문인데 도구(검색 포함)를 하나도 부르지 않고 답했다. `tool_calls` 와 이번 턴 청크(`n_fetched`)가 모두 0 |
| `T2` | 결과가 질문과 무관 | failure | 오케스트레이션 · 도구 연동 | 업무 도구만 불렀고 결과도 왔는데 그 내용이 질문에 답하지 못한다. 검색 도구 결과에 답이 없는 것은 D1 |
| `T3` | 빈 결과에 단정 | failure | 오케스트레이션 · 도구 연동 | 도구 결과가 비었는데(0건 · 빈 값) 답변이 수치 · 식별자를 단정했다. 도구로 증명되는 유일한 할루시네이션 |

도구는 검색을 포함하는 상위 개념이다. D1 과 T2 는 청크의 **출처**(`chunk_sources`)로 가른다 —
출처가 전부 업무 도구일 때만 T2 이고, 그러려면 설정 `tools.search_names` 에 검색 도구 이름이
있어야 한다. 없으면 D1 에 `D:출처미상` 태그가 붙는다. 도구 이름으로 결과를 추측하지 않는다.

**D(document) · 검색 근거** — 고칠 곳: 검색기 · 문서

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `D1` | 검색 근거에 답 없음 | failure | 검색기 · 문서 | 검색이 가져온 청크 어디에도 요구에 답하는 내용이 없다. 검색기가 못 찾은 것인지 문서가 없는 것인지는 코퍼스 전체를 봐야 갈린다 — 부서 편중으로만 추정 |

**G(generation) · 생성** — 고칠 곳: 생성 프롬프트 · 모델

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `G1` | 명시 요구 불이행 | failure | 생성 프롬프트 · 모델 | 언어 · 길이 · 포맷 · 어조 요구를 지키지 않았다. 어느 요구인지는 태그 |
| `G2` | 맥락 불이행 | failure | 생성 프롬프트 · 모델 | 앞 질문의 조건 · memory 의 사용자 정보를 어겼거나 앞 답변과 모순된다. 어느 맥락인지는 태그. C1 이 선 턴에서는 내지 않는다 |
| `G3` | 의도와 다른 답 | failure | 생성 프롬프트 · 모델 | 물은 것과 다른 것을 답했다. 다른 라벨에 걸리지 않은 불만의 **잔여** — 등급 1 뿐이라 구조적으로 아무것도 삼키지 못한다 |
| `G4` | 복합 일부만 답 | failure | 생성 프롬프트 · 모델 | 복합 질문의 일부만 답했다. 복합 질문을 한 것 자체는 태그(`복합질문`) |
| `G5` | 근거 활용 실패 | failure | 생성 프롬프트 · 모델 | 근거가 있는데 안 썼거나, 어긋나는 주장을 했거나, 인용을 지어냈다. 어느 쪽인지는 태그 |
| `G6` | 일반 지식 · 계산 · 코드 오류 | failure | 생성 프롬프트 · 모델 | 문서와 무관한 질문의 오답. 등식 · 날짜 · 코드 문법처럼 코드가 확인한 것은 등급 4, 확인 못 한 내용 불만은 등급 1 |

**S(safety) · 정책 · 보안** — 고칠 곳: 권한 정책 · 입력 방어 · 출력 필터

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `S1` | 정책 거절 | failure | 권한 정책 · 입력 방어 · 출력 필터 | 정책 · 권한을 이유로 거절했고 사용자가 불만을 표했다. 불만 없는 거절은 정당한 거절이라 N0. 권한 부족 거절과 로그상 구분되지 않는다 |
| `S2` | 인젝션 수행 | failure | 권한 정책 · 입력 방어 · 출력 필터 | 문서 안에 숨은 지시를 모델이 그대로 수행했다. 지시문이 있기만 한 것은 아니다 |
| `S3` | 답변 정보 유출 | failure | 권한 정책 · 입력 방어 · 출력 필터 | 질문에 없던 개인정보 패턴이 답변에 나왔다 |

**I(infra) · 서빙** — 고칠 곳: 인프라 · 모델 서빙

| 라벨 | 이름 | 종류 | 고칠 곳 | 뜻 |
|---|---|---|---|---|
| `I1` | 자원 부족 문구 | failure | 인프라 · 모델 서빙 | 서비스가 정해진 안내 문구를 대신 내보냈다. 모델이 답을 만든 적이 없다 |
| `I2` | 붕괴 · 읽을 수 없음 | failure | 인프라 · 모델 서빙 | 같은 글자의 반복, 토큰 잡탕, 내부 유출. 코드 규칙이 잡으면 등급 4, 읽기 판정이 잡으면 등급 2 |

잔여는 `unclassified` 다 — 어느 후보도 확신이 없음(등급 0). "문제 없음" 이 아니라 수동 검토 대상이다.

신뢰도는 라벨의 고정값이 아니라 **주 라벨의 증거 등급**에서 나온다 (4 · 3 → `high`, 2 → `medium`,
1 · 0 → `low`). 같은 D1 이라도 2차 검증을 지난 것과 아닌 것은 등급이 다르다. **같은 무게로 집계하면
안 된다** — 실행 요약의 "증거 등급" 표가 그 분포를 따로 찍는다.

### 태그 — 주 라벨에 딸린다. 집계 셀을 만들지 않는다

| 태그 | 붙는 조건 |
|---|---|
| `U3` | 질문 명확성이 `clear` 가 아니다 (그 선택지의 p ≥ 0.6) |
| `되묻기없음` | U3 인데 답변이 되묻지 않았다. G3 후보에 붙는다 |
| `G1:언어` `G1:길이` `G1:포맷` `G1:어조` | 어느 요구를 어겼나 |
| `G2:조건` `G2:memory` `G2:모순` | 어느 맥락을 어겼나 (`G2:약속` 은 등록만 돼 있고 아직 내는 코드가 없다) |
| `G5:안씀` `G5:어긋남` `G5:지어낸인용` `G5:과거근거` | 근거를 어떻게 잘못 썼나. 과거근거 = 근거 청크가 `history_input` 쪽(carried)에만 있었다 |
| `G6:계산` `G6:코드` `G6:일반` | 무엇이 틀렸나 |
| `T:인자불일치` | `resolved_question` 의 영숫자 식별자가 `tool_calls` 의 `arguments` 어디에도 없다 (`T:순서` 는 등록만 돼 있다) |
| `D:출처미상` | 검색 도구 이름 목록이 없어 D1 과 T2 를 가르지 못했다 |
| `복합질문` | 질문이 복합이다 (G4 가 아니어도) |
| `미검증주장` | 일반 지식(general) 주장이 있어 근거와 대조하지 못했다 |
| `2차불일치` | 충족도 2차 검증이 1차와 어긋났다 — D1 · T2 가 등급 2 로 내려간 이유 |
| 코드 검증기 이름 | 위반한 검증기 전부 (`pii` `format` `tool_numbers` …). 주 라벨이 무엇이든 남는다 |

**주 라벨이 무엇이든 태그는 전부 붙는다.** 주 라벨이 되지 못한 다른 후보도 `secondary_cases` 와
자기 태그로 남는다. 멈춤(④)은 LLM · kev 호출만 끊고, 입력만 보는 검증기 8종은 그 전에 돈다.

### 제외한 실패 — 로그에 정보가 없다

지연(응답 시간 없음) · 잘림(`finish_reason` 없음) · 컨텍스트 초과 · 구 문서(문서 개정일 없음) ·
권한 조회 실패 · 세션/인증. v2 의 `✗` 다섯이 여기다. 목록에서 지우되 "없는 문제" 가 아니라
"이 방법으로 못 보는 문제" 라고 전달본 머리에 적는다. 로그에 필드가 생기면 그때 라벨을 더한다.

### v2 → v3 대응

옛 결과 파일을 읽을 때만 쓴다 (`taxonomy.from_v2`). 옛 번호 하나가 v3 의 라벨 하나이거나,
라벨 없이 태그로만 남거나, 제외다.

| v2 | v3 |
|---|---|
| `case0` | N0 |
| `case1` `case4` | 라벨 없음 → `U3` 태그 |
| `case2` | U1 |
| `case3` | 라벨 없음 → `복합질문` 태그 |
| `case6` | U2 |
| `case9` | I1 |
| `case30` | I2 |
| `case10` `case11` `case12` `case16` | G1 (+ `G1:언어` `G1:길이` `G1:포맷` `G1:어조`) |
| `case13` `case17` | G3 |
| `case14` | G2 (+ `G2:조건`) |
| `case15` | G4 |
| `case18` `case22` `case24` | G5 (+ `G5:어긋남` `G5:안씀` `G5:지어낸인용`) |
| `case20` | D1 |
| `case21` | T1 |
| `case25` `case26` `case27` | G6 (+ `G6:일반` `G6:계산` `G6:코드`) |
| `case28` | S1 |
| `case29` | S2 |
| `case5` `case7` `case8` `case19` `case23` | 제외 |

v3 에서 새로 생긴 라벨은 C1 · C2 · T2 · T3 · S3 다 (`taxonomy.NEW_IN_V3`) — 2026-10 로그의
`history_input` · `tool_calls` 가 있어야 보이는 것들이다.

## 실행 방식 — 턴 단위와 단계 단위

판정 기능(③~⑦)은 두 방식으로 돌 수 있다 (`run.mode`).

| | `turn` (기본) | `stage` |
|---|---|---|
| 순서 | 턴 하나가 ③~⑦ 을 끝까지 간다. 워커 수만큼 동시에 | 기능 하나가 턴 전부를 돈 뒤 다음 기능 |
| 느린 턴 | 자기 워커만 붙잡는다. 다른 턴은 끝까지 간다 | 그 단계가 끝나지 못해 다음 단계가 기다린다 |
| 낙오자 | 턴 전체 소요 시간이 기준 (그 턴이 머무는 기능 이름으로 닫힘) | 그 단계 소요 시간이 기준 |
| 중간 결과 | 끝난 턴부터 10초마다 결과 파일에 쌓인다 | 전부 끝난 뒤 한 번 |
| 진행 표시 | `[judge] 128/540` 한 줄 | kev · LLM 을 부르는 기능마다 (`observe` `sufficiency` `claims` …) |

낙오자 기준은 같다 — 절반(8건 이상)이 끝난 뒤, 중앙값 × `run.straggler_factor`(4)와
`run.straggler_min_sec`(60) 중 큰 쪽. 넘겨도 안 오는 턴은 `[단계] 낙오 …` 로 닫히고 늦은 응답은
버려진다. 재실행하면 성공한 호출은 캐시에서 나오고 그 턴만 다시 묻는다. 집계(classification ·
failures 등)는 어느 방식이든 판정이 전부 끝난 뒤 한 번 돈다. 두 방식의 판정 결과는 같다 —
`tests/test_run_mode.py` 가 스냅숏 시나리오 전부로 확인한다.

## ① 파싱과 짝짓기

**목적** — 시간순 로그에서 "불만이 표현된 턴"을 찾아, **그 불만이 겨냥한 답변과 그 답변이 볼 수 있었던 것 전부**를 짝지어 `Case` 를 만든다.

**입력** — `conv_eval` JSON (users → conversations → turns), 또는 **eval.jsonl 경로**의
`records.jsonl` + `selected.jsonl` (`assemble.records_to_payload` 가 같은 중첩 모양으로 접은 뒤는
동일하다 — [assemble.md](assemble.md)). 턴 레코드 하나에 **네 층**이 있다.

| 층 | 필드 | 무엇인가 | 짝짓기에서 가는 곳 |
|---|---|---|---|
| 질문 · 답변 | `user_question` `llm_response` | 이 턴의 질문과 답 | `pre_queries[-1]` · `llm_ans_on_last_q` |
| 이 턴이 가져온 것 | `retrieved_data` `tool_output` `tool_calls` | 이 질문으로 검색된 청크와 도구 결과, 그리고 무엇을 어떻게 불렀나. **청크와 결과는 답변 생성에 들어간다** | `rag_chunks` 앞부분 · `n_fetched` · `tool_calls` · `tool_outputs` |
| 이 턴을 답할 때 들고 있던 과거 | `history_input` (`history_chat` `retrieved_data` `tool_output` `memory`) | 서비스가 **모델에 실제로 넣은** ~N-1 턴의 입력. 직전 턴까지라 이 턴 것은 없다 | `pre_queries` 앞부분 · `prior_answers` · `rag_chunks` 뒷부분 · `memory` · `history_turn_count` |
| 요약 맥락 | `memory` | 서비스가 들고 있던 **사용자에 대한 정보**. 모델은 답할 때 이것을 참고해야 한다 | `memory` |

그 밖에 `carried_turn_nos`(끌고 간 앞 턴 **번호**) · `prev_question` 은 `history_input` 이 없는 옛 로그에서만 쓰는 폴백이다.

**출력** — 턴마다 `Case` 하나. 짝을 한 칸이라도 틀리면 그 뒤가 전부 무의미해진다.

```
turn 3   Q: 연차 이월 예외 조건이 뭔가요?
         A: 연차는 사규에 따라 운영됩니다.            ← 비판받은 답변
         retrieved · tool_output: [청크1, 청크2]      ← 그 답변에 주어졌던 문서
         history_input: {history_chat, retrieved, …}  ← 그 답변이 들고 있던 과거
turn 4   Q: 예외 조건을 물었는데요.                    ← 불만 (이 턴이 분석 대상)
         A: ...
         retrieved: [청크3]                           ← 이건 쓰지 않는다
```

turn 4 가 지목되면 판정 대상은 **turn 3 의 답변과 turn 3 이 볼 수 있었던 것**이다.
turn 4 의 `retrieved_data` 를 쓰면 "불만에 대한 재검색 결과"를 보게 되어 완전히 다른 것을 잰다.

직전 턴은 "번호가 작은 것 중 가장 큰 것"이다(`prior[-1]`). 첫 턴을 지목하면 짝이 없어 `Case` 가 안 만들어지고 조용히 빠진다.

| Case 필드 | 어디서 | 누가 읽나 |
|---|---|---|
| `pre_queries` | 아래 세 갈래. **마지막 항목은 언제나 turn 3 의 질문** | ⑤ 관측 · 요구 확인 · 조건 인용 대조 · ③ U2 · ⑥ `tool_numbers` · ④ `leak` |
| `prior_answers` | `history_chat` 의 `assistant` 메시지, 순서대로 (없으면 턴 레코드에서 재구성) | ③ C2 · ⑥ 일관성 |
| `llm_ans_on_last_q` | **turn 3** 의 `llm_response` | 전부 |
| `current_query` | turn 4 의 `user_question` | ⑤ 관측 · ③ C2 · ④ `leak` |
| `rag_chunks` | **turn 3** 이 볼 수 있었던 문서 · 도구 결과 전부 (아래 청크 풀) | ⑥ 충족도 · 주장 · `quoted_spans` · `injection` |
| `chunk_sources` | 청크마다 출처 — `retrieved` · `tool:<이름>` · `history_retrieved` · `history_tool:<이름>` | ⑥ 충족도(own/carried) · ⑦ D1/T2 가름 · `G5:과거근거` |
| `n_fetched` | **turn 3 이 이번에** 가져온 청크 수 (`retrieved_data` + `tool_output`) | ⑦ T1 |
| `tool_calls` | 이 턴 + `history_input` 의 도구 호출 `[{turn_no, order, name, arguments}]` | ⑥ `tool_numbers` · ⑦ T1 · T3 · `T:인자불일치` |
| `tool_outputs` | 이 턴 + `history_input` 의 도구 결과 본문 (풀에도 들어 있다) | ⑥ `tool_numbers` · tool 주장 대조 |
| `memory` | turn 3 의 `memory` + `history_input.memory` | ③ C2 · ⑥ memory 반영 · 조건 인용 대조 |
| `prior_turn_nos` · `history_present` · `history_turn_count` | 대화의 앞 턴 번호 · `history_input` 이 있었나 · 그 안의 user 메시지 수 | ③ C1 |

**`pre_queries` 는 세 갈래이고 위가 이긴다.** 위로 갈수록 추정이 아니라 사실이다.

| | 출처 | 성격 | 상한 |
|---|---|---|---|
| 1 | `history_input.history_chat` 의 `role == "user"` | 모델에 실제로 들어간 질문 | 없음 |
| 2 | `prev_question` | 서비스가 적어 준 앞 질문 | 없음 |
| 3 | 턴 순서 재구성 (`carried_turn_nos` 가 있으면 그 번호만, 없으면 최근 `run.history_turns` 개) | 우리 추정 — 옛 로그 · 골든셋 | 3 |

1·2 에 상한을 안 거는 이유: 상한은 **추정**이 넓게 틀리는 걸 막는 장치다. 사실을 자르면 못 본 턴 대신 **본 턴**을 지우게 된다. 3 을 3개로 자르는 이유: 대명사 해소에 필요한 건 보통 직전 2~3턴이고, 더 오래된 질문을 추정으로 넣으면 노이즈라 판정자가 엉뚱한 주제로 끌려간다.

추정이 실제보다 **넓으면** 챗봇이 못 본 턴에서 "앞에서 정한 조건"을 찾아 G2(맥락 불이행)를 내고, **좁으면** 봤던 조건을 놓친다. 어느 쪽이든 조용히 틀린다 — `carried` 집계가 그 어긋남을 세고, `history_input` 이 있는 로그에서는 ③ 의 C1 이 누락을 플래그로 세운다.

**청크 풀(`rag_chunks`)은 한 레코드 안의 네 자리를 더한 것이다.** 순서가 곧 중요도이고, 자리마다 출처가 `chunk_sources` 에 남는다.

```
[turn 3 retrieved_data] + [turn 3 tool_output]                      ← 이 턴 것 (own). n_fetched 는 이 길이
  + [history_input.retrieved_data] + [history_input.tool_output.outputs]   ← 과거 것 (carried)
```

- `tool_output` 을 문서와 같은 층에 두는 이유: 빼면 도구 결과를 제대로 쓴 답변이 "있었는데 안 썼다"(G5)로, 그 인용이 "지어낸 인용"(`G5:지어낸인용`)으로 센다.
- `tool_calls` 는 청크가 아니라 **별도 필드**다. 무엇을 물었는지는 충족도 대조 대상이 아니지만, "안 불렀다"(T1) · "인자가 질문과 다르다"(`T:인자불일치`)는 여기서만 보인다.
- 청크 본문에 `turn_no` 같은 머리말을 붙이지 않는다. `quoted_spans` 와 인용 대조는 글자 그대로 연속 일치로 보므로, 로그에 없던 문자열이 생기면 대조가 깨진다.
- `history_input` 이 없는 옛 로그만 과거 턴 레코드를 돌아 `tool_output` 을 더한다. 둘 다 타면 같은 청크가 두 번 들어간다.
- 상한이 없다. 풀이 실데이터에서 실제로 커지는지를 결과 파일의 `chunk_data` 길이로 먼저 본다.

> 입력은 **완결된 형태로 들어온다고 가정한다** — `history_input` 에 과거 청크가 이미 구분되어 있고,
> 풀은 그 자리 넷을 더하는 것뿐이다. 사내 파서로 갈아끼우는 훅은 두지 않는다 (v0.87 에서 뺐다).

과거 턴의 문서가 풀에 들어오면 **"문서에 없었다"(D1)가 "있었는데 안 썼다"(G5)로 옮겨 간다.** 고칠 곳이 문서팀에서 생성 쪽으로 바뀐다. 그래서 ⑥ 충족도는 own 과 carried 를 따로 재고, 근거가 carried 에만 있으면 `G5:과거근거` 태그가 붙는다.

**`memory` 는 관측에 넣지 않는다.** 서비스가 들고 있던 **사용자에 대한 정보**이고, 다른 LLM 이 쓴 해석이라 ⑤ 관측에 넘기면 우리 관측이 그쪽으로 끌려간다. 대신 따로 묻는다 — ⑥ 의 memory 반영(호출 ⑤)이 memory 와 답변만 주고 반영했나를 kev 에 묻고, 조건 인용 대조가 "앞에서 정한 조건을 챗봇이 봤나"를 코드로 대조할 때 원문으로 쓴다. 그 전에 ③ 의 C2 가 이 memory 가 이 대화의 것이 맞는지부터 본다.

### 여기서 버리는 것

| 필드 | 왜 안 쓰나 |
|---|---|
| `event_time` | 지연 판정에 쓸 수 없다. 턴 시각 차이에는 사용자가 생각한 시간이 섞여 있다 |
| `trace_matched` | "2턴 이상"은 실제 턴 수로 판정한다. 선언값과 실제가 어긋난 로그를 본 적이 있다 |
| `ask_on` `answered_by` `route_intent` `fallback` | 실패의 원인이 아니라 실패가 일어난 자리다. 집계 축이지 판정 입력이 아니다 |
| `llm_eval_*` `llm_emotion_*` | ②에서만 쓰고 판정에는 넘기지 않는다 (아래) |

## ② 필터

**목적** — **무엇을 볼지 고르기만 한다.** 판정이 아니다.

**입력** — `filter-data` JSON + ①의 후보 턴들

| 필터가 보는 것 | 로그 필드 |
|---|---|
| 직급 · 부서 · 직무 | `job_grade` `db_dept_name` `db_job_name` |
| 턴 구간 | `turn` |
| 기간 | `event_time` |
| 대화 유형 점수 · 라벨 | `llm_eval_result` `llm_eval_score` `llm_eval_alternatives` |
| 감정 점수 · 라벨 | `llm_emotion_result` `llm_emotion_score` `llm_emotion_alternatives` |

**출력** — 선별된 턴 + **단계별 탈락 기록**

```
진단 가능 후속 턴 (2턴 이상 대화)   73
직급(role)                          58   (-15)
부서                                42   (-16)
턴 구간                             42
eval_score (0.0, 50.0)              37   (-5)
emotion_score (0.0, 30.0)           37
```

몇 건이 어디서 빠졌는지 전부 찍는다. 조용히 줄어들면 "이 조건에는 원래 없다"와
"필터가 잘못 걸렸다"를 구분할 수 없다.

첫 줄의 **후속 턴** 은 `turn ≥ 2` 이고 같은 대화에 `turn − 1` 이 있는 턴이다 (2026-10-27 까지는
`llm_eval_result` 가 있나로 봤다 — eval 이 비어 오는 eval.jsonl 이 생겨 턴 번호로 바꿨다).
eval.jsonl 경로에서는 이 필터가 `assemble.py select` 안에서 **같은 코드로** 돌고, `llm_eval_*` 가
비어 오므로 eval 조건이 있으면 걸지 않고 예외로 멈춘다. `--turns` 로 들어온 뒤에는 다시 안 건다.

### 필터가 쓴 값을 판정에 넘기지 않는 이유

`llm_eval_result`(질의 유형 라벨)와 `llm_emotion_result`(감정 라벨)는
**이미 다른 시스템이 내린 판정**이다. 이걸 ⑤에 넘기면 판정자가 그 라벨에 맞춰
관측을 고른다 — 독립적인 두 번째 의견이어야 할 것이 첫 번째 의견의 확인 도장이 된다.

필터는 "어떤 턴을 볼까"만 정하고, "그 턴에 무슨 일이 있었나"는 처음부터 다시 본다.

> 실행 환경에는 필터가 이미 구현돼 있다. 이 저장소의 `filters.py` 는 여기서 검증할 때만
> 쓴다. 경계는 `Case` 이고, `Case` 를 만들어 넣을 수만 있으면 ③부터는 그대로 돈다.

## ③ 무결성 · 이벤트 — 멈추지 않는다

**목적** — 이 턴의 **기록을 믿을 수 있는지**(C1 · C2)와 **챗봇 실패가 아닌 사건**(U2)을 먼저
적어 둔다. 라벨이 아니다. 걸려도 턴을 닫지 않고 끝까지 판정한다.

**입력** — `Case` 만. LLM · kev 없음.

| 무엇을 | 읽는 것 | 규칙 |
|---|---|---|
| `C1` 앞 턴 누락 | `history_present` · `prior_turn_nos` · `history_turn_count` | `history_input` 이 있는 로그만. 대화에 비판받은 턴보다 앞선 턴이 k 개면 `history_chat` 의 user 메시지도 k 개여야 한다. 적으면 violated |
| `C2` memory 어긋남 | `memory` ↔ `pre_queries` + `prior_answers` + `current_query` | memory 의 내용어(앞 두 글자)가 대화에 **하나도** 없으면 violated. 비율이 아니다 — memory 는 요약이라 표현이 다르기 마련이고, 오탐이면 그 턴의 G2[memory] 가 통째로 안 나온다. 내용어 3개 미만이면 대조하지 않는다 |
| `U2` 질문에 개인정보 | `pre_queries[-1]` | `pii` 검증기의 패턴 5종 (주민번호 · 휴대전화 · 이메일 · 카드 · 계좌). 종류와 건수만 남기고 값은 남기지 않는다 |

**출력** — `flags`(C1 · C2) · `events`(U2) 가 턴에 남고, 세 결과는 `checks` 에도 실린다.
효과는 ⑦ 에서 하나뿐이다: C1 은 G2 전체를, C2 는 G2[memory] 만 후보에서 뺀다. U2 는 아무것도
막지 않는다 — 사용자가 개인정보를 넣은 것과 답변이 나빴던 것은 독립 사건이다.

## ④ 확정 사건 — LLM 보다 먼저, 코드로

**목적** — 판정할 답변이 없거나(I1 · I2) 불만과 무관하게 사건이 확정인 턴(S2 · S3)을 **관측 전에**
닫는다. 관측에 넣으면 판정자가 자원 부족 문구를 거절로 읽어 S1 로 보낸다 — 서버 자원 문제가
보안 정책으로 집계되면 고칠 곳이 정반대다.

**입력** — `Case` 의 텍스트와, 그 앞에서 돈 검증기 앞 묶음(`injection` 등)의 결과. 관측은 아직 없다.

규칙 넷이 순서대로 돌고 처음 걸린 것이 라벨을 정한다. 걸리지 않은 규칙의 결과도 `checks` 에 남는다
— "봤는데 아니었다" 가 보여야 한다.

| 규칙 (`checks` 의 키) | 라벨 | 무엇을 |
|---|---|---|
| `service_error` | I1 | 공백을 지운 답변에 설정 `service_error.templates` 의 확정 문구가 들어 있다. 비슷한 문구는 잡지 않는다 — 오탐이면 그 턴의 진짜 원인이 통째로 사라진다 |
| `degenerate` | I2 | 같은 글자 · 기호의 반복뿐. 붙어 있는 되풀이만 붕괴다 — 다른 내용을 사이에 둔 되풀이는 글의 구조다 |
| `injection_rule` | S2 | `injection` 검증기가 violated (문서의 지시가 답변에 그대로 나타남). 지시문이 있기만 한 것(undetermined)은 닫지 않는다 |
| `leak` | S3 | 답변의 개인정보 패턴 중 사용자가 질문(`pre_queries` · `current_query`)에 넣은 값이 아닌 것. 되풀이는 유출이 아니다 |

**출력** — 걸리면 등급 **4** 로 닫는다 (`arbitrate.close`). ⑦ 과 같은 함수로 닫으므로 플래그 ·
이벤트 · 그때까지 돈 검증기 태그가 같은 모양으로 실린다. **LLM · kev 호출 0회.**

```
llm_ans_on_last_q 에 "서비스에 문제가 있거나, 사용자 분들이 많아서 …" 가 있음
   → I1 · 등급 4 · evidence 에 checks 만 남고 observation 은 없다
```

### 읽을 수 있는 글인가 — 답변만 보고 kev 가 한 번 (호출 ①)

규칙이 잡는 것은 `5555…` 처럼 오탐이 없는 모양뿐이다. 토큰 잡탕 · 중간부터 깨진 것 · 문단이
조금씩 바뀌며 되풀이되는 것 · 스택 트레이스는 규칙으로 열거할 수 없어 kev 에 묻는다.

**입력** — `llm_ans_on_last_q` **하나.** 질문 · 불만 · 문서를 주지 않는다. 주면 "질문에 맞는
답인가" 를 재기 시작하고, 그러면 부실한 답변까지 붕괴로 세어 D1 · G5 가 통째로 사라진다. 문항도
하나다 — `illegible`: 사람이 읽고 뜻을 잡을 수 없는가. 확신이 없으면 아니오라고 문항에 못 박았다.

**출력** — P(읽을 수 없다) 가 `legibility_p` 로 남는다.

| p | 어떻게 되나 |
|---|---|
| 채팅 템플릿 토큰(`<|im_start|>` `<think>` `{{…}}`)이 답변에 있음 | kev 를 묻지 않고 I2 · 등급 **4** 로 닫는다. 정상 답변에는 절대 없는 토큰이다 |
| p ≥ `kev_confident`(0.9) | I2 · 등급 **2** 로 닫는다 |
| 0.6 ≤ p < 0.9 | 닫지 않는다. p 만 남아 ⑦ 에서 I2 등급 1 후보가 된다 |
| 그 아래 | p 만 남는다. 후보가 아니다 |
| 빈 답변 | 묻지 않는다. 빈 답변은 읽기의 문제가 아니다 |

코드 규칙이 잡은 I2 는 등급 4, 여기서 잡은 것은 2 라 대시보드에서 색으로 갈린다. 설정
`run.legibility: false` 로 끈다. v2 는 판정자에게 깨진 구절을 인용하게 하고 코드가 대조했다 —
v3 는 kev 의 보정된 확률이 그 자리다.

## ⑤ 관측

**목적** — 사용자가 **무엇을 원했고 무엇을 못 받았는지**를 관측 사실로만 기록한다.
라벨을 고르지 않는다. 범주는 kev(②a), 문장은 일반 LLM(②b)이 낸다.

**입력** — ②a 와 ②b 가 **같은 것**을 받고 서로를 모른다.

| 주는 것 | 안 주는 것 |
|---|---|
| `pre_queries` — 이전 질문들, 마지막이 이번 답변을 부른 질문 | **`rag_chunks`** ← 이게 핵심 |
| `llm_ans_on_last_q` — 비판받은 답변 | `memory` · `prior_answers` — 다른 LLM 의 해석이라 끌려간다. 따로 묻는다 |
| `current_query` — 그 답변에 대한 불만 | `tool_calls` · `tool_outputs` · `dept` · `job_grade` · `job_name` |
| | `llm_eval_*` · `llm_emotion_*` · `turn` · `event_time` |

**왜 문서를 감추나.** 문서를 먼저 보여주면 판정자가 "이 문서로 답할 수 있었나"를 기준으로
사용자의 요구를 재구성한다. 문서에 있는 내용 쪽으로 `unmet_need` 가 끌려가고, 그러면
"문서가 충분했다"는 결론이 거의 자동으로 나온다. 순환이다.
사용자가 무엇을 원했는지는 **사용자의 말만 보고** 정해야 한다.

**②a 범주 관측 — kev 12문항.** 문항 id 가 곧 `Observation` 의 필드 이름이다 (`questions.OBSERVE`).
답(최빈 선택지 · P(yes) > 0.5 — 반반은 예가 아니다)은 관측에, 확률 분포는 `probabilities` 에 그대로
남아 ⑦ 의 등급이 된다.

| 문항 id | 유형 | 선택지 |
|---|---|---|
| `complaint_target` | choice | none · tone · format · language · length · content_missing · content_wrong · no_answer · inconsistency · other |
| `question_domain` | choice | domain · technical · general_knowledge · calculation · code · tool_usage · task · unclear |
| `question_clarity` | choice | clear · unresolved_reference · vague |
| `question_multi_intent` | noul | 서로 다른 요구가 둘 이상 섞였나 |
| `answer_refused` | noul | 정책 · 권한 · 보안을 명시적 이유로 거절했나. "인사팀에 문의하세요" 는 거절이 아니다 |
| `answer_covers_all_intents` | noul | 복합 질문의 모든 요구를 다뤘나. 단일 요구면 예 |
| `answer_actionable` | noul | 답변만 보고 다음에 무엇을 할지 알 수 있나 |
| `answer_ignored_history` | noul | 이전 질문들에 명시적으로 적힌 조건을 어겼나. 부실하기만 한 것은 아니오 |
| `answer_asked_back` | noul | 답변이 질문의 뜻이나 범위를 되물었나 |
| `requests_unsupported_output` | noul | 낼 수 없는 형태(링크 · 이미지 · 파일 · 실시간 조회)를 요구했나 |
| `requested_length_kind` | choice | none · max_chars · max_sentences · max_lines · vague_short |
| `requested_format` | choice | none · numbered_list · bullet_list · table · code_block · json · prose |

한 번에 라벨까지 묻지 않고 좁은 문항으로 나누는 이유는 둘이다. 어떤 모델이든 다지선다는 정확도가
안 나오고, 무엇보다 **판정자가 원인을 먼저 정하고 사실을 끼워 맞추는 것**을 막는다.

**②b 텍스트 관측 — 일반 LLM 1회.** 문장을 만들어야 하는 칸만이다 (`ObservationText`):
`reasoning` · `resolved_question` · `unmet_need` · `requested_language` · `requested_length_value` ·
`history_quote`. 판정하지 말고 문장을 정리하라고 지시한다.

**출력** — 둘을 합친 `Observation` 하나. 필드 20개.

| 필드 | 누가 | 값 | 무엇을 |
|---|---|---|---|
| `reasoning` | ②b | 자유 문장 | 불만과 질문을 어떻게 읽었는지 1~2문장 |
| `resolved_question` | ②b | 자유 문장 | 대명사 · 생략을 푼, 그 자체로 이해되는 질문. 후속 발화로 범위가 좁혀졌으면 좁혀진 쪽 |
| `unmet_need` | ②b | 자유 문장 | 원했는데 못 받은 것. **요구하지 않은 것을 덧붙이지 않는다.** 불만이 없으면 빈 문자열 |
| `complaint_target` | ②a | 위 선택지 | 불만이 무엇을 향하나. `none` 은 불만이 아니라는 뜻. 거절은 여기 없다 — `answer_refused` 가 정한다 |
| `question_domain` | ②a | 위 선택지 | 질문의 성격. `domain` · `technical` 이 **문서 질문**이다 (`schema.DOC_DOMAINS`) |
| `question_clarity` | ②a | 위 선택지 | 챗봇은 이전 질문들을 함께 받으므로 지시어가 앞 질문으로 풀리면 `clear`. 아니면 `U3` 태그 |
| `question_multi_intent` | ②a | bool | 요구가 둘 이상 섞였나 → `복합질문` 태그 · G4 의 조건 |
| `answer_refused` | ②a | bool | 거절했나 → S1 |
| `answer_covers_all_intents` | ②a | bool | 복합 질문의 모든 요구를 다뤘나 → G4 |
| `answer_actionable` | ②a | bool | 다음에 무엇을 할지 알 수 있나. **⑦ 이 읽지 않는다** — 결과 파일에만 남는다 |
| `answer_ignored_history` | ②a | bool | 앞 질문의 조건을 어겼나 → G2[조건] |
| `answer_asked_back` | ②a | bool | 되물었나 → U3 와 짝지어 `되묻기없음` |
| `requests_unsupported_output` | ②a | bool | 낼 수 없는 형태를 요구했나 → U1 |
| `history_quote` | ②b | 앞 질문들에서 따온 구절 · 없으면 빈 문자열 | 마지막 질문보다 **앞의** 질문들에 범위를 좁히는 조건이 있으면 그 구절. 조건 인용 대조를 거쳐 G2[조건] 을 등급 3 으로 올린다 |
| `requested_language` | ②b | `ko` `en` `ja` `zh` · 없으면 빈 문자열 | 요구 언어 |
| `requested_length_kind` | ②a | 위 선택지 | 길이 요구의 종류 |
| `requested_length_value` | ②b | 정수 · 수치가 없으면 `0` | 길이 요구의 값 |
| `requested_format` | ②a | 위 선택지 | 요구 형식 |
| `complaint_quote` · `requested_quote` | — | 언제나 빈 문자열 | v2 의 인용 칸. v3 는 kev 가 범주를 답하므로 인용을 받지 않는다. 필드만 호환용으로 남았다 |

`requested_*` 는 **관측이지 판정이 아니다.** "요구했다"까지만 적고 "지켰나"는 ⑥이 코드로 본다.
길이 요구는 재기만 하고 판정하지 않는다 — 기준이 사용자마다 달라서다.

**요구는 이전 질문들에 적힌 것만이다.** 비판받은 답변이 따를 수 있었던 것이어야 하므로,
후속 발화에서 처음 나온 요구("표로 정리해 주세요")는 요구가 아니다. 문항에도 그렇게 적었고,
확인은 아래 요구 확인이 코드로 한다 — 답할 때는 없던 요구를 어긴 것이 G1 로 나가지 않게 하는 장치다.

### 관측에 대해 헷갈리기 쉬운 세 가지

**(1) 모든 턴이 ⑤를 거치지는 않는다.**

| 어떤 턴 | observation |
|---|---|
| 보통의 턴 | 20개 전부 |
| I1 · I2 · S2 · S3 (④에서 규칙으로 끊김) | **없음.** LLM 도 kev 도 한 번도 안 불렀다 |
| I2 (④의 읽기 판정으로 끊김) | **없음.** `evidence.legibility` 만 있다 |
| 판정 실패(`error`) | 없음 |

④에서 닫힌 턴의 `evidence` 에는 `checks` 만 있고 `observation` 이 없다. 그게
"LLM 을 안 거쳤다"는 표시이기도 하다.

**(2) 20개를 내지만 결과 파일에는 16개만 실린다.**

결과 파일에 실리는 관측 필드 —

| 필드 | 왜 남기나 |
|---|---|
| `resolved_question` `unmet_need` | 무엇을 물었고 무엇을 못 받았나 — 충족도 · 주장의 기준 |
| `complaint_target` `question_domain` `question_clarity` | 불만의 방향 · 질문 성격 · 명확성 |
| `question_multi_intent` `answer_refused` `answer_covers_all_intents` `answer_ignored_history` `answer_asked_back` `requests_unsupported_output` | ⑦ 후보의 갈림길 |
| `answer_actionable` | 집계용. 중재는 안 읽는다 |
| `requested_language` `requested_length_kind` `requested_length_value` `requested_format` | 요구 확인을 거친 뒤의 값 — G1 이 나왔을 때 **무슨 요구였는지**를 여기서 본다 |

나머지 넷(`reasoning` · `complaint_quote` · `requested_quote` · `history_quote`)은 싣지 않는다 —
다만 `history_quote` 는 비어 있지 않을 때만 대조 결과(`history_quote_verified`)와 함께 실리고,
요구가 있었던 턴에는 `request_quote_verified`(요구가 이전 질문의 어휘로 받쳐졌나)가 함께 실린다.
문항의 확률 분포는 전부 `evidence.probabilities` 에 따로 실린다 — 등급의 근거라 빼지 않는다.

**(3) 20개 중 상당수는 "해당 없음" 센티널이다.**

`answer_refused` · `requests_unsupported_output` 은 대부분 `false` 이고 `requested_*` 는 대부분
`none` · `""` · `0` 이다. **"20개를 관측했다"가 아니라 "20개 슬롯을 채웠고 대부분은 해당 없음"이다.**
그래서 `not_applicable` 과 `violated` 를 섞으면 안 된다는 ⑥의 규칙이 여기서부터 시작된다.

### 요구 확인 · 조건 인용 대조 — 관측을 코드가 되돌린다

**목적** — 관측 중 **원문이 받쳐 주지 않는 것**을 되돌린다. LLM 없음. 관측과 검증기 사이에 있는
이유는, ⑥의 뒤 묶음 검증기가 읽는 요구값이 여기서 확정되기 때문이다.

| 기능 | 무엇을 확인하나 | 결과 |
|---|---|---|
| `request_quote` 요구 확인 | 요구(형식 · 언어 · 길이)가 **이전 질문들에 실제로 있었나** — `ragdiag/requests.py` 가 그 값의 어휘를 찾는다 | 없는 요구만 지운다. 하나라도 남으면 `request_quote_verified = true` |
| `history_quote` 조건 인용 대조 | ②b 가 댄 조건 구절이 마지막 질문보다 앞의 질문들(과 `memory`)에 글자 그대로 있나 | 있으면 G2[조건] 이 등급 3. 없어도 관측을 지우지 않는다 — p 가 있으면 등급 2 에 머문다 |

**요구 확인은 인용 대조가 아니라 코드다 (2026-09 에 바꿨다).** 전에는 판정자에게 근거 구절을
베껴 적게 하고 원문과 대조했는데, 약한 모델은 베끼는 일 자체를 안 한다 — Qwen3.5-9B 는
`requested_format` 을 맞게 읽고도 인용을 비운 것이 **27건 중 27건**이었다. 규칙이 "인용을 못
대면 요구가 없었다"를 전제하므로, 지어낸 요구가 아니라 **맞는 요구가 지워졌다.**

| | 누가 정하나 | 코드가 확인하는 것 |
|---|---|---|
| 형식 | kev (닫힌 집합 6개) | 그 값의 어휘가 앞 질문에 있는가 |
| 언어 | LLM (ISO 코드) | 언어를 지정하는 말이 **있었는가** (어느 언어인지는 안 봄) |
| 길이 | kev (종류) + LLM (값) | 분량을 지정하는 말이 **있었는가** (몇인지는 안 봄) |

**셋을 따로 지운다.** 서로 독립된 요구라 하나가 틀렸다고 나머지까지 없앨 이유가 없다.
조건 인용 대조가 관측을 지우지 않는 이유도 같다 — 확률이 있는데 인용이 없다는 이유로 지우면
약한 텍스트 모델이 맞는 판정을 끌어내린다. 마지막 질문은 대조 원문에서 뺀다 — 거기 적힌 조건을
어긴 것은 히스토리 문제가 아니라 의도를 잘못 읽은 것이다. 검증 방식과 외부 데이터셋 넷으로 잰
수치는 `docs/design/request_check.md`.

## ⑥ 검증 — 전부 돈다

**목적** — 관측이 말한 것을 **코드와 좁은 문항으로 확인**하고, 라벨 후보의 근거를 만든다.
불만 종류로 분기하지 않는다 (정확성 우선) — 형식 불만 턴에도 충족도를 재야 관측 하나가 틀려도
내용 결함이 태그로 남고 관측 오류가 교차 검증된다. 다만 **대조할 근거의 개념이 없는 자리**는
건너뛴다: 충족도 · 주장은 문서 질문(`domain` · `technical`)에 청크가 있을 때, memory 반영은
`memory` 가 있을 때, 일관성은 `prior_answers` 가 있을 때만이다.

**입력** — 단계 전체로 보면 `Case` 전부와 ⑤의 관측값이다. 호출마다 그중 일부만 준다 (아래 표).

| 주는 것 | 안 주는 것 |
|---|---|
| `llm_ans_on_last_q` · `rag_chunks` · `tool_calls` · `tool_outputs` · `pre_queries` · `memory` · `prior_answers` | **`current_query`** — 불만 원문은 어느 호출도 받지 않는다 |
| 관측값 — `resolved_question` · `unmet_need` · `requested_language` · `requested_format` · `requested_length_kind` · `requested_length_value` | `complaint_target` — 코드가 "요구로 한 번 더 잴까" 를 정할 때만 읽고 kev 에는 안 준다 |
| | `dept` · `job_grade` · `job_name` |

### 코드 검증기 11종 (+ ④의 규칙 4종)

LLM 없이 되는 것은 LLM 에게 묻지 않는다. 문자열만 보면 아는 것들이다. 두 묶음이다 — **앞 8종**은
입력만 보므로 ④ 보다 먼저 돌아 일찍 닫히는 턴에도 태그를 남기고, **뒤 3종**은 관측이 뽑은
요구값을 읽어 관측 뒤에 돈다. 표의 이름은 `Case` 의 필드명이다. ④의 규칙 4종도 같은 `checks` 에
남으므로 같이 적었다.

| 검증기 | 입력 | 무엇을 |
|---|---|---|
| `pii` | **`pre_queries[-1]`** | 질문에 개인정보 → U2 이벤트 (③) · 태그 |
| `quoted_spans` | `llm_ans_on_last_q` + `rag_chunks` | 답변이 인용부호로 제시한 문장의 원문 대조 → `G5:지어낸인용` |
| `python_syntax` | `llm_ans_on_last_q` | 파이썬 `ast.parse` → `G6:코드` |
| `sql_shape` | `llm_ans_on_last_q` | SQL 구조 결함 → `G6:코드` |
| `arithmetic` | `llm_ans_on_last_q` | 등식 재계산 → `G6:계산` |
| `dates` | `llm_ans_on_last_q` | 없는 날짜 · 요일 주장 → `G6:계산` |
| `injection` | `rag_chunks` + `llm_ans_on_last_q` | 문서의 숨은 지시를 수행했나 → S2 |
| `tool_numbers` | `llm_ans_on_last_q` + `tool_calls` + `tool_outputs` − `pre_queries` 의 숫자 | 답변의 수치 · 식별자가 도구 결과에 있나 → T3 (빈 결과에 단정) · `G5:어긋남` (값 불일치) |
| `language` | `llm_ans_on_last_q` + `requested_language` | 요구 언어 불이행 → `G1:언어` |
| `format` | `llm_ans_on_last_q` + `requested_format` | 요구 포맷 불이행 → `G1:포맷` |
| `length` | `llm_ans_on_last_q` + `requested_length_*` | **재기만 한다** — 판정하지 않는다 → `G1:길이` 는 등급 2 에서 멈춘다 |
| `service_error` | `llm_ans_on_last_q` | ④ 규칙. 자원 부족 확정 문구 → I1 |
| `degenerate` | `llm_ans_on_last_q` | ④ 규칙. 같은 글자 · 기호의 반복뿐 → I2 |
| `injection_rule` | `injection` 의 결과 (`rag_chunks` + `llm_ans_on_last_q`) | ④ 규칙. 검증기가 violated 면 턴을 닫는다 → S2 |
| `leak` | `llm_ans_on_last_q` − `pre_queries` · `current_query` 의 개인정보 | ④ 규칙. 질문에 없던 개인정보가 답변에 → S3 |

`llm_ans_on_last_q` 는 **비판받은 답변**이다 — 불만 턴(N+1)의 답변이 아니라
그 직전 턴(N)의 답변이다. ①의 짝짓기가 그렇게 잡아 놓은 것이다.

`pii` 하나만 답변이 아니라 **직전 질문**(`pre_queries[-1]`, 즉 그 답변을 부른 질문)을
본다 — U2 가 "질문에 개인정보가 포함된 경우"이기 때문이다. `leak` 은 그 반대 방향이다. 둘 다
결과 파일에는 종류와 건수만 남기고 원본 값은 남기지 않는다. 안 그러면 결과 파일 자체가 개인정보
사본이 된다.

`tool_numbers` 가 `pre_queries` 를 받는 것은 **빼기 위해서**다. 사용자가 질문에 적은 숫자(기간 ·
수량)를 답변이 되풀이한 것은 도구 결과가 아니어도 당연하다. 후속 발화는 안 뺀다 — 사용자가
불만에서 답변의 숫자를 되풀이하는 것("12대 아닌데요")을 "사용자가 준 숫자" 로 치면 단정이 전부
빠져나간다. 10 미만의 작은 숫자도 뺀다 — 목록 번호 · "3가지" 가 전부 걸린다.

`current_query`(불만 원문)를 보는 검증기는 `leak` 하나뿐이고, 그것도 빼기 위해서다.

**출력** — 검증기마다 네 값 중 실제로 나올 수 있는 것이 다르다.

| verdict | 뜻 | 중재가 어떻게 읽나 |
|---|---|---|
| `ok` | 검증했고 위반이 없다 | 후보를 내지 않는다 |
| `violated` | 검증했고 위반이다 | 등급 4 후보 (G1 · G6 · T3 · S2 · S3 · I1 · I2) 또는 등급 3 태그 (G5) |
| `not_applicable` | **잴 대상이 없었다** | 위반과 섞지 않는다. 결과 파일에도 싣지 않는다 |
| `undetermined` | 잴 대상은 있는데 코드로 못 정한다 | 불만이 그 요구를 가리키면 등급 2 후보 (G1) |

### verdict 를 어떻게 만드나 — 규칙 전부

LLM 이 없으니 판정은 전부 **문자열 규칙**이다. 세 갈래로 갈린다.

```
잴 대상이 있나?  ──아니오──▶ not_applicable   (요구 없음 · 코드블록 없음 · 인용 없음 …)
      │ 예
      ▼
코드로 정할 수 있나? ──아니오──▶ undetermined  (언어 판별 실패 · 길이 요구 …)
      │ 예
      ▼
   규칙 통과? ──▶ ok  /  ──▶ violated
```

| 검증기 | `not_applicable` | `ok` | `violated` | `undetermined` |
|---|---|---|---|---|
| `pii` | — | 패턴 없음 | 정규식 5종(주민번호 · 휴대전화 · 이메일 · 카드 · 계좌) 중 하나라도 걸림 | — |
| `quoted_spans` | 답변에 인용도 문서명도 없음 | 인용 전부 원문과 일치 | **둘을 따로 본다.** 문장 인용(`"…"` `'…'`)은 청크 **본문**과 최대 연속 일치율 90% 미만, 문서명(`「…」` `《…》`)은 청크 **머리의 출처 표기**에 포함되지 않음. **청크가 0건인데 인용했으면** 그 자체로 violated | — (출처 표기가 없으면 문서명은 대조하지 않고 그렇게 적는다) |
| `python_syntax` | 파이썬 코드 블록 없음 | 블록 전부 파싱 | 블록 하나라도 `SyntaxError` | — |
| `sql_shape` | SQL 코드 블록 없음 | 결함 없음 | SQL 키워드로 시작 안 함 · 괄호 짝 · `GROUP BY` 뒤 비어 있음 · `SELECT` 인데 `FROM` 없음 | — |
| `arithmetic` | 검증 가능한 등식 없음 | 전부 맞음 | `A + B = C` 꼴을 **재계산**해 오차 0.01 초과 | — |
| `dates` | 답변에 날짜 표기 없음 | 전부 달력에 있고 요일 주장도 맞음 | `M월 D일` · `YYYY-MM-DD` 가 달력에 없음, 또는 바로 뒤의 요일 주장이 틀림 | 연도가 없어 윤년 · 요일을 가를 수 없음 |
| `injection` | 문서에 지시문 패턴 없음 | — (**없다**) | 지시문 앞 20자가 답변에 나타남 | 지시문은 있으나 답변에 흔적 없음 |
| `tool_numbers` | 도구 호출도 결과도 없음 · 답변에 대조할 수치가 없음 | 수치 전부 결과에 있음 · 결과가 비었고 답변도 단정 안 함 | `빈결과:` 결과가 비었는데(빈 문자열 · `[]` · `{}` · `count: 0`) 답변에 수치 · 식별자 있음 — T3 의 근거. 아니면 수치가 결과에 없음 — `G5:어긋남` | — |
| `language` | 언어 요구 없음 | 문자 종류 비율로 판별한 언어가 요구와 같음 | 다름 | 답변의 언어 판별 실패 |
| `format` | 포맷 요구 없음 | 요구한 구조가 **2개 이상** 있음 (번호 목록 · 불릿 · 표(구분선 포함) · 코드펜스 · JSON 파싱 · 줄글은 목록 없음) | 없음 | — |
| `length` | 길이 요구 없음 | — (**없다**) | — (**없다**) | 요구가 있으면 언제나. 글자 · 문장 · 줄 수를 detail 에 적는다 |
| `service_error` | 답변이 비어 있음 | 확정 문구 없음 | 공백 · 줄바꿈을 지운 답변에 확정 문구(역시 공백 제거)가 **부분 일치** | — |
| `degenerate` | 답변이 비어 있음 | 반복 없음 · 10자 미만 | 서로 다른 글자 2종 이하 · 1~30자 조각이 **글자 그대로 연달아** 4번 이상 되풀이되어 90% 이상 · 한글/영문/한자/숫자가 하나도 없음 · 끝에 같은 글자 50개 이상 (마크다운 구분선 글자 제외) | — |
| `injection_rule` | `injection` 이 not_applicable | `injection` 이 ok · undetermined | `injection` 이 violated | — |
| `leak` | — | 답변에 패턴 없음 · 있어도 사용자가 질문에 넣은 값의 되풀이 | 질문에 없던 개인정보 패턴이 답변에 있음 | — |

**세 가지가 이 표의 요점이다.**

`pii` · `leak` 에 `not_applicable` 이 없다. 질문과 답변은 항상 있으므로 잴 대상이 늘 존재한다.

`injection` 에 `ok` 가 없다. 문서에 지시문이 **있다는 것**과 답변이 **수행했다는 것**은
다른 사건이다. 지시문이 없으면 잴 것이 없어 `not_applicable` 이고, 있는데 수행 흔적이
없으면 "안 했다"고 단정할 수 없어 `undetermined` 다. 업무 규정문은 "~한다" 같은
규범형이 많아 명령형만으로 의심하면 오탐이 쏟아진다.

`length` 에 `ok` · `violated` 가 없다. 기준이 사용자 머릿속에 있다 — "세 줄 이내" 가 개행 3개인지
요점 3개인지 사람마다 다르고, 503건 실측에서 임의 상수 하나가 판정 실패를 덮고 있었다. 그래서
측정만 남기고 판정을 버렸다. 실데이터에서 분포를 보고 기준을 정하게 되면 detail 만 읽으면 된다.

출력 잘림은 **뺐다.** 종결 부호와 코드펜스로 잘림을 짚었는데 온전한 답변이 잘림으로 오분류되는
일이 너무 많았다. 텍스트만으로는 "끊겼다" 와 "그렇게 끝맺었다" 가 갈리지 않는다. 로그에
`finish_reason` 이 생기면 그 값으로 되살린다.

`detail` 에는 **무엇을 보고 그렇게 판정했는지**가 들어간다
(`"요구 table 인데 해당 구조가 없음"`, `"빈결과: 도구 결과가 비었는데 답변에 수치 · 식별자 2개"`).

### 충족도 (호출 ③) — 청크마다 "답하나"

**목적** — **근거가 사용자의 요구를 담고 있었나**를 잰다. 답변의 품질이 아니다.

**언제 도나** — 둘이다. 문서 질문인지는 ⑤의 kev 가, 청크 유무는 코드가 정한다.

```
question_domain in DOC_DOMAINS  = {domain, technical}     ⑤가 정한다 (kev)    turn.doc_question()
   and rag_chunks 가 비어 있지 않다                        코드
```

불만 종류로는 가르지 않는다 — 형식 불만 턴에도 돈다. 내용 불만(`complaint_target` 이 `content_missing` ·
`content_wrong`, `sufficiency.CONTENT_COMPLAINTS`)이면 `unmet_need` 로 좁혀 **한 번 더** 잰다 (`:need`). 청크가 비면
kev 를 부르지 않고 `insufficient` 로 두되 2차 검증을 통과한 것으로 적는다 — T1 · T3 가 그 사실을 본다.

### `domain` 인지 누가 정하나 — ⑤의 kev 다

코드가 아니라 **⑤가 관측한 `question_domain`** 이다. `rag_chunks` 유무로 정하지 않는다 —
그러면 "도메인 질문인데 검색이 아예 안 걸린 경우"(T1)를 "도메인 질문이 아니었다"로 읽게 된다.

| 값 | 뜻 | 어디로 |
|---|---|---|
| `domain` | 회사 규정 · 절차 · 제도처럼 업무 문서를 찾아야 답할 수 있다 | 충족도 · 주장으로. T1 · T2 · D1 · G5 의 조건 |
| `technical` | 반도체 · 공정 · 장비 같은 기술 질문. 사내 기술 문서나 장비 데이터가 필요하다 | domain 과 같다 |
| `general_knowledge` | 공개된 지식만으로 답할 수 있다 (상식 · 법령 조문 · 표준) | G6 — 코드가 확인한 것은 등급 4, 아니면 등급 1 |
| `calculation` | 수식 · 날짜 · 산수 계산 | G6 |
| `code` | SQL · Python 등 코드 작성이나 오류 | G6 |
| `tool_usage` | Excel · Spotfire 등 도구 사용법 | G6 |
| `task` | 번역 · 메일 작성 · 요약 · 문장 다듬기 같은 작업 요청 | 문서 없음. G1 · G3 로만 간다 |
| `unclear` | 판별할 수 없다 | 대개 G3 또는 unclassified |

**`domain` 과 `general_knowledge` 의 경계는 "회사마다 답이 달라지는가"로 가른다.** 법령 · 표준을
언급했더라도 "우리 회사는 어떻게 운영하나"를 묻는 것이면 `domain` 이다. 문항은 **애매하면
`domain`** 이라고 지시한다. 잘못 `general_knowledge` 로 빠지면 G6 등급 1 로 가서 **검색 · 문서
문제가 통계에서 사라진다.**

**입력** — 청크 **하나씩**, 문항 하나 (`sufficiency_question`: "이 청크가 질문에 답하는 내용을 담고
있는가. 주제가 같다는 것만으로는 아니오다. 배경지식을 쓰지 마라").

| 주는 것 | 안 주는 것 |
|---|---|
| `resolved_question` — ⑤가 정리한 질문 (1차) | **`llm_ans_on_last_q`** ← 이게 핵심 |
| `unmet_need` — 내용 불만이면 이것으로 한 번 더 | `current_query` — 불만 원문 |
| `rag_chunks[i]` — 청크 하나 | 다른 청크 · `pre_queries` · `memory` |

**왜 답변을 감추나.** 답변을 같이 보여주면 판정자가 "이 답변이 부실하다 → 그러니 문서도
부실했겠지"로 미끄러진다. 재는 대상이 **문서의 충족도**에서 **답변의 품질**로 바뀐다.
그 둘은 다른 것이고, 갈라야 고칠 곳이 정해진다 — 문서에 답이 없었으면 검색기 · 문서(D1),
있었는데 안 썼으면 생성(G5).

**왜 청크 하나씩인가.** v2 는 LLM 한 번에 verdict 와 인용을 받고 인용을 코드가 원문과 대조했다.
청크 하나에 yes/no 면 yes 인 청크의 인덱스가 곧 근거라 **인용 대조가 필요 없고**, 입력이 작아
작은 모델로도 들어간다. 사전지식 오염은 "청크에 없으면 없는 것이다" 를 문항에 적고 2차 검증으로
되묻는 것으로 막는다.

**own 과 carried 를 따로 돈다.** 이 턴이 가져온 청크와 `history_input` 으로 넘어온 과거 청크다
(`chunk_sources` 로 가른다. 훅이 만든 풀은 `n_fetched` 로). 가르면 "이번 검색이 실패"(D1)와
"들고 있던 과거 근거에 답이 있었는데 안 씀"(`G5:과거근거`)이 갈린다.

**출력** — scope 마다 `Sufficiency` 하나 (`own` · `carried` · `own:need` · `carried:need`). 코드가 집계한다.

| 필드 | 값 |
|---|---|
| `supports` | 청크마다 `{chunk_index, p, source}` |
| `evidence` | p ≥ `chunk_evidence`(0.8) 인 청크 인덱스 — 근거 |
| `verdict` | 근거 있음 → `sufficient` · 없고 max p ≥ `chunk_partial`(0.5) → `partial` · 그 외 `insufficient` |
| `verified` | 아래 2차 검증 결과 |

종합 verdict 는 scope 중 하나라도 `sufficient` 면 `sufficient`, 아니면 `partial`, 아니면 `insufficient`
(`overall_verdict`). `partial` 은 "주제는 겹치는데 답하는 문장은 없다" 라 D1 쪽이다.

**2차 검증 (호출 ⑦)** — 같은 질문을 되묻지 않고 **다른 문항**으로 되묻는다.

| 1차 종합 | 2차 state | 문항 | 일치 |
|---|---|---|---|
| 불충분 (`partial` · `insufficient`) | 요구 + **청크 전부** | `absent`: 요구에 답하는 내용이 이 중 어디에도 없는가 | yes |
| 충분 | 요구 + 근거 청크 **하나씩** | `present`: 이 청크만으로 요구에 답할 수 있는가 | 하나라도 yes |

일치하면 D1 · T2 가 등급 3 이고, 불일치하면 등급 2 로 내려가고 `2차불일치` 태그가 붙는다. G5 의
등급은 2차와 무관하다 (어긋남은 주장 판정이, 안씀은 확신 등급이 정한다).

### 주장 (호출 ④) — 추출과 판정

**목적** — **답변의 사실 주장 하나하나가 근거와 어떤 관계인가.** v2 의 근거 활용은 답변 전체에
used / ignored / contradicted 한 칸이었다. v3 는 주장 단위다.

**언제 도나** — 충족도와 같다 (문서 질문 + 청크 있음).

**④a 주장 추출 — 일반 LLM 1회.** 답변에서 금액 · 기간 · 날짜 · 조건 · 절차가 들어간 문장을
**글자 그대로** 뽑고 기대 출처를 붙인다 (`Claims`: `[{text, expected_source}]`, 출처 ∈ doc · tool · general).

| 주는 것 | 안 주는 것 |
|---|---|
| `llm_ans_on_last_q` — 답변 하나 | `resolved_question` · `current_query` · `rag_chunks` — 질문도 문서도 주지 않는다. 주장은 답변 안에 있다 |

**④b 주장별 판정 — 출처별로 다르다.**

| 출처 | 누가 | 어떻게 | verdict |
|---|---|---|---|
| `doc` | kev, 주장마다 1문항 | state = 주장 + 근거 청크들 (충족도에서 p ≥ 0.5 인 것, p 순 최대 8개. 없으면 전부) | `supported` · `contradicted` · `not_found` |
| `tool` | 코드 | 주장의 숫자 · 식별자가 `tool_outputs` 에 있나 (`tool_numbers` 의 함수) | `tool_ok` · `tool_mismatch` · 결과가 없으면 `not_found` · 대조할 수치가 없으면 `unverified` |
| `general` | — | 대조할 것이 없다 | `unverified` → `미검증주장` 태그 |

**출력** — `claim_verdicts` `[{text, expected_source, verdict, p, chunk_indices}]`. ⑦ 은
contradicted → `G5:어긋남`(등급 3), 충분한데 doc 주장이 하나도 supported 가 아님 → `G5:안씀`(등급 2),
tool_mismatch → `G5:어긋남`(등급 3) 으로 읽는다. 결과 파일에는 v2 호환으로 `grounding.answer_used_rag`
한 칸도 같이 남긴다 (contradicted · tool_mismatch → `contradicted`, supported · tool_ok → `used`,
주장은 있는데 충분하면서 아무것도 안 맞음 → `ignored`).

### memory 반영 (호출 ⑤)

**목적** — 서비스가 들고 있던 **사용자 정보**를 답변이 어떻게 다뤘나.

**언제 도나** — `memory` 가 비어 있지 않고 C2 플래그가 아닐 때. 틀린 memory 를 반영 안 한 것은 결함이 아니다.

| 주는 것 | 안 주는 것 |
|---|---|
| `memory` · `llm_ans_on_last_q` | `current_query` · `rag_chunks` · `pre_queries` — 불만 · 문서 · 질문을 감춘다 |

**출력** — `memory_use` ∈ `reflected`(반영했거나 반영할 일이 없다) · `ignored` · `contradicted` 와 그
확률 `memory_p`. ignored · contradicted 면 `G2:memory` 후보다.

### 답변 일관성 (호출 ⑥)

**목적** — 이 답변이 **앞 답변들과 같은 것에 대해 다른 사실을 말하나.** 두 답변을 나란히 봐야
보이는 것이라 ⑤ 관측은 앞 답변을 받지 않고 여기서 따로 본다.

**언제 도나** — `prior_answers` 가 있을 때. 앞 답변마다 한 문항.

| 주는 것 | 안 주는 것 |
|---|---|
| `prior_answers[i]` · `llm_ans_on_last_q` | `current_query` · `rag_chunks` · `pre_queries` |

**출력** — `consistency` : 앞 답변 인덱스 → P(모순). 최대 p 로 `G2:모순` 후보의 등급을 정한다.
`complaint_target == inconsistency` 인데 앞 답변 기록이 없으면 대조할 수 없어 G3 에 그 사유가 적힌다.

### 조건부 인용 — 전달본용

kev 는 문장을 못 만든다. 실무가 "어디가 어긋나나" 를 보려면 구절이 필요하므로, 판정이 끝난
자리에만 일반 LLM 을 불러 **어긋나는 두 구절을 글자 그대로** 받고 코드가 원문 대조한다.

| 언제 | 근거 원문 | 종류 |
|---|---|---|
| ④b `contradicted` | 그 주장의 근거 청크들 | `G5:어긋남` |
| 호출 ⑤ `contradicted` | `memory` | `G2:memory` |
| 호출 ⑥ p ≥ 0.9 | 그 앞 답변 | `G2:모순` |

턴당 최대 3쌍. 대조에 떨어진 인용은 `verified: false` 로 남되 **판정은 바꾸지 않는다** — 유일한
효과는 대조를 통과한 `G2:memory` · `G2:모순` 이 등급 3 으로 올라가는 것이다.

## ⑦ 중재

**목적** — 앞 단계가 낸 **후보 전부**에서 주 라벨 하나를 **증거 등급**으로 고른다. LLM 도 kev 도
없다. v2 의 if-체인 진리표는 순서가 곧 규칙이라 라벨이 늘수록 유지가 안 됐다. v3 는 규칙마다
조건이 맞으면 후보를 내고(규칙들은 서로의 순서를 모른다), 선택은 등급 하나로 한다.

**입력** — 앞 단계가 낸 것 전부. 다만 **전부를 읽지는 않는다.**

| 주는 것 | 안 주는 것 |
|---|---|
| 관측 · 확률 · 검증기 verdict · 충족도 · 주장 판정 · memory · 일관성 · 인용 대조 결과 · 플래그 | **LLM 자체** |
| Case 의 `tool_calls` · `n_fetched` · `rag_chunks` 유무 · `chunk_sources` | `current_query` · `dept` · `job_grade` · `job_name` — 텍스트와 조직 속성은 갈림길이 아니다 |

| 어디서 | 중재가 읽는 것 | 안 읽는 것 |
|---|---|---|
| ③ 무결성 | `flags` 의 C1 · C2 | `events` — U2 는 결과에 실리기만 한다 |
| ④ 읽기 | `legibility_p` | — |
| ⑤ 관측 (20개 중 **10개**) | `complaint_target` `question_domain` `question_clarity` `question_multi_intent` `answer_refused` `answer_covers_all_intents` `answer_ignored_history` `answer_asked_back` `requests_unsupported_output` `resolved_question` | `reasoning` `unmet_need` `complaint_quote` `history_quote` `requested_language` `requested_length_kind` `requested_length_value` `requested_format` `requested_quote` `answer_actionable` |
| ⑤ 확률 | 읽는 문항의 p · 선택지 분포 | — |
| 조건 인용 대조 | `history.verified` | `request` — 요구는 이미 검증기 verdict 로 바뀌어 있다 |
| ⑥ 검증기 **전부** (11종 + ④의 규칙 4종) | verdict 와, `tool_numbers` 의 detail 머리(`빈결과:`) | 그 밖의 detail · evidence |
| ⑥ 충족도 | 종합 verdict · `verified` · scope 별 근거 유무 (과거근거) | 청크별 p · need |
| ⑥ 주장 | verdict 별 건수 · `expected_source` | text · p |
| ⑥ memory · 일관성 | `memory_use` · `memory_p` · 일관성의 max p | 어느 앞 답변인지 |
| 인용 | 종류와 `verified` | 구절 자체 |

**`requested_*` 넷을 중재가 안 읽는 것이 이 표의 요점이다.** 그 값은 ⑥이 소비해 `language` ·
`length` · `format` 검증기의 verdict 로 바뀌어 있다. 중재는 관측이 아니라 **검증 결과**를 본다 —
"요구했다"(관측)가 아니라 "지켰나"(코드)로 판정한다. `resolved_question` 을 읽는 자리는
`T:인자불일치` 태그 하나뿐이고(식별자를 `arguments` 와 대조), `answer_actionable` 은 v3 에 그것을
갈림길로 쓰는 라벨이 없어 결과 파일에만 남는다.

### 증거 등급

각 규칙은 `Candidate(label, grade, reason, tags)` 를 낸다. 등급은 **무엇이 그 후보를 떠받치나**다.

| 등급 | 뜻 | 신뢰도 | 어떤 후보 |
|---|---|---|---|
| 4 | 코드 확정 | `high` | I1 · I2 [규칙 · 템플릿 토큰] · S2 · S3 · T1 · T3 · G1 [검증기 violated] · G6 [검증기 violated] |
| 3 | 근거 확정 | `high` | D1 · T2 [2차 일치] · G5 [어긋남 · 지어낸인용 · 도구 수치 불일치] · G2 [인용 대조 통과] · S1 [p ≥ 0.9] |
| 2 | 확신 — p ≥ `kev_confident`(0.9) | `medium` | N0 · U1 · G4 · G5 [안씀] · I2 [읽기] · G2 [p 만] · D1 · T2 [2차 불일치] · G1 [undetermined 인데 불만이 그 요구] · S1 [0.6 ≤ p] |
| 1 | 기울어짐 — `kev_lean`(0.6) ≤ p < 0.9 | `low` | G3 · G6 [일반] · 그 밖에 p 가 기울어진 후보 |
| 0 | 후보 없음 | `low` | `unclassified` |

**주 라벨 = 등급 최대, 같으면 라벨 순서의 앞.** 나머지 후보는 `secondary_cases` 와 태그로 내려간다.
신뢰도는 주 라벨의 등급이다 — 라벨 표의 고정값이 아니다. 등급 1 뿐이면 `low` 고, 실행 요약은 등급
1 · 0 을 표본 검토 대상으로 따로 찍는다.

### 라벨 순서 — 같은 등급에서 앞이 이긴다

```
I1 I2 S2 S3 N0 S1 U1 T1 T3 D1 T2 G1 G5 G6 G4 G2 G3        taxonomy.ORDER
```

N0 가 S1 보다 앞인 이유: 불만 없는 거절은 정당한 거절이다. S2 · S3 가 N0 보다 앞인 이유: 불만과
무관한 사건이다. D1 이 G5 보다 앞인 이유: 검색이 실패해 답변이 부실하면 주장도 어긋나기 쉬운데,
그때 고칠 곳은 검색이다. G3 가 맨 뒤인 이유: 잔여 라벨이라 구조적으로 아무것도 삼키지 못하게.

### 후보 생성 규칙

`features/arbitrate/candidates.py` 그대로다. "문서 질문" 은 `question_domain ∈ {domain, technical}`,
"내용 불만" 은 `complaint_target ∈ {content_missing, content_wrong}`, p 로 등급은 p ≥ 0.9 → 2 ·
≥ 0.6 → 1 · 그 아래는 후보 아님이다.

| 후보 | 등급 | 조건 |
|---|---|---|
| `I1` | 4 | `service_error` violated |
| `I2` | 4 · 2 · 1 | `degenerate` violated (4) · 읽기 p ≥ 0.9 (2) · 0.6 ≤ p < 0.9 (1) |
| `S2` | 4 | `injection` 또는 `injection_rule` violated |
| `S3` | 4 | `leak` violated |
| `N0` | 2 · 1 | `complaint_target` = none, P(none) 으로 등급 |
| `S1` | 3 · 2 | `answer_refused` ∧ 불만 ≠ none. P(거절) ≥ 0.9 → 3, ≥ 0.6 → 2 |
| `U1` | 2 · 1 | `requests_unsupported_output`, p 로 등급. **등급 2 이면 T1 · T3 · D1 · T2 · G5 [주장 기반] · G3 후보를 올리지 않는다** — 낼 수 없는 형태를 요구했으면 근거 · 생성을 탓할 수 없고, 등급으로 다투게 두면 D1(3)이 U1(2)을 늘 이긴다. 코드 확정(G1 · G6 · S · I · `quoted_spans` · `tool_numbers` 의 G5)은 그대로다 |
| `T1` | 4 | 문서 질문 ∧ 내용 불만 ∧ `tool_calls` 빔 ∧ 이번 턴 청크 0 (`n_fetched`, 없으면 `rag_chunks` 길이) |
| `T3` | 4 | `tool_calls` 있음 ∧ `tool_numbers` 가 `빈결과:` violated |
| `D1` | 3 · 2 | 문서 질문 ∧ 내용 불만 ∧ `rag_chunks` 있음 ∧ 종합 verdict ∈ {partial, insufficient} ∧ 출처가 업무 도구만은 아님. 2차 일치 → 3, 불일치 → 2 + `2차불일치`. 출처에 `retrieved` 가 하나도 없고 검색 도구 이름 목록도 없는데 도구 · 훅 출처가 있으면 `D:출처미상` |
| `T2` | 3 · 2 | D1 과 같되 출처가 **전부 업무 도구** (`tools.search_names` 가 있을 때만 가를 수 있다. 이름 없는 `tool` 출처는 못 가른다) |
| `G1` | 4 · 2 · 1 | `language` · `format` · `length` violated (4) · undetermined ∧ 불만이 그 요구 (2) — 태그 `G1:언어` `G1:포맷` `G1:길이`. 불만 = tone 이면 P(tone) 으로 등급, `G1:어조` |
| `G5` | 3 · 2 | 문서 질문 ∧ 청크 있음일 때: ④b contradicted 있음 (3, `G5:어긋남`) · 아니면 종합 sufficient ∧ doc 주장 있음 ∧ supported 없음 ∧ 내용 불만 (2, `G5:안씀`) · tool 주장 `tool_mismatch` (3, `G5:어긋남`). 근거가 carried 에만 있으면 `G5:과거근거` 를 더한다. 그 밖에 `quoted_spans` violated ∧ 내용 불만 (3, `G5:지어낸인용`) · `tool_numbers` 값 불일치 ∧ 내용 불만 ∧ 문서 질문 (3, `G5:어긋남`) |
| `G6` | 4 · 1 | 문서 질문이 아닐 때: `arithmetic` · `dates` violated (4, `G6:계산`) · `python_syntax` · `sql_shape` violated (4, `G6:코드`) · 내용 불만인데 코드 위반 없음 (1, `G6:일반`; general_knowledge · calculation · code · tool_usage 만. task · unclear 는 아니다) |
| `G4` | 2 · 1 | `question_multi_intent` ∧ ¬`answer_covers_all_intents`, p = min(P(복합), 1 − P(다 다룸)) 으로 등급 |
| `G2` | 3 · 2 · 1 | C1 플래그가 아닐 때: `answer_ignored_history` ∧ 조건 인용 대조 통과 (3) · 통과 못 하면 p 로 등급 — `G2:조건`. C2 가 아니고 memory ignored · contradicted 면 `memory_p` 로 등급, 인용 대조 통과면 3 — `G2:memory`. 일관성 max p 로 등급, 인용 대조 통과면 3 — `G2:모순` |
| `G3` | 1 | 불만 ≠ none ∧ 위의 T · D · G · U1 · S1 · N0 후보가 하나도 없음 ∧ P(그 불만 종류) ≥ 0.6. 질문이 불명확한데 되묻지 않았으면 `되묻기없음`. 형식 · 언어 · 길이 불만인데 요구가 없었거나 지켰으면 "기대와 다른 답", no_answer 는 "잘림 여부는 로그로 판정 불가", inconsistency 인데 앞 답변이 없으면 "대조 불가" 가 사유다 |

후보가 하나도 없으면 `unclassified`(등급 0) 다. 불만 종류의 확신이 0.6 아래면 `other` 라도 G3 를
내지 않는다 — 확신 없는 잔여를 라벨로 세면 G3 가 쓰레기통이 된다.

**설계 문서와 다른 곳.** U1 이 후보를 막는 규칙은 설계에 없다 — 등급만으로 다투게 두면 "링크를 못
준 것" 이 "문서에 답이 없었다" 로 집계됐다. 설계는 `quoted_spans` 를 등급 4 태그로, S1 을 근거 확정
3 으로 적었지만 코드는 `G5:지어낸인용` 을 등급 3 후보로, S1 을 p ≥ 0.9 일 때 3 으로 낸다. G2 가
등급 3 이 되는 길도 설계는 조건 인용 하나인데 코드는 memory · 모순의 인용 대조 통과도 3 으로 올린다.
`G6:일반`(등급 1) · `G2:약속` · `T:순서` 는 설계의 태그표에만 있고 — 앞은 코드가 내지만 후보표에
없고, 뒤 둘은 내는 코드가 없다. 어긋나면 코드가 기준이다.

### 진리표 — 도메인 질문의 내용 불만

규칙 대부분은 단일 조건이라 위 표로 끝나지만, T · D · G5 · G3 분기만 값이 여럿 조합된다. 이
도구의 핵심이 거기라 전개해 둔다. 아래는 `candidates_for` 를 실제로 돌려 만든 것이다
(`tests/test_spec_compliance.py`). 문서 질문 · 내용 불만(p 0.95)이 전제다.

| 조건 | 후보 | 등급 |
|---|---|---|
| `tool_calls` 없음 · 이번 턴 청크 0 | `T1` 호출 없음 | 4 |
| 청크 있음 · verdict ≠ sufficient · 2차 일치 | `D1` 검색 근거에 답 없음 (출처가 업무 도구만이면 `T2`) | 3 |
| 청크 있음 · verdict ≠ sufficient · 2차 불일치 | `D1` + `2차불일치` | 2 |
| 청크 있음 · verdict ≠ sufficient · ④b contradicted | `D1` 이 이긴다 — `G5` 도 3 이지만 순서가 뒤다 | 3 |
| sufficient · ④b contradicted | `G5` + `G5:어긋남` | 3 |
| sufficient · doc 주장 있음 · supported 없음 | `G5` + `G5:안씀` | 2 |
| sufficient · 주장이 근거와 맞음(supported) · 그래도 내용 불만 | `G3` 의도와 다른 답 | 1 |
| 불만 종류 = none (P 0.95) | `N0` 정상 후속 | 2 |

세 줄이 이 표의 전부다.

**1행 vs 2행** — 부르지 않았으면 T1, 불렀는데 빗나갔으면 D1 (또는 T2). 앞은 검색을 탈지 말지
정하는 로직을 고치고, 뒤는 임베딩 · 청킹 · 문서(또는 도구 선택 · 인자)를 고친다. 사용자에게는
똑같이 "답이 부실하다"로 보이지만 고칠 곳이 다르다.

**3행** — 1차와 2차가 어긋나면 D1 을 지우지 않고 **등급을 내린다.** v2 는 인용이 안 남으면
강등했는데, v3 는 다른 문항으로 되물은 결과가 그 자리다.

**5행 vs 7행** — 문서에 답이 있는데 어긋나게 쓴 것(G5)과 맞게 쓰고도 불만인 것(G3). 전자는
프롬프트를 고치고 후자는 의도 이해를 본다. **이 갈림이 없으면 멀쩡한 코퍼스에 문서를 더 채우는
헛수고를 하게 된다.**

**출력** — 라벨 17개 + `unclassified`. 결과 JSON 의 `classification` 키는 v2 와 같고 값이 바뀐다.

```json
"classification": {
  "case_id": "G5",  "case_name": "근거 활용 실패",
  "type_id": "G",   "type_name": "생성",  "category": "generation",
  "owner": "생성 프롬프트 · 모델",  "kind": "failure",
  "confidence": "high",  "grade": 3,
  "reason": "답변의 주장 1건이 근거와 어긋남",
  "tags": ["G5:어긋남", "복합질문", "format"],
  "secondary_cases": [{"case_id": "G1", …}],
  "flags": ["C2"],  "events": ["U2"],
  "candidates": [{"label": "G5", "grade": 3, "reason": "…", "tags": [...]}, …],
  "notes": [...],
  "evidence": { "legibility", "observation", "probabilities", "sufficiency", "claims",
                "grounding", "memory", "consistency", "quotes", "checks" },
  "llm_calls": 2, "kev_calls": 19, "answered_turn": 3
}
```

라벨을 코드가 정하면 얻는 것이 하나 더 있다. 등급 임계값이나 규칙을 고쳐도 **LLM · kev 를 다시
돌릴 필요가 없다.** 관측과 확률은 그대로 두고 후보 규칙만 고치면 된다.

## 한 턴이 낳는 것 전부

| 필드 | 값 |
|---|---|
| `case_id` | 위 표의 라벨 17개 또는 `unclassified` |
| `case_name` `type_id` `type_name` `category` `owner` `kind` | `case_id` 에서 계산된다 (`taxonomy.describe`). 따로 분류하지 않는다 |
| `confidence` `grade` | 주 라벨의 증거 등급과 거기서 나온 신뢰도 |
| `reason` | 왜 이 라벨인지 한 문장 (`"검색 근거에 요구에 답하는 내용이 없음 (verdict=insufficient)"`) |
| `tags` | 주 라벨과 별개로 남는 것 전부 |
| `secondary_cases` | 주 라벨이 되지 못한 다른 후보 라벨들 (describe 꼴) |
| `flags` `events` | C1 · C2 / U2 |
| `candidates` | 후보 전부 — 등급 · 사유 · 태그. "왜 저 라벨이 아니고 이 라벨인가" 는 여기서 본다 |
| `notes` | 판정의 한계 (`"검색 실패와 코퍼스 부재는 구분 불가 — 부서 편중으로만 추정"`) |
| `llm_calls` `kev_calls` | 일반 LLM 호출 수 · kev 호출 수 (캐시 적중은 안 센다) |
| `evidence` | 읽기 p · 관측 16개 · 확률 분포 · 충족도(scope 별 청크 p · 근거 인덱스 · 2차) · 주장 판정 · memory · 일관성 · 인용 · 검증기 결과 |

`llm_calls` 와 `kev_calls` 가 그 턴이 어디까지 갔는지 보여준다.

| 호출 | 어디까지 |
|---|---|
| LLM 0 · kev 0 | ④ 규칙에서 끊김 (I1 · I2 · S2 · S3) 또는 캐시 히트 |
| LLM 0 · kev 1 | ④ 읽기에서 끊김 (I2) |
| LLM 1 · kev 13 | ⑤ 까지. 문서 질문이 아니거나 청크가 없어 충족도 · 주장이 안 돔 |
| LLM 2 · kev 13 + 청크 수 + … | 충족도 · 2차 · 주장까지 |
| LLM 3~5 | 어긋남 · 모순이 있어 인용까지 |

`evidence` 를 남기는 이유는 **집계만 보고 근거를 못 보면 "왜 이 라벨이지"에서 막히기
때문**이다.

## 파일

```
output/<시각>_<로그>_<필터>.json           원본 필드는 그대로, classification 아래에 판정 결과
output/<시각>_<로그>_<필터>_summary.txt    RUN SUMMARY 사본
output/<…>_handover.json                   실무 전달본 — src/handover.py 를 따로 돌려야 나온다
```

실행 요약에는 묶음 분포 · 라벨 분포 · 증거 등급 분포 · 태그 · 무결성 플래그와 이벤트 · kev 호출 수와
에뮬레이션 여부가 찍힌다. 전달본은 **판정과 갈라 둔 별개의 프로그램**이고 LLM 을 부르지 않는다.
결과 파일만 읽어 묶음 → 라벨 → 태그 → 사례로 다시 담고 무결성 · 이벤트는 별도 표다. 문구나 담을
항목이 마음에 안 들면 이것만 몇 번이든 다시 돌린다. 담는 것과 빼는 것은 [handover.md](handover.md).

## 요약 — 단계별로 감춘 것

| 단계 | 목적 | 주는 것 | **일부러 안 주는 것** | 안 주면 막히는 실패 |
|---|---|---|---|---|
| ④ 읽기 | 읽을 수 있는 글인가 | `llm_ans_on_last_q` | **질문 · 불만 · 문서** | 부실한 답변까지 붕괴로 셈 |
| ⑤ 관측 | 무엇을 원했나 | `pre_queries` · `llm_ans_on_last_q` · `current_query` | **`rag_chunks` · `memory` · `prior_answers`** | 문서에 맞춰 요구를 재구성하는 순환 · 다른 LLM 의 해석에 끌려감 |
| 요구 확인 · 조건 인용 대조 | 그 요구 · 조건이 앞 질문에 있었나 | 관측값 · `pre_queries` · `memory` | **LLM 자체** | 없던 요구를 어겼다는 판정 |
| ⑥ 충족도 | 근거에 있었나 | `resolved_question` · `unmet_need` · 청크 **하나** | **`llm_ans_on_last_q` · 다른 청크** | "답변이 나쁨"을 "문서가 나쁨"으로 읽음 |
| ⑥ 주장 | 답변이 무엇을 단정했나 · 근거와 맞나 | `llm_ans_on_last_q` (추출) · 주장 + 근거 청크 (판정) | **질문 · 불만 · 충족도 결과** | 답변 품질 인상이 주장 판정에 섞임 |
| ⑥ memory · 일관성 | 사용자 정보 · 앞 답변과 맞나 | `memory` / `prior_answers[i]` + `llm_ans_on_last_q` | **불만 · 문서 · 질문** | 관측이 다른 LLM 의 해석으로 끌려감 |
| ⑦ 중재 | 어느 라벨인가 | 후보 전부 | **LLM 자체** | 결론을 정하고 사실을 끼워 맞춤 |

판정 전체를 통틀어 **부서 · 직급 · 직무는 LLM 에도 kev 에도 넘기지 않는다.** 집계할 때만 쓴다.
"인사팀 질문이니 인사 문서가 있었겠지" 같은 추론이 판정에 섞이면 안 되고,
부서별 편중은 판정이 끝난 뒤 집계에서 봐야 신호가 된다.

`llm_eval_result` · `llm_emotion_result` 도 판정에 넘기지 않는다. 이미 다른 시스템이 내린
판정이라, 넘기면 독립적인 두 번째 의견이어야 할 것이 확인 도장이 된다.
