# 처리 흐름 — 무엇을 쓰고 무엇을 일부러 안 쓰는가

`conv-data`(대화 로그)와 `filter-data`(필터)가 들어와 묶음이 붙기까지의 경로. 단계마다
**목적 · 입력 · 출력**으로 적었다. 설계는 [design/decision_tree_v4.md](design/decision_tree_v4.md),
묶음 · 문항 표는 [taxonomy.md](taxonomy.md).

읽을 때 중요한 것은 각 단계가 무엇을 받는가가 아니라 **무엇을 일부러 안 받는가**다. 판정자에게
정보를 더 주면 정확해질 것 같지만 이 파이프라인에서는 반대다 — 정보를 더 주면 **원인이 아니라
인상을 판정하게 된다.** 그래서 단계마다 입력을 잘라낸다.

```bash
python <저장소>/src/run.py \
    --conv-data   data/conv_eval.json \
    --filter-data data/filter.json \
    --output-dir  outputs
```

---

## 전체 그림

실행 주체가 둘이다. **코드**(문자열 규칙 · 순서 읽기)와 **kev**(분류 모델 — yes/no · 택일 문항에
보정된 확률로 답한다. 문장은 못 만든다). 설정 `kev.url` 이 없으면 일반 LLM 이 같은 문항에 JSON
으로 답하는 에뮬레이션으로 떨어진다 (확률은 self-report 라 실행 요약에 "kev 에뮬레이션" 이라고
찍힌다). 문장을 만드는 자리는 없다.

```
conv-data ─┐
           ├─▶ ① 파싱·짝짓기 ─▶ ② 필터 ─▶ Case
filter-data┘                                │
                                            ├─▶ 플래그 열         코드     앞 턴 누락 · history 재구성 · 질문에 개인정보. 멈추지 않는다
                                            ├─▶ ③ 코드 확정       코드     자원 부족 문구 · 빈 답변 · 붕괴 ─▶ 시스템 ─▶ 끝
                                            ├─▶ ④ 불만 판정       kev 1   8문항 · 순서로 읽음 ─▶ 정상 · 시스템 · 생성 · 사용자 ─▶ 끝
                                            ├─▶ ⑤ 근거 판정       kev 1   5문항 · 전체가 정함 ─▶ 생성 · 근거 ─▶ 끝 / 일부면 ⑥
                                            └─▶ ⑥ 불만 부분 근거  kev 1   1문항 ─▶ 생성 · 근거
                                            어디서든 모름 ─▶ 검토 (멈춘 문항 기록)
                                                     │
                  output/<시각>_<로그>_<필터>.json ◀──┤   turns[] — verdict · steps · flags · axes · text
                  output/<시각>_<로그>_<필터>_summary.txt ◀┘
                           │
                           └─▶ src/handover.py ─▶ …_handover.json   실무 전달본
```

| 단계 | kev 요청 | 언제 도나 |
|---|---|---|
| 플래그 열 | — | 항상. 멈추지 않는다 |
| ③ 코드 확정 | — | 항상. 걸리면 여기서 끝 |
| ④ 불만 판정 | 1 | ③ 을 통과한 턴 |
| ⑤ 근거 판정 | 1 (네 칸이 전부 비면 0) | ④ 를 통과한 턴 |
| ⑥ 불만 부분 근거 판정 | 1 | ⑤ 가 "일부" 로 열어 둔 턴 |

**턴당 kev 요청 최대 3, 보통 2, 일반 LLM 0.** 요청 하나에 문항 여러 개를 넣고 kev 는 각각 독립으로
채점한다 — "1 이 예일 때만 2 를 봐라" 는 kev 가 아니라 코드가 읽는다. 묶음은 kev 가 고르지
않는다 — 코드가 답을 순서(④) 또는 합(⑤)으로 읽어 정한다.

**세 줄로 줄이면 이렇다.**

1. 질문을 **순서대로** 묻고 **처음 걸리는 묶음 하나**를 붙인다. 후보도 등급도 중재도 없다.
2. 단계마다 입력을 뺀다 — ④ 는 문서를, ⑤ 는 답변과 불만을 안 본다.
3. 모름은 그 자리에서 **검토**로 닫는다. 결과 한 줄이 "어느 단계 어느 문항에서 멈췄고 뭐라 답했나" 다.

## 실행 방식 — 턴 단위와 단계 단위

판정 기능은 두 방식으로 돌 수 있다 (`run.mode`).

| | `turn` (기본) | `stage` |
|---|---|---|
| 순서 | 턴 하나가 ③~⑥ 을 끝까지 간다. 워커 수만큼 동시에 | 기능 하나가 턴 전부를 돈 뒤 다음 기능 |
| 느린 턴 | 자기 워커만 붙잡는다. 다른 턴은 끝까지 간다 | 그 단계가 끝나지 못해 다음 단계가 기다린다 |
| 중간 결과 | 끝난 턴부터 10초마다 결과 파일에 쌓인다 | 전부 끝난 뒤 한 번 |

낙오자 기준은 같다 — 절반(8건 이상)이 끝난 뒤, 중앙값 × `run.straggler_factor`(4)와
`run.straggler_min_sec`(60) 중 큰 쪽. 넘겨도 안 오는 턴은 `[단계] 낙오 …` 로 닫히고 늦은 응답은
버려진다. 재실행하면 성공한 호출은 캐시에서 나오고 그 턴만 다시 묻는다. 두 방식의 판정 결과는
같다 — `tests/test_run_mode.py` 가 열한 경로 전부로 확인한다.

## ① 파싱과 짝짓기

**목적** — 시간순 로그에서 "불만이 표현된 턴"을 찾아, **그 불만이 겨냥한 답변과 그 답변이 볼 수 있었던 것 전부**를 짝지어 `Case` 를 만든다.

**입력** — `conv_eval` JSON (users → conversations → turns), 또는 **eval.jsonl 경로**의
`records.jsonl` + `selected.jsonl` (`assemble.records_to_payload` 가 같은 중첩 모양으로 접은 뒤는
동일하다 — [assemble.md](assemble.md)). 턴 레코드 하나에 **네 층**이 있다.

| 층 | 필드 | 무엇인가 | 짝짓기에서 가는 곳 |
|---|---|---|---|
| 질문 · 답변 | `user_question` `llm_response` | 이 턴의 질문과 답 | `pre_queries[-1]` · `llm_ans_on_last_q` |
| 이 턴이 가져온 것 | `retrieved_data` `tool_output` `tool_calls` | 이 질문으로 검색된 청크와 도구 결과, 그리고 무엇을 어떻게 불렀나. **청크와 결과는 답변 생성에 들어간다** | `rag_chunks` 앞부분 · `n_fetched` · `tool_calls` · `tool_outputs` |
| 이 턴을 답할 때 들고 있던 과거 | `history_input` (`history_chat` `retrieved_data` `tool_output` `memory`) | 서비스가 **모델에 실제로 넣은** ~N-1 턴의 입력. 직전 턴까지라 이 턴 것은 없다 | `pre_queries` 앞부분 · `history_messages` · `rag_chunks` 뒷부분 · `memory` · `history_turn_count` |
| 요약 맥락 | `memory` | 서비스가 들고 있던 **사용자에 대한 정보**. 모델은 답할 때 이것을 참고해야 한다 | `memory` |

그 밖에 `carried_turn_nos`(끌고 간 앞 턴 **번호**) · `prev_question` 은 `history_input` 이 없는 옛 로그에서만 쓰는 폴백이다.

**출력** — 턴마다 `Case` 하나. 짝을 한 칸이라도 틀리면 그 뒤가 전부 무의미해진다.

```
turn 3   Q: 연차 이월 예외 조건이 뭔가요?
         A: 연차는 사규에 따라 운영됩니다.            ← 비판받은 답변
         retrieved · tool_output: [청크1, 청크2]      ← 그 답변에 주어졌던 문서
         history_input: {history_chat, retrieved, …}  ← 그 답변이 들고 있던 과거
turn 4   Q: 예외 조건을 물었는데요.                    ← 불만 (이 턴이 분석 대상)
         A: ...
         retrieved: [청크3]                           ← 이건 쓰지 않는다
```

turn 4 가 지목되면 판정 대상은 **turn 3 의 답변과 turn 3 이 볼 수 있었던 것**이다.
turn 4 의 `retrieved_data` 를 쓰면 "불만에 대한 재검색 결과"를 보게 되어 완전히 다른 것을 잰다.

직전 턴은 "번호가 작은 것 중 가장 큰 것"이다(`prior[-1]`). 첫 턴을 지목하면 짝이 없어 `Case` 가 안 만들어지고 조용히 빠진다.

| Case 필드 | 어디서 | 누가 읽나 |
|---|---|---|
| `pre_queries` | 아래 세 갈래. **마지막 항목은 언제나 turn 3 의 질문** | ④ ⑤ ⑥ 의 `question` · 플래그(질문에 개인정보) |
| `history_messages` · `history_reconstructed` | `history_chat` 의 user · assistant 를 원래 순서대로. 비었고 앞 턴이 있으면 최근 3턴 재구성 (`conv.reconstruct_history`) | ④ 의 `history` · 플래그(재구성 턴 수) |
| `llm_ans_on_last_q` | **turn 3** 의 `llm_response` | 전부 |
| `current_query` | turn 4 의 `user_question` | ④ ⑥ 의 `followup` |
| `rag_chunks` | **turn 3** 이 볼 수 있었던 문서 · 도구 결과 전부 (아래 청크 풀) | ⑤ ⑥ 의 근거 네 칸 (`chunk_sources` 로 가른다) |
| `chunk_sources` | 청크마다 출처 — `retrieved` · `tool:<이름>` · `history_retrieved` · `history_tool:<이름>` | 근거 네 칸 가르기 (`Case.retrieved_chunks` · `tool_chunks` · `history_chunks`) |
| `n_fetched` | **turn 3 이 이번에** 가져온 청크 수 (`retrieved_data` + `tool_output`) | dry-run 의 풀 크기 지표 |
| `tool_calls` | 이 턴 + `history_input` 의 도구 호출 `[{turn_no, order, name, arguments}]` | 아직 판정에 안 쓴다 (2단계 태그 재료) |
| `tool_outputs` | 이 턴 + `history_input` 의 도구 결과 본문 (풀에도 들어 있다) | 아직 판정에 안 쓴다 |
| `memory` | turn 3 의 `memory` + `history_input.memory` | ⑤ ⑥ 의 메모리 칸 |
| `prior_turn_nos` · `history_present` · `history_turn_count` | 대화의 앞 턴 번호 · `history_input` 이 있었나 · 그 안의 user 메시지 수 | 플래그(앞 턴 누락) |

**`pre_queries` 는 세 갈래이고 위가 이긴다.** 위로 갈수록 추정이 아니라 사실이다.

| | 출처 | 성격 | 상한 |
|---|---|---|---|
| 1 | `history_input.history_chat` 의 `role == "user"` | 모델에 실제로 들어간 질문 | 없음 |
| 2 | `prev_question` | 서비스가 적어 준 앞 질문 | 없음 |
| 3 | 턴 순서 재구성 (`carried_turn_nos` 가 있으면 그 번호만, 없으면 최근 `run.history_turns` 개) | 우리 추정 — 옛 로그 · 골든셋 | 3 |

1·2 에 상한을 안 거는 이유: 상한은 **추정**이 넓게 틀리는 걸 막는 장치다. 사실을 자르면 못 본 턴 대신 **본 턴**을 지우게 된다. 3 을 3개로 자르는 이유: 대명사 해소에 필요한 건 보통 직전 2~3턴이고, 더 오래된 질문을 추정으로 넣으면 노이즈라 판정자가 엉뚱한 주제로 끌려간다.

추정이 실제보다 **넓으면** 챗봇이 못 본 턴에서 "앞에서 한 요구" 를 찾아 사용자 묶음(새 요구)을 놓치고, **좁으면** 했던 요구를 새 요구로 읽는다. 어느 쪽이든 조용히 틀린다 — `history_input` 이 있는 로그에서는 앞 턴 누락 플래그가 누락을 세운다.

**청크 풀(`rag_chunks`)은 한 레코드 안의 네 자리를 더한 것이다.** 순서가 곧 중요도이고, 자리마다 출처가 `chunk_sources` 에 남는다.

```
[turn 3 retrieved_data] + [turn 3 tool_output]                      ← 이 턴 것 (own). n_fetched 는 이 길이
  + [history_input.retrieved_data] + [history_input.tool_output.outputs]   ← 과거 것 (carried)
```

- `tool_output` 을 문서와 같은 층에 두는 이유: 빼면 도구 결과를 제대로 쓴 답변이 "근거 없음" 으로 센다 — 도구 결과도 근거다.
- `tool_calls` 는 청크가 아니라 **별도 필드**다. 무엇을 물었는지는 근거 판정 대상이 아니다. 1단계에서는 판정에 안 쓰고 2단계 태그(도구 안 부름 · 인자 불일치)의 재료다.
- 청크 본문에 `turn_no` 같은 머리말을 붙이지 않는다. `quoted_spans` 와 인용 대조는 글자 그대로 연속 일치로 보므로, 로그에 없던 문자열이 생기면 대조가 깨진다.
- `history_input` 이 없는 옛 로그만 과거 턴 레코드를 돌아 `tool_output` 을 더한다. 둘 다 타면 같은 청크가 두 번 들어간다.
- 상한이 없다. 풀이 실데이터에서 실제로 커지는지를 결과 파일의 `chunk_data` 길이로 먼저 본다.

> 입력은 **완결된 형태로 들어온다고 가정한다** — `history_input` 에 과거 청크가 이미 구분되어 있고,
> 풀은 그 자리 넷을 더하는 것뿐이다. 사내 파서로 갈아끼우는 훅은 두지 않는다 (v0.87 에서 뺐다).

과거 턴의 문서가 풀에 들어오면 **근거 묶음이 생성 묶음으로 옮겨 간다.** 고칠 곳이 문서팀에서 생성 쪽으로 바뀐다. 그래서 ⑤ 는 "앞 턴 근거" 를 따로 칸으로 두고, 답이 거기에만 있었으면 `where` 가 그렇게 남는다.

**`memory` 는 ④ 불만 판정에 넣지 않는다.** 서비스가 들고 있던 **사용자에 대한 정보**이고, 다른 LLM 이 쓴 해석이라 넘기면 판정이 그쪽으로 끌려간다. 대신 ⑤ 근거 판정의 한 칸(메모리)으로 들어간다 — 답이 거기에만 있었으면 생성 묶음에 `where = 메모리` 로 남는다.

### 여기서 버리는 것

| 필드 | 왜 안 쓰나 |
|---|---|
| `event_time` | 지연 판정에 쓸 수 없다. 턴 시각 차이에는 사용자가 생각한 시간이 섞여 있다 |
| `trace_matched` | "2턴 이상"은 실제 턴 수로 판정한다. 선언값과 실제가 어긋난 로그를 본 적이 있다 |
| `ask_on` `answered_by` `route_intent` `fallback` | 실패의 원인이 아니라 실패가 일어난 자리다. 집계 축이지 판정 입력이 아니다 |
| `llm_eval_*` `llm_emotion_*` | ②에서만 쓰고 판정에는 넘기지 않는다 (아래) |

## ② 필터

**목적** — **무엇을 볼지 고르기만 한다.** 판정이 아니다.

**입력** — `filter-data` JSON + ①의 후보 턴들

| 필터가 보는 것 | 로그 필드 |
|---|---|
| 직급 · 부서 · 직무 | `job_grade` `db_dept_name` `db_job_name` |
| 턴 구간 | `turn` |
| 기간 | `event_time` |
| 대화 유형 점수 · 라벨 | `llm_eval_result` `llm_eval_score` `llm_eval_alternatives` |
| 감정 점수 · 라벨 | `llm_emotion_result` `llm_emotion_score` `llm_emotion_alternatives` |

**출력** — 선별된 턴 + **단계별 탈락 기록**

```
진단 가능 후속 턴 (2턴 이상 대화)   73
직급(role)                          58   (-15)
부서                                42   (-16)
턴 구간                             42
eval_score (0.0, 50.0)              37   (-5)
emotion_score (0.0, 30.0)           37
```

몇 건이 어디서 빠졌는지 전부 찍는다. 조용히 줄어들면 "이 조건에는 원래 없다"와
"필터가 잘못 걸렸다"를 구분할 수 없다.

첫 줄의 **후속 턴** 은 `turn ≥ 2` 이고 같은 대화에 `turn − 1` 이 있는 턴이다 (2026-10-27 까지는
`llm_eval_result` 가 있나로 봤다 — eval 이 비어 오는 eval.jsonl 이 생겨 턴 번호로 바꿨다).
eval.jsonl 경로에서는 이 필터가 `assemble.py select` 안에서 **같은 코드로** 돌고, `llm_eval_*` 가
비어 오므로 eval 조건이 있으면 걸지 않고 예외로 멈춘다. `--turns` 로 들어온 뒤에는 다시 안 건다.

### 필터가 쓴 값을 판정에 넘기지 않는 이유

`llm_eval_result`(질의 유형 라벨)와 `llm_emotion_result`(감정 라벨)는
**이미 다른 시스템이 내린 판정**이다. 이걸 ④에 넘기면 kev 가 그 라벨에 맞춰
답을 고른다 — 독립적인 두 번째 의견이어야 할 것이 첫 번째 의견의 확인 도장이 된다.

필터는 "어떤 턴을 볼까"만 정하고, "그 턴에 무슨 일이 있었나"는 처음부터 다시 본다.

> 실행 환경에는 필터가 이미 구현돼 있다. 이 저장소의 `filters.py` 는 여기서 검증할 때만
> 쓴다. 경계는 `Case` 이고, `Case` 를 만들어 넣을 수만 있으면 ③부터는 그대로 돈다.

## 플래그 열 — 멈추지 않는다

**목적** — 트리 밖의 사실 셋을 턴마다 적는다. 판정에 안 끼어든다.

| 플래그 | 어떻게 | 왜 라벨이 아닌가 |
|---|---|---|
| 앞 턴 누락 | 대화의 앞 턴 수 ↔ `history_chat` 의 user 메시지 수 (`prior_turn_nos` · `history_turn_count`). `history_input` 자체가 없는 옛 로그는 "판정 안 함" | 모델이 못 본 것인지 로그가 떨어뜨린 것인지 못 가른다 |
| history 재구성 턴 수 | `history_chat` 이 비어 턴 순서로 되살린 턴 수 (`Case.history_reconstructed`) | 추정이라는 표시 |
| 질문에 개인정보 | `pre_queries[-1]` 의 개인정보 패턴. 종류 · 건수만, 값은 안 남긴다 | 답변의 성패와 독립인 사건 |

코드: `features/integrity`, `features/pii`.

## ③ 코드 확정 — kev 보다 먼저, 코드로

**목적** — 판정할 답이 없는 턴을 kev 전에 닫는다. kev 에 넣으면 판정자가 자원 부족 문구를 거절로
읽어 권한 정책 쪽으로 보낸다 — 고칠 곳이 정반대다.

**입력** — `Case.llm_ans_on_last_q` 하나. 불만은 안 본다 — 답이 없으면 불평 여부와 무관하게 시스템이다.

| 순서 | 규칙 | 어떻게 |
|---|---|---|
| 1 | 자원 부족 문구 | 공백을 지운 답변에 설정 `service_error.templates` 의 문구가 통째로 들어 있다. 비슷한 문구는 안 잡는다 |
| 2 | 빈 답변 | 공백 지우고 아무것도 없다 |
| 3 | 붕괴 | 같은 글자·기호의 붙은 반복뿐 — 글자 2종 이하 · 짧은 조각 되풀이 · 글자 없음 · 끝에 긴 반복 |

처음 걸린 규칙에서 멈추고 뒤 규칙은 "보지 않음" 으로 적는다. 안 걸린 규칙의 결과도 남긴다 ("봤는데
아니었다"). 걸리면 시스템 · 확실 · kev 0.

셋 다 걸리면 확실하고 다른 점은 놓치는 양이다. 붕괴는 보수적이라 토큰 잡탕 · 조금씩 바뀌는 되풀이
· 템플릿 토큰을 못 잡는데, 그건 ④ 의 "읽을 수 없는 글" 문항이 받는다.

코드: `features/code_rules` (`service_error` · `empty_answer` · `degenerate`).

## ④ 불만 판정 — 사용자가 무엇을 불평했나

**목적** — 후속 발화와 답변만 보고 정상 · 시스템 · 생성 · 사용자를 가르고, 내용 불만만 ⑤ 로 넘긴다.

**입력 넷** — `history`(아래 규칙) · turn N 질문 · turn N 답변 · turn N+1 발화.
**안 주는 것** — 문서 · 도구 결과 · memory · 앞 턴 청크. 주면 kev 가 "답이 맞았나" 를 재기 시작하고
그건 ⑤ 의 일이다.

**문항 여덟, 요청 하나** (`questions.COMPLAINT`, 순서가 읽는 순서) — [taxonomy.md](taxonomy.md)
의 표. 코드가 1→8 순서로 읽어 처음 걸리는 데서 멈춘다. 1 이 아니오면 2~8 이 뭐라 했든 정상이다.
2~5 는 답변 자체가 보여 주는 사실이라 후속 발화의 성격(6 · 7)보다 앞이다 — 끊긴 답에 욕만
했어도 끊긴 건 시스템이다. 6 · 7 이 8 과 ⑤ 보다 앞인 건, 단서가 없거나 요구가 바뀐 불만은 원래
질문의 근거를 재 봐야 뜻이 없어서다.

**history 규칙** — `history_chat` 이 있으면 그대로(상한 없음 — 사실은 자르지 않는다). 비었고 앞 턴이
있으면 턴 순서로 **최근 3턴**을 재구성한다 (`carried_turn_nos` 가 있으면 그 턴들, 없으면 최근 것).
재구성은 "사용자가 전에 그 요구를 했나"(7) 를 위한 것이고, 모델이 그걸 봤는지는 앞 턴 누락
플래그가 따로 말한다.

**출력** — `steps` 에 여덟 답 전부 (멈춘 뒤의 것도 — 검토할 때 "뒤는 뭐라 했나" 가 보인다).
모름이면 그 문항에서 멈춰 검토.

코드: `features/complaint`.

## ⑤ 근거 판정 — 근거에 답이 있었나

**목적** — turn N 이 볼 수 있었던 근거에 질문의 답이 있었나. 있었으면 생성, 없었으면 근거.

**입력** — turn N 질문 + 근거 네 칸.
**안 주는 것** — 답변 · 후속 발화. 근거 유무는 답변과 무관하고, 주면 kev 가 답의 옳고 그름을 잰다.

| 칸 | 출처 |
|---|---|
| 이번 턴 검색 청크 | `retrieved_data` |
| 이번 턴 도구 결과 | `tool_output` |
| 앞 턴 근거 | `history_input.retrieved_data` + `history_input.tool_output` |
| 메모리 | `memory` + `history_input.memory` |

**문항 다섯, 요청 하나** — 칸별 넷("일부라도 답하는 내용이 있나")과 전체 하나("전부 · 일부 · 없음").
빈 칸의 문항은 묻지 않는다. 묶음은 **전체 문항 하나**가 정하고 칸별은 `where`(어디에 있었나)로
남는다 — 칸마다 따로 물으면 답이 두 칸에 반씩 걸친 복합 질문을 칸별 전부 아니오로 놓치기 때문에
전체 문항이 그 구멍을 막는다. 칸별이 모름이어도 묶음에 안 끼어든다.

```
전체 = 전부  → 생성 (where = 칸별 예인 칸)
전체 = 없음  → 근거 (where = 빈 칸 · 아니오 칸)
전체 = 일부  → ⑥ 으로
전체 = 모름  → 검토
네 칸 전부 빔 → kev 안 부르고 근거(빈 묶음). where = 네 칸 전부
```

코드: `features/evidence`.

## ⑥ 불만 부분 근거 판정 — 근거가 일부일 때만

**목적** — 질문이 둘을 묻고 근거가 하나만 덮었을 때, 사용자가 **빠진 쪽**을 불평했으면 근거,
**있던 쪽**을 틀렸다고 불평했으면 생성. ⑤ 는 후속 발화를 안 봐서 이 둘을 못 가른다.

**입력** — turn N 질문 · turn N+1 발화 · 근거 네 칸. 답변은 여기서도 안 준다.

**문항 하나** — "불만이 가리키는 부분에 답이 근거에 있다". 예 → 생성, 아니오 → 근거, 모름 → 검토.

⑤ 의 여섯째 문항으로 넣지 않고 따로 요청하는 이유: 같은 요청에 넣으면 state 에 후속 발화가 들어가
⑤ 의 다섯 문항 전부가 불만을 본 채로 채점된다.

코드: `features/complaint_evidence`.

## 한 턴이 낳는 것 전부

```json
{
  "chat_id": "c-0192", "turn": 4, "event_time": "…", "target_turn": 3, "target_event_time": "…",
  "verdict": { "bucket": "생성", "sure": true, "stopped_at": "근거 판정",
               "because": "근거에 답이 전부 있었는데 답변이 살리지 못했다", "where": ["이번 턴 검색 청크"] },
  "steps":  [ { "step": "코드 확정", "rules": { "자원 부족 문구": "아니오", "빈 답변": "아니오", "붕괴": "아니오" } },
              { "step": "불만 판정", "answers": { "후속 발화가 답변을 문제 삼는다": { "answer": "예", "p": 0.97 }, "…": "…" } },
              { "step": "근거 판정", "answers": { "이번 턴 검색 청크에 답이 있다": { "answer": "예", "p": 0.95 },
                                                 "이번 턴 도구 결과에 답이 있다": "비어 있어 묻지 않음", "…": "…" } } ],
  "flags":  { "앞 턴 누락": false, "history 재구성 턴 수": 0, "질문에 개인정보": false },
  "axes":   { "부서": "…", "직급": "…", "직무": "…", "answered_by": "rag", "ask_on": "web", "fallback": "" },
  "text":   { "question": "…", "answer": "…", "followup": "…", "history": [], "이번 턴 검색 청크": ["…"], "…": [] }
}
```

- `verdict` 다섯 키 고정. `because` 는 멈춘 자리마다 **고정 문장**(`taxonomy.BECAUSE`)이라 같은
  결론은 늘 같은 문장이다. 검토면 `stopped_at` 이 `"불만 판정 · <문항 문장>"` 이고 `because` 에
  확률이 붙는다.
- `steps` 는 돈 단계만, 순서대로. 문항 문장이 키다 (`questions.TEXT`). `p` 는 **보인 답의
  확신**이고 ("아니오 0.95" = 확신 있는 아니오), 모름일 때만 P(예) 그대로다.
- 식별자는 둘 — `turn` · `event_time` 은 불만 턴(N+1), `target_*` 는 답변 턴(N).
- `text` 는 `--no-text` 로 뺀다. 전달본 · 대시보드가 결과 파일만 읽어 사례를 만들므로 기본은 싣는다.
- 판정이 실패한 턴은 식별자 다섯과 `error` 만 (`[단계] 예외` · `[단계] 낙오`).

파일 머리 `summary` 에 묶음별 · 멈춘 단계별 · 막힌 문항별(`review_at`) 건수가 있다.
